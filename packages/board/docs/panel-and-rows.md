# Luca board: the panel and the chat rows

The plugin shows a run in two places:

- **The side panel** ("Luca board", a workspace tab that also opens in the Explorer). From top to bottom it shows:
  - plan usage (five-hour and weekly), from the rate-limit readings in the agents' sessions, colored green below 60%, yellow from 60% to 85%, and red above 85%
  - how much of the plan the whole run used, once the engine records it
  - a banner when the run stopped (for example, the wrong credentials, or a billing stop) or its engine stopped
  - a limit-wait banner that names the window that was hit
  - a repo-wait banner (#632), while the run waits for an earlier run on the same repo (#615), from `repo_wait_started` until `repo_wait_ended`: "waiting for run 20260923t113000z-5b1e0c2a on this repo · 12m 5s", in amber, with the amber bar of a wait on purpose and a time that counts up
  - **Needs you**, pinned on top: stuck work, with the reason, what was tried, and a button for each reply the engine takes, and **Help me** (see [Replying from the board](replying.md))
  - the tickets, as a stack of stages: Blocked → Building → Reviewing → Testing → Fixing → Joining → Done → Skipped. A stage says what the ticket is really doing (#549): Building is its first test-writer and implementer pass; Reviewing, only while a reviewer works; Testing, the red check or the checks running; Fixing, any fix round (after the checks, a review, or a join); Joining, joining the run branch and the checks there, until the run branch is pushed. Each card has step dots for tests → red check → code → checks → review. A refactor ticket's first two dots are dashed, because it skips them. Done and Skipped start folded. A card shows how much of the plan its ticket used, once the engine records it. Tap a card for its details.
  - **For a person**, only when the run left some tickets out (#499): the tickets labeled `ready-for-human`, and the ones that wait on them, each with why ("for a person", or "waits on #12, which is for a person"). They aren't a problem, so this is a quiet, muted list that starts folded, never in **Needs you**.
  - the final review's 5 lenses, as a second stack (Waiting → Reviewing → Fixing → Clean). It stays dimmed until every ticket is done or skipped. A run that ended with nothing to do, or that intake refused, has nothing to review, so the panel leaves this section out and the header row says "none, nothing to review".
  - **the live feed** (#634), a folded section ("Live feed"): the run's last 50 actions from the live file's `feed`, across tickets. A tap opens it: one line per action, newest last, with its time, its ticket, the role in its model's colour (a helper's actions read "helper", in Haiku's colour), and the action ("✎ editing gate-runner.ts"). A reload shows the actions the live file holds. While the panel is open, the feed stays open or folded as it was left.
  - the footer: the run id, its event count and whether the engine runs, and the counters.
  - **the status bar** (#633), pinned at the bottom while the cards scroll, on one line: "4/10 joined · 2·1 agents · 3.1M/15M tok · week 42% · latest 2s ago". That is the tickets joined out of the run's tickets; the agents in a turn (from the live file), counted per model, each count in its model's colour; the run's tokens out of its run budget; plan use this week ("week –" before the first reading); and the latest event's age, counting up every second. It repeats the header's tokens and plan use on purpose, since the header scrolls away. A tap shows it all in words: "4 of 10 tickets joined · agents running: 2 on opus, 1 on sonnet · 3.1M of the run's 15M tokens · plan 42% used this week · latest event 2s ago".
- **The live file** (#628): while a run goes, the engine keeps `live.json` in the run folder (`<runs_dir>/<run_id>/live.json`), beside the journal but never in it: what each agent in a turn is doing now, with its helpers (`agents[].helpers`: each one's model, latest action and whether it's done), each ticket check's wait for a slot (`waits`), the run's last 50 actions (`feed`), and the run's first plan-usage reading. Its full shape is in the engine's docs (`packages/engine/docs/board-and-command-line.md`, "The live file"); the board reads it with its own schema (`shared/board-state-live.ts`), so the two must change together. The plugin reads it on each `board.read` for the selected run, whether it started the run or not, and lays it over the state the journal made (`server/live-file.ts`); only the latest file counts, and nothing of it is stored. A card with a live entry says who is working and on what next to its step dots, in place of the step text ("implementer ✎ editing gate-runner.ts"), and, while a tool call is open, how long it has run ("implementer ▸ bun test · running 3m 12s"). Its tokens count up with the turn, followed by the latest action's age ("3.7k tokens · 2s ago"). The panel's plan usage fills in from the live file's first reading until the journal has one. A check waiting inside its step for a prepare slot or a test slot (#632, the file's `waits`) turns its card's pill to "waiting", in amber, with the amber bar and "waiting for a prepare slot (1 of 1 in use)" or "waiting for a test slot (2 of 2 in use)" and how long, in place of the step text; once the slot is taken, the check's text comes back. With no live file (an old run), a card shows its step text as before.
- **The heartbeat** (#631): a busy card with a live entry ends its step-dots line in 20 small bars, one per second, oldest on the left, each as tall as its agent's activity that second (the newest 20 of the live file's 30 `activity` counts). They are green while working, and a flat line in the muted colour when those seconds had no activity. Done, skipped, stuck and blocked cards have none, and a waiting card has its amber bar instead. The bars are plain `View`s (`client/heartbeat.tsx`), redrawn with the card on the board's 1-second tick.
- **Helper lines** (#636): under a card's step-dots line, each helper its agent has running gets one line, with a left edge in the helper's model colour (Haiku blue): "helper", the model as a coloured tag, its latest action, and how long ago ("helper [haiku] ⌕ finding callers of createSlots 4s ago"). The line goes away once the helper is done, and a card with no helpers looks as before. The status bar counts running helpers with the agents, in Haiku's colour (`client/helper-lines.tsx`).
- **Engine not running** (#635): a run whose engine is gone or hung says so, whoever started it. The plugin's process check (every 15 seconds) also covers the runs it didn't start, and only labels those, never restarts them; a live file whose `written_at` is more than 60 seconds old means the engine is hung or gone. Either way, while the run still needs an engine (not ended, not over), its busy and waiting cards read "engine not running · last sign of life 3m 40s ago" (no engine process) or "no sign of life for 1m 10s" (a stale live file) in red on their step-dots line, in place of a wait; their heartbeat is a flat red line, and their timers stop at the last sign of life. The header's "Now:" step stops its time there too, the repo-wait banner turns red, stops its time and adds the same words, and the footer's engine word says so (`client/engine-life.ts`). A long tool call, with the live file still rewritten every 5 seconds, shows neither.
- **One line, tap for more** (#626): every line of a ticket card, and every footer line, stays on one line. Text that doesn't fit ends in "…". A tap on a cut line opens a small bubble with all of its text; a second tap, or a tap anywhere else on the panel, closes it. On a computer, hovering opens it too. One bubble is open at a time. The fixed parts never shrink or get cut: the ticket number, the status pill, the step dots, the `fix n/3` and `review n/3` chips, the tokens, and any tag. Only the text beside them gives way. The chat rows still wrap in full.
- **Model tags and Clef's line** (#630): while an agent works on a ticket, its card has a line with the agent's model as a coloured tag: Opus purple, Sonnet orange, Haiku blue, Clef green, and the engine muted. These are fixed hues that read on light and dark themes, the one exception to "every colour from the host theme". A model the board doesn't know gets the muted colour. Beside the tag, Clef's line says why the agent got that model, from `agent_started` (`model` and `model_reason`) and the agent's `agent_model` answer (Clef's pick and confidence). When Clef's pick decided it, a small bar is filled to Clef's confidence: green when sharp (at or over the config's `models.confidence_bar`, 0.8 by default), orange when split (under it). The short texts:
  - `decision_model`: "0.92 sharp → sonnet"
  - `unsure`: "0.56 split → stayed on opus"
  - `floor`: "floor opus → opus"
  - `after_failure`: "a try failed → opus"
  - `no_answer`: "clef didn't answer → opus"
  - `locked`: "<role>s always run on opus", like "ticket-reviewers always run on opus"

  A tap on the line shows a full sentence, like "Clef picked sonnet but was only 0.56 sure (split: under 0.8), so Luca stayed on opus." An older journal, with no `model_reason`, shows the tag only.
- **Live rows in the chat where you started the run**: a header row that updates in place, one row per meaningful event, stuck rows with the same reply buttons and **Help me**, and a limit-wait row. The rows never reach the model.

The code reuses the designs of the board prototype (`prototype/paseo-board`: variant B v2 for the panel and variant C for the rows), but none of its code.
