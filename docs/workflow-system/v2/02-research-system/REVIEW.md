# Review: 02-research-system

## Reviewer: Research System Reviewer (Cold Isolation)

## Date: 2026-03-22

## Iteration: 1

## Summary Assessment

The research system documentation is thorough, well-structured, and internally consistent within its own four files. The multi-agent research model, source confidence hierarchy, file format specification, and convergence logic are all specified to a level of detail sufficient for implementation. However, there are meaningful inconsistencies between this section and the cross-referenced documents in `04-agent-orchestration/research-team.md` and `05-review-loops/research-review-protocol.md`, particularly around pipeline step numbering, file directory layouts, gap ID conventions, token budgets, and the convergence decision tree for IMPORTANT gaps. Several edge cases in the confidence model and convergence logic deserve explicit handling.

## Critical Findings

- **CRIT-RS-001**: `05-review-loops/research-review-protocol.md` (lines 9-34) -- **Pipeline step numbering contradicts 02-research-system/README.md.** The review-loops document places research at Steps 2 and 4, discuss/pre-mortem at Step 3, and research review at Step 5. The research system README (line 13-26) places research at Step 4, discussion at Step 5, and does not mention the review loop as a numbered step -- it describes it as part of the research phase's internal loop. This creates ambiguity about whether "research review" is Step 5 of the main pipeline or an internal sub-step of Step 4. -- **Suggested resolution**: Establish a single canonical step numbering in the `01-workflow-steps/` README and ensure all sections reference it consistently. Document whether the review loop is a top-level step or an internal sub-process.

- **CRIT-RS-002**: `05-review-loops/research-review-protocol.md` vs `02-research-system/research-file-structure.md` -- **Research file directory layout is inconsistent.** The research-review-protocol.md (lines 67-69, 347-355) shows a flat directory under `.planning/research/` with a `deep/` subdirectory for deep expansions. The research-file-structure.md (lines 7-19) shows research files nested under `.planning/phases/NN-name/research/` with no `deep/` subdirectory -- deep expands are numbered `05+` in the same directory. These are structurally incompatible layouts. An implementer would not know which directory structure to create. -- **Suggested resolution**: Pick one canonical layout. The `02-research-system` version (`.planning/phases/NN-name/research/`) is more specific and aligns with phase-scoped work. Update `05-review-loops/research-review-protocol.md` to use the same layout.

- **CRIT-RS-003**: `05-review-loops/research-review-protocol.md` vs `02-research-system/review-loop-convergence.md` -- **Gap ID naming conventions conflict.** The review-loop-convergence.md (lines 214-226) uses `G-COMP-NNN`, `G-ACC-NNN`, `G-ACT-NNN` for gap identifiers. The research-review-protocol.md (lines 146-152) uses `GAP-C-NNN`, `GAP-I-NNN`, `GAP-M-NNN`, `ACC-NNN` -- categorized by severity rather than reviewer. These two systems are not interchangeable. A gap identifier scheme based on reviewer prefix (G-COMP, G-ACC, G-ACT) tells you who found it; a scheme based on severity prefix (GAP-C, GAP-I, GAP-M) tells you how bad it is. Both are useful, but using both without reconciliation means cross-references between REVIEW-LOG.md and the review protocol will break. -- **Suggested resolution**: Adopt one convention. The reviewer-prefixed scheme from `02-research-system` (G-COMP-NNN) is more informative because severity can change across iterations, but the reviewer who found it is stable. Add severity as a field on each gap, not embedded in the ID.

## Important Findings

- **IMP-RS-001**: `multi-agent-research.md` vs `04-agent-orchestration/research-team.md` -- **Token budget numbers diverge significantly.** `multi-agent-research.md` (lines 275-281) specifies per-researcher budgets of 8K-50K tokens across complexity levels, with totals of 32K-200K. `research-team.md` (lines 900-908) specifies per-agent budgets of ~2K-12K tokens. For MODERATE complexity, `multi-agent-research.md` says 20K per agent / 80K total; `research-team.md` says ~8K per agent. The 2.5x discrepancy is large enough to produce different behavior -- an agent given 8K tokens will produce fundamentally different research than one given 20K tokens. -- **Suggested resolution**: Determine the intended budget and update both documents. If the agent orchestration doc describes the output token count (what the agent writes) while the research system doc describes the full context budget (input + output + tool calls), document this distinction explicitly in both places.

- **IMP-RS-002**: `review-loop-convergence.md` (lines 228-241) vs `05-review-loops/research-review-protocol.md` (lines 186-217) -- **IMPORTANT gap handling on loop continuation differs.** The convergence doc says that when 0 CRITICAL gaps remain and IMPORTANT gaps exist, the loop continues only if `config.continue_for_important == true` AND `iteration < max_iterations - 1`. The review protocol's decision tree (lines 213-214) says: "Only IMPORTANT gaps and iteration < max --> LOOP" and "Only IMPORTANT gaps and iteration >= max --> APPROVED" -- with no mention of a `continue_for_important` config toggle. The review protocol always loops on IMPORTANT gaps if budget allows; the convergence doc makes this configurable. -- **Suggested resolution**: The convergence doc is more detailed and should be authoritative. Update the review protocol decision tree to reference the `continue_for_important` config and the `max_iterations - 1` reservation.

- **IMP-RS-003**: `source-confidence-model.md` (lines 256-263) -- **Staleness threshold for "0-6 months: No adjustment" is ambiguous for very fast degrading source types.** The staleness exceptions table (lines 268-276) says npm/package metadata has "Very fast degradation (3+ months)" and community practices degrade at "6+ months". But the staleness thresholds table (line 259) says "0-6 months: No adjustment." These contradict: a source type that degrades at 3 months should not get "No adjustment" for 6 months. -- **Suggested resolution**: Add a column or note to the staleness thresholds table clarifying that the generic thresholds are overridden by source-type-specific degradation rates from the exceptions table. Or better, produce a merged table that shows the effective threshold per source type.

- **IMP-RS-004**: `multi-agent-research.md` (lines 295-352) -- **Custom researcher configuration lacks a schema definition.** The JSON config example for custom researchers (lines 339-352) introduces fields (`name`, `agent_id`, `output_file`, `phases`) but there is no Zod schema or formal type definition for this structure. Given the project's schema-first-parsing rule, this should be defined as a Zod schema. -- **Suggested resolution**: Add a reference to where the Zod schema for `research.custom_researchers` should live (e.g., `src/agents/__schemas/research.schemas.ts`), or add a note that the schema will be created during implementation.

- **IMP-RS-005**: `04-agent-orchestration/research-team.md` -- **Agent output format in research-team.md differs from the mandatory format in research-file-structure.md.** The output templates in research-team.md (e.g., lines 168-228 for architecture researcher) use a different structure than the "Standard Research File Format" defined in research-file-structure.md (lines 53-121). For example, research-team.md uses section headers like "Recommended Architecture", "Component Map", "Design Patterns", "Anti-Patterns", "Codebase Consistency" -- while research-file-structure.md mandates Summary, Findings (with F-PREFIX-NNN numbering), Sources (with tier grouping), and Metadata. The agent prompt templates would produce output that fails the mandatory format check. -- **Suggested resolution**: Either update the agent prompt templates in research-team.md to produce output matching the mandatory format from research-file-structure.md, or document that the format in research-file-structure.md is a post-processing target and the raw agent output uses a different structure that is transformed during synthesis.

## Minor Findings

- **MIN-RS-001**: `review-loop-convergence.md` (lines 364-366) -- **Division by zero in diminishing returns formula.** The formula `gap_reduction_rate = (gaps_previous - gaps_current) / gaps_previous` produces a division-by-zero error when `gaps_previous == 0`. This occurs at the start of the review loop if Iteration 1 produces zero gaps (all reviewers approve). While the convergence criteria would already trigger CONVERGED before reaching diminishing returns detection, the formula should explicitly handle this edge case. -- **Suggested resolution**: Add a guard: "If `gaps_previous == 0`, the loop has converged and diminishing returns detection does not apply."

- **MIN-RS-002**: `research-file-structure.md` (lines 270-277) -- **Confidence breakdown in Metadata section has no guidance on what constitutes an acceptable distribution.** The format specifies `[X] HIGH, [Y] MEDIUM, [Z] LOW` but does not define what ratio is acceptable. A file with 0 HIGH and 8 LOW findings is technically valid by format, but would signal a quality problem. -- **Suggested resolution**: Add guidance such as "A research file with fewer than 50% of findings at MEDIUM or higher confidence should be flagged by the Accuracy Reviewer for insufficient verification effort."

- **MIN-RS-003**: `source-confidence-model.md` (line 277) -- **UNVERIFIED confidence level is defined as "Do not include in research output" but is still listed in the confidence level table as a valid level.** If UNVERIFIED findings must never appear in output, the level effectively does not exist in the output format. Having it in the table creates ambiguity about whether a researcher might legitimately output an UNVERIFIED finding as a placeholder. -- **Suggested resolution**: Clarify that UNVERIFIED is an internal classification used during the verification protocol. It should never appear in the final research file. Add "(internal only -- never in output)" to the table entry.

- **MIN-RS-004**: `review-loop-convergence.md` (lines 298-300) -- **Convergence formal criteria (lines 303-310) do not account for the CONVERGED_WITH_NOTES state.** The formal criteria show convergence requires `total_important_gaps == 0 OR config.continue_for_important == false`. But the convergence states table (line 318) defines CONVERGED_WITH_NOTES as "0 CRITICAL, some IMPORTANT gaps accepted." The formal criteria would produce CONVERGED (not CONVERGED_WITH_NOTES) when `continue_for_important == false` even if IMPORTANT gaps exist. The mapping from formal criteria to convergence state names is not specified. -- **Suggested resolution**: Add a mapping that explicitly connects the formal criteria outputs to the four convergence states.

- **MIN-RS-005**: `multi-agent-research.md` (line 370) -- **Reference to `lu-research-synthesizer` from v1 continuing to exist is not documented elsewhere.** The synthesizer agent is mentioned as producing GRADUATION-REPORT.md but has no agent specification in `04-agent-orchestration/research-team.md` (which covers only the four researchers, not the synthesizer or reviewers). -- **Suggested resolution**: Either add a reference to where the synthesizer agent is specified, or note that its specification lives in a different document (e.g., `04-agent-orchestration/graduation-agent.md` as referenced in research-team.md line 913).

## Verdict: NEEDS REVISION

The three critical findings (pipeline step numbering conflict, directory layout conflict, gap ID convention conflict) must be resolved before this documentation could be reliably implemented. An engineer following `02-research-system` would produce a different system than one following `05-review-loops/research-review-protocol.md`. The important findings (token budget mismatch, output format mismatch, IMPORTANT gap handling divergence) further complicate consistent implementation. The internal quality of the four `02-research-system` files is high -- the issues are primarily at the seams where this section interfaces with the agent orchestration and review loops sections.
