# Research: State is Data, Not Documents (Learning 9)

> **Learning:** GSD2 uses structured files throughout: YAML frontmatter in summaries, JSON for verification, structured state files. The orchestrator reads data, not prose. When the orchestrator needs to make a routing decision, it parses JSON -- it never asks an LLM to interpret a markdown file.
>
> **Cross-references:** Learning 5 (structured verification), Learning 10 (crash recovery), Learning 7 (ceremony audit)

## Current Dual State Problem

Luca maintains two representations of workflow state that must stay synchronized:

### 1. state.json (typed, machine-readable)

Location: `.planning/state.json`

The XState state machine persisted to disk. Contains:

```json
{
  "status": "active",
  "value": "idle",                    // current machine state
  "historyValue": {},
  "context": {
    "session_id": "...",
    "complexity": "TRIVIAL",
    "oversight": "full-auto",
    "phase_results": [],
    "verification_attempts": 0,
    "intuition_flags": [],
    ...40+ fields defined in WorkflowContext
  },
  "children": {}
}
```

**Strengths:** Typed via Zod schemas (`workflowContextSchema`). Machine-parseable. Full workflow context. XState-native format.

**Weaknesses:** XState envelope format (`status`, `value`, `historyValue`, `children`) wraps the actual context. The `context` field is the useful data, but callers must unwrap it. Deep nesting makes simple reads cumbersome.

### 2. STATE.md (human-readable, markdown)

Location: `.planning/STATE.md`

A derived markdown view generated by `luca-bridge snapshot`. Contains:

```markdown
# Project State

## Current Position

- **Status:** Idle
- **Task Complexity:** TRIVIAL
- **Oversight:** full-auto

## Session Identity

- **Session ID:** ...

## Progress

(no phases completed yet)

## Allowed Events

- `START`

## Previous Milestones

- v8.5.2 -- Statusline HUD & Edit Gate (2026-03-30)
  ...
```

**Strengths:** Human-readable at a glance. Shows milestone history. Lists allowed events.

**Weaknesses:** Must be regenerated after every state change. Contains no data that state.json does not. An LLM reading STATE.md to determine workflow position is burning tokens on prose parsing when it could read a JSON field.

### The synchronization burden

The `luca-bridge` CLI maintains a **dual-write guarantee**: every state transition writes to both `state.json` AND regenerates `STATE.md`. This introduces:

1. **Two write paths** that must stay in sync
2. **Two read paths** that agents choose between (bridge reads JSON; legacy agents grep STATE.md)
3. **Inconsistency risk** if one write succeeds and the other fails
4. **Overhead** from snapshot generation on every transition

### Where STATE.md is currently read

From `lu.skill.ts` and other skills/agents, STATE.md is read via:

- `grep "Task Complexity:" .planning/STATE.md` (fallback for complexity)
- General markdown reads for human inspection
- Legacy skills that predate the bridge

From the bridge CLI:

- `luca-bridge snapshot` generates STATE.md from state.json
- Bridge read commands already return JSON from state.json directly

## Proposed: state.json as Sole Source of Truth

### What changes

1. **state.json remains the canonical state file.** No change to its role.
2. **STATE.md becomes a derived convenience view,** generated on-demand only (not on every transition).
3. **All orchestrator reads go through state.json** (via bridge or direct file read). No more grep-ing STATE.md for data.
4. **Dual-write guarantee is eliminated.** Bridge writes to state.json only. STATE.md generation becomes an explicit `luca-bridge snapshot` call, run at session boundaries or on user request.

### What happens to STATE.md

**Option A: On-demand derived view (recommended)**

STATE.md continues to exist as a human-readable view, but it is:

- Generated only when explicitly requested (`luca-bridge snapshot`)
- Generated at session start and session end (not per transition)
- Never read programmatically by the orchestrator or agents
- Treated as ephemeral -- can be stale between snapshots

**Option B: Eliminate entirely**

STATE.md is deleted. Humans inspect state via `luca-bridge read-status` (which outputs formatted JSON or could output a human-readable summary). The statusline HUD already shows real-time state in the terminal.

**Recommendation: Option A.** STATE.md is valuable for humans inspecting `.planning/` in a file browser or GitHub PR review. It costs nothing if not generated per-transition. Make it on-demand.

## Schema Design for Comprehensive state.json

The current `workflowContextSchema` in `types.ts` already defines 40+ fields. However, the state.json file stores the XState snapshot format, which wraps the context in machine metadata. For direct reads, this is awkward.

### Proposed: Flatten the envelope

Add a `pipeline` section to the context that tracks orchestrator-level position explicitly:

```typescript
// New fields to add to workflowContextSchema
pipeline_position: z.object({
  current_step: z.enum([
    "init", "preflight", "classify", "configure", "git-setup",
    "backlog", "phase-order", "phase-loop", "milestone", "wrap-up"
  ]).default("init"),
  current_phase_step: z.enum([
    "dependency-check", "oversight-gate", "classify", "gates",
    "research", "discuss", "plan", "plan-review",
    "execute", "harness", "verify", "review", "review-fix",
    "learn", "process-data", "commit", "update-state", "gap-close"
  ]).optional(),
  loop_index: z.number().int().nonnegative().default(0),
  remaining_phases: z.array(z.number().int()).default([]),
  completed_steps: z.array(z.string()).default([]),
  started_at: z.string().optional(),
}).optional(),

// New: structured verification results (replaces prose VERIFICATION.md)
verification_results: z.array(z.object({
  phase_id: z.number().int(),
  harness: z.object({
    status: z.enum(["passed", "failed"]),
    checks: z.array(z.object({
      name: z.string(),
      command: z.string(),
      exit_code: z.number().int(),
      duration_ms: z.number().int().nonnegative(),
      error_count: z.number().int().nonnegative().default(0),
    })),
    timestamp: z.string(),
  }).optional(),
  verification: z.object({
    status: z.enum(["passed", "failed", "partial"]),
    gaps: z.array(z.string()).default([]),
    coverage_percent: z.number().min(0).max(100).optional(),
    timestamp: z.string(),
  }).optional(),
  review: z.object({
    reviewers: z.array(z.object({
      name: z.string(),
      findings: z.array(z.object({
        severity: z.enum(["critical", "major", "minor", "info"]),
        message: z.string(),
        file: z.string().optional(),
        line: z.number().int().optional(),
      })),
      verdict: z.enum(["pass", "fail", "warn"]),
    })),
    timestamp: z.string(),
  }).optional(),
})).default([]),

// New: git workflow context (currently in lu-context.json)
git_workflow: z.object({
  issue_number: z.number().int().optional(),
  issue_url: z.string().optional(),
  branch_name: z.string().optional(),
  pr_number: z.number().int().optional(),
  pr_url: z.string().optional(),
  commits: z.array(z.object({
    hash: z.string(),
    phase_id: z.number().int(),
    message: z.string(),
    timestamp: z.string(),
  })).default([]),
}).optional(),

// New: token profile (from Learning 8)
token_profile: z.enum(["budget", "balanced", "quality"]).default("balanced"),
```

## Applying the Same Principle to Other Artifacts

### Verification output

**Current:** `VERIFICATION.md` (prose) + `harness-result.json` (structured, but separate file)

**Proposed:** Verification results live in `state.json` context as `verification_results[]`. The harness runner writes structured output directly to state via bridge. The verifier agent outputs JSON. VERIFICATION.md becomes a derived view (or is eliminated -- the PR description can be generated from structured data).

### Phase results

**Current:** Phase summaries in `{wave}-SUMMARY.md` (prose)

**Proposed:** Phase results in `state.json` context as `phase_results[]` with structured fields. Prose summaries can be generated from structured data at milestone boundary for human consumption.

### Milestone summaries

**Current:** `milestones/v{SEMVER}-AUDIT.md` (prose with tables)

**Proposed:** Milestone audit data in structured form. The audit file can still be generated as a derived markdown view for GitHub/human review, but the source data is JSON.

### Session ledger

**Current:** `.planning/session-ledger.jsonl` (already structured, append-only)

**Proposed:** No change. Session ledger is already the gold standard for structured state. It provides an append-only audit trail of all events.

## How luca-bridge Commands Change

### Current bridge commands and their state interactions

| Command           | Current behavior                          | Proposed change                                                                    |
| ----------------- | ----------------------------------------- | ---------------------------------------------------------------------------------- |
| `ensure-init`     | Creates state.json + STATE.md             | Creates state.json only. STATE.md on first snapshot.                               |
| `snapshot`        | Generates STATE.md from state.json        | Unchanged. Now explicitly on-demand instead of auto.                               |
| `transition`      | Writes state.json + regenerates STATE.md  | Writes state.json only. No STATE.md regeneration.                                  |
| `set-field`       | Writes state.json + regenerates STATE.md  | Writes state.json only.                                                            |
| `read-status`     | Reads state.json, returns JSON            | Unchanged.                                                                         |
| `read-complexity` | Reads state.json, returns JSON            | Unchanged.                                                                         |
| `read-phase`      | Reads state.json, returns JSON            | Unchanged.                                                                         |
| `read-field`      | Reads state.json, returns JSON            | Unchanged. Add new fields (pipeline_position, verification_results, git_workflow). |
| `suspend`         | Writes checkpoint + state.json + STATE.md | Writes checkpoint + state.json only.                                               |
| `resume-phase`    | Reads checkpoint + state.json             | Unchanged.                                                                         |

### New bridge commands (proposed)

| Command                                    | Purpose                                                                    |
| ------------------------------------------ | -------------------------------------------------------------------------- |
| `write-verification --phase=N --data=json` | Write structured verification result for a phase                           |
| `write-git --data=json`                    | Update git workflow context (issue, branch, commits)                       |
| `read-pipeline`                            | Read pipeline position (shortcut for read-field --field=pipeline_position) |

### Migration of existing bridge consumers

Skills and agents that currently grep STATE.md:

1. **Complexity fallback:** `grep "Task Complexity:" .planning/STATE.md` becomes `luca-bridge read-complexity` (already the primary path)
2. **Phase status:** `grep "Phase" .planning/STATE.md` becomes `luca-bridge read-phase`
3. **General state inspection:** Human reads STATE.md in editor -- unchanged, but STATE.md may be stale between snapshots

The migration is low-risk because the bridge is already the primary read path. STATE.md grep is already documented as a fallback. Removing the fallback simplifies the code path.

## Eliminating /tmp/lu-context.json

Currently, the `/lu` orchestrator uses `/tmp/lu-context.json` as a sidecar state file for:

- Loop index and remaining phases
- Git workflow context (issue number, branch name)
- Agent output accumulation

**Problem:** This is a second source of truth outside of state.json. It lives in /tmp (volatile, OS-managed). On crash, it may or may not survive.

**Proposed:** Merge lu-context.json into state.json:

- `pipeline_position` replaces loop index / remaining phases
- `git_workflow` replaces git workflow context
- Agent output accumulation stays in lu-context.json (ephemeral, session-scoped) OR moves to a session-scoped section of state.json

**Decision:** Keep lu-context.json for ephemeral agent output accumulation (it is large and per-session). Move pipeline position and git workflow to state.json (they are small and need crash recovery). This gives us the best of both: state.json has everything needed for deterministic recovery (Learning 10), lu-context.json holds accumulated agent output that is nice-to-have but not critical.

## Constraints from Claude Code Runtime

1. **File writes are atomic-ish.** Bun's `Bun.write()` is not transactional, but for single-file JSON writes it is effectively atomic (write-then-rename pattern). The dual-write problem disappears when we write only to state.json.

2. **Bridge CLI invocation cost.** Each `luca-bridge transition` spawns a Bun process to read state.json, apply the transition, and write back. This is ~100-200ms per call. Removing the STATE.md regeneration from each transition saves ~50ms of that.

3. **Agent prompt size.** Agents that currently read STATE.md in their prompts (to understand context) can instead receive a structured JSON summary. This is actually smaller than the markdown version, reducing prompt tokens.

4. **No filesystem events.** Claude Code does not provide filesystem watchers. State changes are detected by reading state.json, not by reacting to file changes. This is fine -- all state reads are explicit.

## Interaction with Other Learnings

- **Learning 5 (Structured Verification):** Verification results moving into state.json is a direct application. The `verification_results[]` array replaces VERIFICATION.md prose.

- **Learning 7 (Ceremony Audit):** Mechanical agents (process-data, learning capture) write structured JSON to state.json instead of producing prose. This enables their elimination as LLM agents -- they become TypeScript functions that call `luca-bridge set-field`.

- **Learning 8 (Token Profiles):** The `token_profile` field in state.json tells the orchestrator which profile is active. Profile-based decisions are deterministic reads from structured state.

- **Learning 10 (Crash Recovery):** This is the enabling learning. Deterministic crash recovery requires structured state. The `pipeline_position` object tells the orchestrator exactly where to resume. Without structured state, crash recovery requires LLM interpretation of STATE.md prose. See Learning 10 research for the full recovery algorithm.

## Risks and Tradeoffs

### Risk: STATE.md becomes stale

**Scenario:** Developer inspects STATE.md between snapshots and sees outdated information.
**Mitigation:** Add a timestamp + warning at the top of STATE.md: "Generated at {timestamp}. Run `luca-bridge snapshot` for current state." Also, the statusline HUD shows real-time state in the terminal.
**Decision:** Accept. Staleness of a derived view is a feature, not a bug. It trades consistency for performance (no per-transition regeneration).

### Risk: state.json grows too large

**Scenario:** After many phases, verification_results and phase_results arrays grow large.
**Mitigation:** Archive completed phase data to session-ledger.jsonl at phase boundaries. Keep only current + previous phase in state.json context. The ledger is the full history; state.json is working memory.
**Decision:** Implement archival at phase boundary. Cap state.json verification_results to last 3 phases.

### Risk: Breaking existing skills that read STATE.md

**Scenario:** Skills using grep-based STATE.md fallbacks break when STATE.md is stale or removed.
**Mitigation:** Phase the migration: (1) Stop dual-writing STATE.md per transition, but keep generating it at session start/end. (2) Update all skills to use bridge reads. (3) Only then consider eliminating STATE.md entirely. This is a multi-milestone migration.
**Decision:** Phase the migration. Never break existing skills in a single change.

## Recommendation

Adopt state.json as sole source of truth in two phases:

**Phase 1 (immediate):** Add `pipeline_position` and `git_workflow` to WorkflowContext schema. Migrate pipeline tracking from lu-context.json to state.json. Stop regenerating STATE.md on every transition (generate at session start/end only). This is the highest-value change with lowest risk.

**Phase 2 (next milestone):** Add `verification_results` to state.json. Update harness runner and verifier agent to write structured results via bridge. Migrate remaining STATE.md grep fallbacks to bridge reads. This completes the "state is data" transition and enables deterministic crash recovery (Learning 10).
