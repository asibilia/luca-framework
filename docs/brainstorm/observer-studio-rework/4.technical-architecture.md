# Technical Architecture: Luca Studio

## Write Layer Architecture

### Target Files and Schemas

| File                                        | Schema                                                              | Write Frequency       | Complexity             |
| ------------------------------------------- | ------------------------------------------------------------------- | --------------------- | ---------------------- |
| `.planning/config.json`                     | `LuConfigSchema` + `ComplexityConfigSchema` + `HarnessConfigSchema` | Every config toggle   | Low — flat JSON        |
| `src/agents/**/*.agent.ts`                  | `AgentConfigSchema` (frontmatter + sections)                        | Per agent edit        | High — TS round-trip   |
| `src/skills/**/*.skill.ts`                  | `SkillConfigSchema`                                                 | Per skill edit        | High — same TS problem |
| `src/rules/**/*.rule.ts`                    | `RuleConfigSchema`                                                  | Per rule toggle/edit  | High — same TS problem |
| `.planning/state.json`                      | XState context                                                      | Per state transition  | Low — JSON             |
| `src/complexity/__helpers/model-routing.ts` | `ModelRoutingTableSchema`                                           | Per routing cell edit | Medium — structured TS |

### Concurrency Model: ETag-Based Optimistic Locking

The real-world pattern is a single developer switching between their editor and Studio. Full locking is overkill.

- Every GET response includes `ETag: sha256(file_contents).substring(0, 16)`
- Every PUT/PATCH includes `If-Match: <etag>`
- API reads current file, computes hash, rejects with `409 Conflict` if diverged
- On 409, UI shows diff of external change, asks user to merge or overwrite

### Validation Pipeline

Every write follows three steps:

1. **Schema parse**: `safeParse()` against Zod schema. Reject 422 with structured errors.
2. **Semantic validation**: Domain-specific checks Zod can't express (DAG cycle detection, nonexistent agent references, disabled parser references).
3. **Atomic write**: Write to `.tmp` sibling, then `rename()` into place. Prevents partial writes.

## The Compilation Problem

### Constraints

- `bun run build:all` crashes Claude Code sessions (documented in MEMORY.md)
- `build-compile.ts` runs `generateAllOutputs()` which compiles every entity
- Pipeline: TypeScript source → in-memory entity → `compileAgent()` → markdown in `.claude/`

### Solution: Per-Entity Incremental Compilation via Sidecar

1. **Sidecar compiler process**: A long-running Bun process that imports compilation functions from `src/compilers/__helpers/compile.ts` and exposes them via local HTTP.

2. **Incremental compilation**: When UI saves an agent, API writes the TypeScript source, then calls sidecar to compile just that one entity. Sub-second.

3. **Compilation trigger strategy**:
   - Config.json edits: no compilation needed, immediate effect
   - Individual entity edits: sidecar compiles single entity on save
   - Never invoke `bun run build:all` from Studio

4. **Why this avoids the crash**: Sidecar compiles one entity in isolation, not the full pipeline. The crash is caused by full pipeline resource consumption + Claude Code process monitoring.

### Sidecar API

> **Updated after research (R2):** Use TCP localhost (port 3457), not Unix domain sockets. Node.js `fetch()` doesn't support the `unix` option, and the Next.js API routes run on Node.js. TCP localhost adds ~200us latency vs 50-500ms compile time — negligible. Sidecar managed by `bun run --watch` in dev for auto-restart on source changes.

```
POST http://localhost:3457/compile
Body: { domain: "agents" | "skills" | "rules", name: "lu-executor" }
Response: { status: "compiled", output_path: ".claude/agents/lu-executor.md", duration_ms: 47 }
```

The Next.js API route calls the sidecar over TCP localhost. The sidecar is the only process that imports from `src/` (maintains the Next.js build boundary). It naturally shares `node_modules/` and tsconfig aliases with the monorepo.

## State Management (Jotai)

### Three-Layer Atom Model

```
Layer 1: Server State (read-only mirror)
  configAtom          — mirrors config.json
  agentRegistryAtom   — mirrors agent list + frontmatter
  routingTableAtom    — mirrors MODEL_ROUTING_TABLE
  stateAtom           — mirrors state.json

Layer 2: Draft State (user edits)
  configDraftAtom     — derives from configAtom, tracks mutations
  agentDraftAtom(name)— per-agent draft state
  routingDraftAtom    — routing table edits

Layer 3: Dirty Tracking
  dirtySetAtom        — Set<string> of entity keys with unsaved changes
  canSaveAtom         — derived: dirtySetAtom.size > 0 && no validation errors
  validationErrorsAtom— Map<string, ZodError[]> per field
```

### Draft/Live Flow

1. Server state atom populated from GET endpoint
2. Draft atom derived as writeable copy when editor opens
3. Edits modify draft only
4. `dirtySetAtom` tracks divergence
5. Save writes draft to API → disk
6. SSE notifies of file change → server state atom updates → dirty tracking collapses

### Undo/Redo

> **Updated after research (R12):** The `jotai-history` package (official `jotaijs` org, 0.x) provides `withHistory(targetAtom, limit)` that wraps any atom with undo/redo capability. Exports UNDO, REDO, RESET action constants and `canUndo`/`canRedo` derived atoms. Only new dependency needed.

```typescript
import { withHistory, UNDO, REDO } from "jotai-history";

const agentDraftAtom = atomFamily((name: string) =>
  atom<AgentConfig>(initialConfig),
);
const agentHistoryAtom = atomFamily((name: string) =>
  withHistory(agentDraftAtom(name), 50),
);
```

Per-entity, max 50 entries, scoped — not global. Concurrent multi-entity editing works naturally via `atomFamily` (each entity gets independent atom tree).

## SSE Architecture

### Single Multiplexed Connection

One `EventSource` to `GET /api/events`. Server multiplexes via SSE `event:` field:

| Event Type         | Payload                              | Trigger                  |
| ------------------ | ------------------------------------ | ------------------------ |
| `file:changed`     | `{ path, hash, domain }`             | fs.watch on source dirs  |
| `state:transition` | `{ previous, current, event_type }`  | state.json change        |
| `compile:start`    | `{ domain, name }`                   | Compilation triggered    |
| `compile:complete` | `{ domain, name, success, errors? }` | Compilation finished     |
| `compile:error`    | `{ domain, name, error }`            | Compilation failed       |
| `ledger:entry`     | `{ ...ledger_entry }`                | New ledger line appended |
| `heartbeat`        | `{ ts }`                             | Every 30s                |

### Server Implementation

> **Updated after research (R1, R4):** SSE confirmed viable in Next.js App Router. Critical: set `Content-Encoding: none` to prevent compression buffering in `next start`. Use chokidar v5 (ESM-only, FSEvents backend on macOS) instead of raw `fs.watch` for reliable file watching with built-in `awaitWriteFinish` debounce at 150ms.

```typescript
// /api/events/route.ts
import chokidar from "chokidar";

export async function GET() {
  const encoder = new TextEncoder();
  const stream = new ReadableStream({
    start(controller) {
      const watcher = chokidar.watch(
        [".planning/", "src/agents/", "src/skills/", "src/rules/"],
        { awaitWriteFinish: { stabilityThreshold: 150 } },
      );
      watcher.on("change", (path) => {
        const domain = detectDomain(path);
        const json = JSON.stringify({ path, domain, hash: computeHash(path) });
        controller.enqueue(
          encoder.encode(`event: file:changed\ndata: ${json}\n\n`),
        );
      });
      // Heartbeat every 30s
    },
    cancel() {
      // Clean up watcher
    },
  });
  return new Response(stream, {
    headers: {
      "Content-Type": "text/event-stream",
      "Content-Encoding": "none", // Critical: prevents compression buffering
      "Cache-Control": "no-cache",
      Connection: "keep-alive",
    },
  });
}
```

### Client Integration with Jotai

`useSSE()` hook opens EventSource and dispatches to atoms:

```typescript
function useSSE() {
  useEffect(() => {
    const es = new EventSource("/api/events");
    es.addEventListener("file:changed", (e) => {
      const data = JSON.parse(e.data);
      if (data.domain === "config") invalidateConfig();
      if (data.domain === "agents") invalidateAgent(data.name);
    });
    es.addEventListener("compile:complete", (e) => {
      setCompileStatus(JSON.parse(e.data));
    });
    return () => es.close();
  }, []);
}
```

CSP note: Current `connect-src 'self'` already permits SSE to same origin.

## Security and Safety

### Validation Layers

1. **Schema validation** (Zod): Structural correctness — invalid types, missing fields, out-of-range values
2. **Semantic validation**: Domain rules beyond Zod:
   - Workflow steps cannot be deleted if others depend on them
   - At least one harness check must remain enabled
   - Required gates cannot be removed
   - Model routing must cover all 5 complexity levels
3. **Safe mode** (`safety.restrictive_editing` in config.json):
   - Core Luca agents (`src/agents/luca/`) read-only
   - Workflow step deletion blocked
   - Destructive gate toggles blocked
   - Model routing cannot set all levels to `fast` for deep-analysis agents

### Rollback via Git

> **Updated after research (R13):** Batch-commit-on-publish (not per-edit) avoids polluting git history. Use `Bun.$` shell commands for git operations — no new dependencies.

- Batch commit on **publish** (not every save) — tagged with `[studio-edit]` prefix
- "Config History" view: `git log --grep="[studio-edit]"` for listing
- "Revert to version": `git checkout <sha> -- <file>` for per-file rollback
- Uses existing git repo as versioning backend — no separate branch or shadow directory
- Rejected alternatives: per-edit commits (too noisy), shadow branch (complex merge), stash (LIFO/unnamed), reflog (ephemeral)

### Pre-Write Type Check

- After writing TypeScript entity file, sidecar runs `bunx --bun tsc --noEmit <filepath>`
- If fails, API returns TypeScript errors in response body
- File still written (user can iterate), but compilation blocked until errors resolved

## The TypeScript Round-Trip Problem

### The Challenge

Agent files are TypeScript with imports, typed config objects, `createAgent()` calls, and export statements. The UI must read structured data and write back valid TypeScript.

> **Research confirmed (R3):** All 129 entity files (47 agents, 58 skills, 24 rules) follow a 100% regular canonical template with zero structural deviations. Every entity already exposes a `.config` getter with the validated config as a plain object — the read path is nearly free. Edge case: 8 agents use `${CONSTANT}` interpolation for shared prompt blocks (COLD*ISOLATION_BLOCK, RESEARCH_REVIEWER*\*) which must be preserved during round-trip.

### Solution: Template-Based Code Generation

All agent files conform to a canonical template (confirmed across 129 files):

```typescript
import { createAgent } from "~/agents/__helpers/create-agent";
import type { AgentConfig } from "~/agents/__schemas/agent.schemas";

const {{varName}}Config: AgentConfig = {{configJson}};

export const {{varName}} = createAgent({{varName}}Config);
```

**Read path:**

1. Read TypeScript file
2. Extract `AgentConfig` object literal via targeted regex (find between `AgentConfig = ` and closing `};`)
3. Evaluate extracted literal in sandboxed context (or lightweight JSON5 parser)
4. Parse with `AgentConfigSchema.safeParse()`

**Write path:**

1. Receive edited `AgentConfig` from UI
2. Validate with `AgentConfigSchema.safeParse()`
3. Serialize to TypeScript object literal (backtick template literals for section content, standard JSON for other values)
4. Inject into template
5. Write file
6. Run `tsc --noEmit` via sidecar
7. If passes, trigger compilation

### Why Not AST (e.g., ts-morph)?

- 6MB dependency pulling full TypeScript compiler API
- Agent files all follow identical template — no arbitrary TS to handle
- Template approach is deterministic (same input → same output)
- Faster (no AST parsing needed)

### Section Content Serialization

Section content contains multi-line markdown with code blocks and escaped backticks. The serializer must:

- Use backtick template literals
- Escape `${` sequences (replace with `\${`)
- Escape backticks (replace `` ` `` with `` \` ``)
- Preserve existing escapes

A dedicated `serializeSectionContent()` function handles this. Must be tested against all existing agent files for round-trip fidelity.

## Key Technical Risks (Updated After Research)

> Research resolved several risks. Remaining risks re-ordered by residual difficulty.

1. **`${CONSTANT}` interpolation in 8 agent prompts (R3)**: These agents use shared prompt blocks via template literal interpolation. The round-trip serializer must detect and preserve these expressions (not escape them as `\${}`). Requires pattern matching to distinguish `${SHARED_BLOCK}` from literal `${user_text}`.

2. **Compilation sidecar reliability (R2)**: TCP localhost is the right IPC choice. Remaining risk: sidecar crash recovery, port conflicts, and cold-start latency when importing large `src/` trees. Mitigated by `bun run --watch` for auto-restart.

3. **ETag conflict resolution UX**: On 409, must show diff of external changes. Straightforward for JSON config, harder for TypeScript entities.

4. ~~**TypeScript round-trip**~~: **RESOLVED (R3)** — 129/129 files conform to canonical template. `.config` getter provides read path. Template-based write path confirmed feasible.

5. ~~**fs.watch reliability**~~: **RESOLVED (R4)** — chokidar v5 with FSEvents backend on macOS + `awaitWriteFinish` debounce. SSE events treated as invalidation hints, not authoritative state.

6. ~~**SSE viability**~~: **RESOLVED (R1)** — Confirmed viable in Next.js App Router with `Content-Encoding: none` header.
