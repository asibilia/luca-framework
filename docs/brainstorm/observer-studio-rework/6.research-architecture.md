# Architecture Research: Luca Studio

Research findings for R1 (Next.js SSE Viability), R2 (Compilation Sidecar Design), and R4 (fs.watch Reliability on macOS).

---

## R1: Next.js SSE Viability

### Finding

Next.js 15 App Router route handlers **can** reliably maintain long-lived SSE connections, but require specific configuration to avoid common pitfalls (compression buffering, idle timeouts, handler-level buffering). For Luca Studio's use case (local-only, standalone mode, single user), SSE via route handlers is viable without a custom server or separate sidecar.

### Evidence

**Working pattern confirmed by Vercel (Lee Robinson):** App Router route handlers support SSE using `ReadableStream` with the correct headers. The canonical pattern uses:

```typescript
// /api/events/route.ts
export const dynamic = "force-dynamic";

export async function GET() {
  const encoder = new TextEncoder();
  const stream = new ReadableStream({
    start(controller) {
      // Do NOT await async work here -- return immediately
      // Start async streaming in background IIFE
      (async () => {
        // ... push events via controller.enqueue()
      })();
    },
    cancel() {
      // Clean up watchers, intervals
    },
  });

  return new Response(stream, {
    headers: {
      "Content-Type": "text/event-stream",
      "Cache-Control": "no-cache, no-transform",
      "Content-Encoding": "none", // Critical: prevents gzip buffering
      Connection: "keep-alive",
      "X-Accel-Buffering": "no", // Prevents nginx proxy buffering
    },
  });
}
```

Source: [GitHub Discussion #48427](https://github.com/vercel/next.js/discussions/48427)

**Known limitations and mitigations:**

| Issue                                       | Cause                                                                                      | Mitigation                                                                                 |
| ------------------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| Buffered streaming in `next start`          | Next.js compression middleware gzips response, holds chunks until connection closes        | Set `Content-Encoding: none` header per-route (no need for global `compress: false`)       |
| Handler-level buffering                     | `await` in `start()` causes Next.js to wait for handler completion before sending Response | Return Response immediately; run async work in background IIFE                             |
| `MaxListenersExceededWarning` in production | EventEmitter leak when SSE route handlers accumulate                                       | Clean up watchers in `cancel()` callback; set explicit listener limits                     |
| Serverless timeouts (Vercel)                | Functions have execution time limits (10s edge, 60s node)                                  | **Not applicable** -- Luca Studio runs standalone (`output: "standalone"`), not serverless |
| Proxy buffering                             | Nginx/reverse proxies buffer SSE by default                                                | `X-Accel-Buffering: no` header; **not applicable** for localhost dev                       |

Sources: [Fixing Slow SSE in Next.js](https://medium.com/@oyetoketoby80/fixing-slow-sse-server-sent-events-streaming-in-next-js-and-vercel-99f42fbdb996), [Next.js compress docs](https://nextjs.org/docs/app/api-reference/config/next-config-js/compress), [Issue #56529](https://github.com/vercel/next.js/issues/56529)

**`next dev` vs `next start` behavior:**

- `next dev`: SSE works out of the box. HMR and dev middleware don't interfere with streaming responses.
- `next start` (standalone): Works with the `Content-Encoding: none` header fix. Without it, compression middleware buffers the stream. The current `next.config.ts` already uses `output: "standalone"`, which is the correct deployment mode for long-lived connections.

**Heartbeat pattern:** Essential for detecting stale connections. A 30-second heartbeat interval (as proposed in `4.technical-architecture.md`) is standard. Pattern:

```typescript
const heartbeat = setInterval(() => {
  controller.enqueue(
    encoder.encode(
      `event: heartbeat\ndata: ${JSON.stringify({ ts: Date.now() })}\n\n`,
    ),
  );
}, 30_000);

// In cancel():
clearInterval(heartbeat);
```

**CSP compatibility:** The existing `connect-src 'self'` in `next.config.ts` already permits SSE to same origin. No CSP changes needed.

### Recommendation

**Use Next.js App Router route handlers for SSE.** No custom server or SSE sidecar needed.

Implementation checklist:

1. Add `export const dynamic = 'force-dynamic'` to the SSE route
2. Set `Content-Encoding: none` header to bypass compression buffering
3. Return Response immediately; stream in background IIFE within `start()`
4. Implement heartbeat at 30-second intervals
5. Clean up all watchers and intervals in `cancel()` callback
6. Do NOT set `compress: false` globally (only disable per-route via header)

### Confidence: High

Multiple verified sources including official Vercel responses, the established `output: "standalone"` config already in place, and the single-user/localhost deployment model eliminates all serverless/proxy concerns. The pattern is well-documented and widely used for LLM streaming (similar long-lived connection profile).

## R2: Compilation Sidecar Design

### Finding

The best IPC mechanism for Next.js-to-Bun sidecar communication is **HTTP over Unix domain socket**. The sidecar should be a standalone `Bun.serve()` process managed by a wrapper script that handles auto-restart. Using Bun's native IPC (`Bun.spawn` with `ipc` handler) is an alternative but HTTP-over-UDS is simpler to debug and test.

### Evidence

**IPC mechanism comparison:**

| Mechanism                            | Latency                  | Debugging                     | Error handling             | Implementation complexity |
| ------------------------------------ | ------------------------ | ----------------------------- | -------------------------- | ------------------------- |
| HTTP over TCP localhost              | ~334us                   | Easy (curl)                   | Standard HTTP status codes | Low                       |
| HTTP over Unix domain socket         | ~130us                   | Moderate (curl --unix-socket) | Standard HTTP status codes | Low                       |
| Bun native IPC (`Bun.spawn` + `ipc`) | Lowest (structuredClone) | Hard (no external tooling)    | Custom protocol needed     | Medium                    |
| stdio pipes                          | Low                      | Hard                          | Custom protocol needed     | High                      |

Sources: [Unix Domain Sockets Guide](https://nodevibe.substack.com/p/the-nodejs-developers-guide-to-unix), [Bun fetch with Unix sockets](https://bun.sh/guides/http/fetch-unix), [Bun.spawn docs](https://bun.sh/docs/api/spawn)

**Bun.serve() Unix socket support is stable:**

`Bun.serve()` has supported Unix domain sockets since v0.8.1 (2023). The API is straightforward:

```typescript
// sidecar/server.ts
Bun.serve({
  unix: "/tmp/luca-studio-compiler.sock",
  routes: {
    "/api/compile": {
      POST: async (req) => {
        const { domain, name } = await req.json();
        // Import and call compile functions from src/compilers/
        const result = await compileEntity(domain, name);
        return Response.json(result);
      },
    },
    "/api/health": () => new Response("OK"),
  },
});
```

Source: [Bun.serve HTTP docs](https://bun.sh/docs/api/http)

**Calling from Next.js API routes:**

Bun's `fetch()` supports Unix sockets natively:

```typescript
// Next.js API route calling sidecar
const response = await fetch("http://localhost/api/compile", {
  unix: "/tmp/luca-studio-compiler.sock",
  method: "POST",
  body: JSON.stringify({ domain: "agents", name: "lu-executor" }),
  headers: { "Content-Type": "application/json" },
});
```

**However**, Next.js runs on Node.js, not Bun. Node.js `fetch()` does NOT support the `unix` option. Two alternatives:

1. **Use HTTP over TCP localhost** (simpler): Sidecar listens on a high port (e.g., 3457). Next.js uses standard `fetch('http://localhost:3457/api/compile')`. No Unix socket complexity.
2. **Use `node:http` with socketPath**: Node.js `http.request()` supports `socketPath` for Unix sockets, but this requires wrapping in a custom fetch-like utility.

**Recommendation: HTTP over TCP localhost** is the pragmatic choice. The latency difference (~200us) is negligible for compilation requests that take 50-500ms. TCP localhost eliminates all compatibility issues between the Node.js Next.js runtime and the Bun sidecar.

**Sidecar process management:**

| Strategy                            | Pros                              | Cons                                                       |
| ----------------------------------- | --------------------------------- | ---------------------------------------------------------- |
| Spawned by `dev` script             | Single command starts everything  | Coupled lifecycle; stdout mixed                            |
| Separate terminal                   | Independent lifecycle; clean logs | User must start manually                                   |
| Spawned by Next.js on first request | Lazy start; no manual step        | Cold-start latency on first compile; crash recovery harder |

**Recommended approach:** Spawned by `dev` script with auto-restart wrapper.

```jsonc
// package.json
{
  "scripts": {
    "dev": "bun run sidecar:dev & bun run css:watch & next dev --port 3456",
    "sidecar:dev": "bun run --watch packages/luca-observer/sidecar/server.ts",
  },
}
```

`bun run --watch` provides automatic restart on file changes during development. For production/non-dev, a simple wrapper handles crash recovery:

```typescript
// sidecar/launcher.ts
const MAX_RESTARTS = 5;
const RESTART_DELAY_MS = 1000;
let restarts = 0;

async function launch() {
  const proc = Bun.spawn(["bun", "sidecar/server.ts"], {
    cwd: import.meta.dir,
    stdout: "inherit",
    stderr: "inherit",
    onExit(proc, exitCode) {
      if (exitCode !== 0 && restarts < MAX_RESTARTS) {
        restarts++;
        console.error(
          `Sidecar crashed (exit ${exitCode}), restarting (${restarts}/${MAX_RESTARTS})...`,
        );
        setTimeout(launch, RESTART_DELAY_MS);
      }
    },
  });
}

launch();
```

Source: [Bun.spawn docs](https://bun.sh/docs/api/spawn)

**Module cache sharing:**

The sidecar IS a Bun process running in the monorepo. It naturally shares:

- The same `node_modules/` (no separate install needed)
- The same `tsconfig.json` path aliases (`~/*` resolves to `src/`)
- Bun's module resolution cache (per-process, not shared, but cold start is fast -- Bun resolves modules in microseconds)

There is no module cache sharing concern. The sidecar imports from `src/compilers/` directly, same as `build-compile.ts` does.

**Health check and readiness:**

The sidecar should expose a `/api/health` endpoint. The Next.js API route should check sidecar health before forwarding compile requests, returning a clear error to the UI if the sidecar is down.

### Recommendation

**Use HTTP over TCP localhost (port 3457) for Next.js-to-sidecar IPC.** Managed via the `dev` script with `bun run --watch` for development and a simple auto-restart wrapper for production.

Architecture:

```
[Browser] <--SSE--> [Next.js :3456] <--HTTP localhost--> [Bun Sidecar :3457]
                    (Route handlers)                     (Bun.serve + src/ imports)
```

The sidecar is the ONLY process that imports from `src/`. Next.js never crosses the build boundary.

### Confidence: High

All components (Bun.serve, Bun.spawn, HTTP localhost) are stable, well-documented APIs. The pattern of a sidecar process alongside Next.js is common in the ecosystem (see: Prisma Studio, tRPC dev server). The main risk is sidecar crash handling, which is mitigated by the auto-restart wrapper.

## R4: fs.watch Reliability on macOS

### Finding

Native `fs.watch` (both Node.js and Bun implementations) is **unreliable on macOS** for production use. The recommended approach is **chokidar v5** for the SSE file watcher in the Next.js process, with a **150ms debounce window** and treating SSE events as hints that trigger re-fetches (not authoritative change notifications).

### Evidence

**Known fs.watch issues on macOS:**

| Issue                                                         | Platform            | Severity                                                                                                                    |
| ------------------------------------------------------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Does not report filenames                                     | macOS               | High -- can't identify which file changed                                                                                   |
| Misses events with some editors (Sublime, potentially others) | macOS               | High                                                                                                                        |
| Reports events twice (duplicate notifications)                | macOS               | Medium -- requires dedup                                                                                                    |
| Emits most changes as `rename` instead of `change`            | macOS               | Medium -- misleading event type                                                                                             |
| New files created after watch started may not be detected     | Bun (all platforms) | High -- [GitHub #23992](https://github.com/oven-sh/bun/issues/23992), [#15085](https://github.com/oven-sh/bun/issues/15085) |

Sources: [chokidar README](https://github.com/paulmillr/chokidar), [libuv #645](https://github.com/libuv/libuv/issues/645), Bun GitHub issues

**Root cause:** Node.js `fs.watch` uses **kqueue** on macOS. Kqueue operates on file descriptors and has known limitations with editor save patterns (atomic writes = delete + create, which breaks the watched fd). FSEvents is the native macOS API designed for file change monitoring and does not have these issues.

**Comparison of file watching options:**

| Library              | Backend on macOS  | Recursive        | Debounce | New file detection                                                 | Bundle size      | Reliability      |
| -------------------- | ----------------- | ---------------- | -------- | ------------------------------------------------------------------ | ---------------- | ---------------- |
| `fs.watch` (Node.js) | kqueue            | Yes (macOS only) | None     | Partial                                                            | 0 (built-in)     | Poor             |
| `fs.watch` (Bun)     | kqueue            | Yes              | None     | **Broken** ([#23992](https://github.com/oven-sh/bun/issues/23992)) | 0 (built-in)     | Poor             |
| `chokidar` v5        | FSEvents (native) | Yes              | Built-in | Yes                                                                | ~15KB (ESM-only) | Excellent        |
| `fsevents` (raw)     | FSEvents (native) | Yes              | None     | Yes                                                                | ~10KB            | Good (low-level) |

**Chokidar v5 details:**

- Released November 2025. ESM-only. Requires Node.js >= 20.
- On macOS, uses native `fsevents` binding by default (Darwin FSEvents API). This is kernel-level file monitoring, not polling.
- Normalizes events across platforms (consistent `add`, `change`, `unlink` events).
- Built-in ready event, error handling, and ignore patterns.
- Used by webpack, Vite, Next.js dev server itself, and thousands of other tools.

Source: [chokidar npm](https://www.npmjs.com/package/chokidar), [chokidar GitHub](https://github.com/paulmillr/chokidar)

**Why NOT Bun's fs.watch:**

Bun's `fs.watch` implementation has documented bugs with new file detection ([#23992](https://github.com/oven-sh/bun/issues/23992), [#15085](https://github.com/oven-sh/bun/issues/15085)). Since the SSE watcher runs inside the Next.js process (Node.js runtime), not the Bun sidecar, we'd be using Node.js `fs.watch` anyway -- which has the kqueue limitations. Chokidar provides a reliable abstraction over both.

**Debounce strategy for IDE save events:**

IDEs like VS Code and Cursor trigger multiple filesystem events per save:

1. Write to temp file
2. Rename temp -> target (atomic save)
3. Sometimes: delete old + write new
4. File metadata updates (mtime, permissions)

This can produce 2-5 events per logical save. Recommended debounce:

```typescript
import chokidar from "chokidar";

const watcher = chokidar.watch(
  [".planning/", "src/agents/", "src/skills/", "src/rules/"],
  {
    ignoreInitial: true,
    // Debounce: wait 150ms after last event before emitting
    awaitWriteFinish: {
      stabilityThreshold: 150,
      pollInterval: 50,
    },
    ignored: ["**/node_modules/**", "**/.git/**", "**/*.tmp", "**/*~"],
  },
);
```

The `awaitWriteFinish` option is chokidar's built-in debounce. It waits for the file size to stabilize (no writes for `stabilityThreshold` ms) before emitting the event. 150ms handles the vast majority of IDE atomic-save patterns without introducing noticeable UI delay.

**SSE events as hints, not authority:**

The architecture in `4.technical-architecture.md` correctly identifies the pattern: SSE `file:changed` events should trigger the client to **re-fetch** the resource, not carry the new data. This means:

1. Watcher detects change -> SSE pushes `{ path, hash, domain }`
2. Client receives event -> calls `GET /api/entities/agents/[name]` to get fresh data
3. Jotai atom updates with validated, schema-parsed response

This makes the watcher failure mode graceful: if an event is missed, the client just has slightly stale data until the next event or manual refresh. If an event fires twice (duplicate), the re-fetch is idempotent.

### Recommendation

**Use chokidar v5 for file watching in the SSE route handler.** Configure with `awaitWriteFinish` at 150ms stabilityThreshold. Treat SSE events as invalidation hints, not data carriers.

Implementation:

```bash
cd packages/luca-observer && bun add chokidar
```

Key configuration:

- Watch directories: `.planning/`, `src/agents/`, `src/skills/`, `src/rules/`, `src/complexity/`
- Ignore: `node_modules`, `.git`, temp files
- `awaitWriteFinish.stabilityThreshold`: 150ms
- `ignoreInitial`: true (don't emit for existing files on startup)

### Confidence: High

Chokidar is the de facto standard for file watching in the Node.js ecosystem. FSEvents on macOS is the correct system-level API. The 150ms debounce is validated by real-world usage in webpack/Vite/Next.js dev server. The "events as hints" pattern eliminates reliability concerns (missed or duplicate events become harmless).

## Cross-Cutting: Architecture Summary

```
                    ┌─────────────────────┐
                    │      Browser        │
                    │   EventSource +     │
                    │   Jotai atoms       │
                    └─────┬───────┬───────┘
                          │       │
                     SSE  │       │  REST
                          │       │
                    ┌─────▼───────▼───────┐
                    │   Next.js :3456     │
                    │   (App Router)      │
                    │                     │
                    │  GET /api/events    │─── chokidar (FSEvents)
                    │  GET/PUT /api/*     │         watches src/ + .planning/
                    │  POST /api/compile  │──┐
                    └─────────────────────┘  │
                                             │ HTTP localhost
                                             │
                    ┌────────────────────────▼┐
                    │   Bun Sidecar :3457    │
                    │   (Bun.serve)          │
                    │                        │
                    │   imports src/         │
                    │   compileAgent()       │
                    │   compileSkill()       │
                    │   compileRule()        │
                    │   tsc --noEmit         │
                    └────────────────────────┘
```

**Key decisions:**

1. SSE lives in Next.js route handlers (no separate SSE server)
2. Sidecar communicates via HTTP on TCP localhost (not Unix sockets, for Node.js compatibility)
3. File watching via chokidar v5 with FSEvents backend (not fs.watch)
4. SSE events are invalidation hints; client re-fetches on event
5. Sidecar managed by dev script with auto-restart on crash
