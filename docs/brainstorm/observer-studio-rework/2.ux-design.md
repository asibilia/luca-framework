# UX Design: Luca Studio

## Core User Flows

### Flow 1: Consumer First Launch

The first launch must answer three questions within 30 seconds: "What is this?", "What's happening now?", and "What can I do?"

1. App opens to **Home** (not "Dashboard" — that implies monitoring, not onboarding)
2. **Status card** at top: "Luca is idle." or "Luca is running Phase 3: Execute on branch `feat/auth-flow`."
3. **Recent activity feed**: last 3-5 completed workflows with outcome badges (success/failure/partial)
4. **Quick actions row**: three cards — "Browse Agents", "View Workflow Pipeline", "Search Memory"
5. Sidebar collapsed to icons by default on first launch. Content area takes focus.
6. No modals, no tours, no tooltips on first launch. Layout teaches through hierarchy.

**Key decision**: Home is a status page with entry points, not a dashboard with charts.

### Flow 2: Consumer Customizing Their Workflow Pipeline

Highest-stakes editing flow. The pipeline is the core of Luca.

1. Navigate to **Pipeline** (under BUILD group)
2. Horizontal DAG visualization of pipeline stages (left-to-right). Each node shows step name, description, enabled/disabled dot
3. Clicking a node opens **detail panel on the right** (split view, not modal): step description, participating agents, model routing at current complexity, toggle switches for optional behaviors
4. Gate toggles show yellow warning inline about orchestrator resolution
5. Changes are NOT live. Panel footer: "1 unsaved change" with **Preview Impact** and **Save Draft** buttons
6. Preview Impact opens a diff view showing which config fields change
7. **Save** writes to config. A top-level **Publish** button (for entity changes) runs validation and shows confirmation with full diff

**Why draft/save**: Consumers don't understand blast radius. The preview builds trust.

### Flow 3: Consumer Creating a Custom Agent

Most complex consumer flow. Agent files are TypeScript — the challenge is making this editable without requiring TypeScript knowledge.

1. Navigate to **Agents** → card grid grouped by category
2. Click **"+ New Agent"** → opens full-page editor (not modal — needs screen space)
3. **Left column**: Structured fields (name with kebab-case enforcement, description, category, model routing grid, tool strategy, tool selector)
4. **Right column**: Prompt editor — monospace textarea with markdown highlighting, 60% of horizontal space
5. Below prompt: collapsible **"Source Preview"** showing generated TypeScript (read-only, updates live)
6. Continuous **validation bar**: name uniqueness, prompt non-empty, model routing complete
7. **Save** writes `.agent.ts` to `src/agents/custom/`. Shows notice: "Agent saved. Run `bun run build:all` to compile."
8. Returns to Agents list with "Custom" badge and "Uncompiled" indicator

**Key decision**: Hybrid form + prompt editor. Structure where it helps (model routing), freeform where creativity matters (the prompt).

### Flow 4: Editor Inspecting Live State

1. Navigate to **State** (under OBSERVE group)
2. **Top section**: JSON tree viewer of state machine context. Recently changed fields highlighted green. Key fields (phase, complexity, oversight) pinned to top.
3. **Bottom section**: Reverse-chronological event log table. Columns: timestamp, event type, summary.
4. **Auto-refresh** on by default (polling every 2s, pulsing green dot). Toggle to manual.
5. Clicking an event highlights the state fields it changed (bidirectional linking)
6. **Freeze button** stops auto-refresh, takes snapshot. Blue banner: "State frozen at [timestamp]."
7. **Send Event** via Cmd+K command palette (hidden from consumers, known to editors)

### Flow 5: Editor Debugging Failed Verification

1. Failed verification surfaces on Home status card and red badge on **Eval** nav item
2. Click → **Eval page**: summary bar with pass/fail per check type (colored horizontal segments)
3. Click failed segment → parsed error list: file path, line number, message, severity
4. File path click → read-only source viewer with error line highlighted + 10 lines context
5. **"Re-run Harness"** button at top with spinner and streaming terminal panel
6. **History sidebar** (collapsible) with last 10 harness runs for comparison

## Navigation Architecture

### Structure

> **Updated after research (R8):** Merged Complexity + Gates into Config. Added Memory. 9 items total.

```
HOME (landing page, no sub-items)

OBSERVE
  Sessions          — Workflow run history
  Memory            — Consolidated MuninnDB (browse | graph | search | health)

BUILD  (prioritized for v1)
  Pipeline          — Workflow editor (interactive DAG)
  Agents            — Agent browser + config editor (read-only prompts in v1)
  Skills            — Skill browser + config editor
  Rules             — Rule browser + config editor

CONFIGURE
  Config            — Complexity routing + gates + harness (tabs)
  Settings          — Raw config, project identity, vault
```

### Navigation Behavior

- Sidebar is fixed-position, 240px wide, collapsible to 56px (icon-only)
- Group headers are non-clickable labels in uppercase small text
- Active page: left border accent + background highlight
- Badges: red dot on Eval when last run failed, count badge on Sessions when workflow is active
- Settings group visually separated at bottom with divider line

### Current Page Consolidation

| Current         | Fate                  | Justification                                         |
| --------------- | --------------------- | ----------------------------------------------------- |
| Dashboard       | → Home                | Status + entry points, not metrics                    |
| Sessions        | Kept                  | Core workflow concern                                 |
| Memory          | Absorbs 5 pages       | MuninnDB is one system; one page with tabs            |
| Learning        | Tab within Memory     | Just memories with `pattern:*` / `pitfall:*` prefixes |
| Vault           | Tab within Memory     | Filtered MuninnDB view                                |
| Knowledge Graph | Tab within Memory     | Graph visualization sub-view                          |
| Workflow Editor | → Pipeline            | Read-only evolves to interactive                      |
| Semantic Search | Feature within Memory | Search bar, not a page                                |
| Decisions       | Tab within Sessions   | Workflow-scoped decision log                          |
| Contradictions  | Removed               | Never populated with real data                        |
| Entities        | Removed               | Replaced by Agents/Skills/Rules pages                 |

## Editing Patterns

### Draft → Save → Compile Model

All editing follows three distinct steps:

1. **Draft**: Edits live in browser state (Jotai atoms). Visual indicators show dirty fields (left-border accent, like git diff gutter). Field-level revert available.
2. **Save**: Writes to source files on disk. Config changes take effect immediately. Entity changes need compilation.
3. **Compile**: Sidecar process compiles individual entities incrementally. Never runs `build:all`.

### Validation Before Save

- **Schema validation**: Zod schemas validate all structured fields. Errors inline next to the field.
- **Name collision detection**: New entities checked against registry in real-time.
- **Dependency checking**: Removing a pipeline step checks if others reference it.
- **Save button disabled** when validation errors exist. Tooltip shows count and summary.

### Undo Strategy

> **Updated after research (R12):** The `jotai-history` package (official Jotai org) provides `withHistory(targetAtom, 50)` with UNDO/REDO constants and canUndo/canRedo flags — matching the original spec exactly.

- **Field-level**: Each field tracks original value. Small "revert" icon next to changed fields.
- **Page-level**: "Discard Changes" button in page header reverts all pending edits.
- **Multi-step undo** (Cmd+Z / Cmd+Shift+Z): Supported via `jotai-history` — per-entity history stack with max 50 entries. Only available in editors (prompt, config forms), not dashboard views.

### Impact Preview

For changes with downstream effects, the save confirmation includes an Impact section:

```
IMPACT PREVIEW
- Changing lu-executor model routing from "balanced" to "capable" at MODERATE
  complexity will affect all MODERATE-level task executions.
- Estimated token cost increase: ~2x for MODERATE tasks.
```

## Progressive Disclosure

### No Explicit Modes

Rather than "Consumer Mode" / "Editor Mode" toggles:

**What consumers see by default:**

- Home, Pipeline, Sessions, Agents, Memory — always visible
- Entity pages show form-based editing (structured fields + prompt editor)
- Pipeline shows DAG with toggle switches and dropdowns
- No raw JSON, no TypeScript source views, no state machine internals

**What reveals itself for editors:**

- **Internals** group (State, Eval) visible to everyone but labeled "(Advanced)"
- **"View Source"** collapsible section in entity editors, collapsed by default
- **Settings** nav group with raw JSON editor — consumers never go there
- **"Send Event"** command palette behind keyboard shortcut (Cmd+K), not a visible button

### Complexity Emergence Patterns

1. **Collapsed sections**: Source Preview, Event Log details, Impact Preview collapsed by default
2. **Contextual actions**: "Re-run Harness" only on Eval page, "Send Event" only on State page
3. **Tooltips for technical terms**: Hover "Model Routing: fast" → "The 'fast' tier uses lightweight models for quick, low-cost responses"
4. **No feature flags for UI complexity**: Every user sees the same app

## The Agent Editing Experience

### Three-Panel Layout

```
+------------------+----------------------------+------------------+
|   METADATA       |   PROMPT EDITOR            |   LIVE PREVIEW   |
|   (form fields)  |   (main editing surface)   |   (compiled out) |
|                  |                            |                  |
|   Name           |   # System Prompt          |   Generated .md  |
|   Description    |                            |   as it would    |
|   Category       |   You are {{ name }},      |   appear in      |
|   Model Routing  |   a specialized agent...   |   .claude/agents/|
|   Tool Strategy  |                            |                  |
|   Tool Selection |                            |                  |
|                  |                            |                  |
+------------------+----------------------------+------------------+
|                  VALIDATION BAR                                  |
+-----------------------------------------------------------------+
```

**Left panel (25%)**: Structured form — name (kebab-case enforced), description, category dropdown, model routing grid (5 rows x 3 tier options), tool strategy radio, tool multi-select.

**Center panel (50%)**: Prompt editor — monospace, markdown highlighting, no AI autocomplete (writing instructions for AI while AI suggests those instructions is confusing). Line numbers, word/character count.

**Right panel (25%)**: Live compiled preview — read-only markdown preview that updates as user edits. Toggle between "Compiled Markdown" and "TypeScript Source" views.

**Bottom bar**: Continuous validation — name uniqueness, prompt non-empty, model routing complete. Warnings non-blocking, errors block save.

### Editing Existing Agents

- Three-panel editor loads with fields populated from parsed `.agent.ts`
- Source file path shown in header
- **Read-only lock** on core Luca agents with "Duplicate" button
- User-created agents (in `custom/`) fully editable
- Diff gutter shows changed lines in prompt editor

### Agent List View

- Group-based tree on left: General, Luca, Custom (expandable/collapsible)
- Card grid on right for selected group
- Each card: name, description (2 lines), model tier badge, tool count, compiled status
- Search bar filters across all groups
- "+ New Agent" button in top-right
