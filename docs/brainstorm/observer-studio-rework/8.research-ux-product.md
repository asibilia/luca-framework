### R5: Existing Observer Page Usage

**Finding**: All 11 current pages depend on MuninnDB for their primary data pipeline. Only 2 pages (Dashboard/Todos, Workflow Editor) have any data source that does not require MuninnDB. For a fresh Luca install with no workflow history and no MuninnDB configured, every page except Workflow Editor and the Todos portion of Dashboard will show empty states.

**Evidence**: Detailed hook-by-hook analysis of data dependencies:

| Page            | Hook                     | Data Source                                                                               | Requires MuninnDB      | Requires Active Session | Fresh Install Usefulness                                                        |
| --------------- | ------------------------ | ----------------------------------------------------------------------------------------- | ---------------------- | ----------------------- | ------------------------------------------------------------------------------- |
| Dashboard       | `use-dashboard`          | `/api/muninn/stats`, `/api/muninn/engrams`, `/api/muninn/graph-data`, `/api/todos`        | Yes (3 of 4 endpoints) | No, but needs history   | LOW -- Todos work, MuninnDB cards show zeros                                    |
| Sessions        | `use-session-explorer`   | `/api/muninn/engrams?type=session`                                                        | Yes                    | Needs past sessions     | NONE -- empty list without session engrams                                      |
| Memory          | `use-memory`             | `/api/muninn/activate`, `/api/muninn/engrams`, `/api/muninn/session`, `/api/muninn/stats` | Yes (all 4 endpoints)  | No, but needs history   | NONE -- empty state without engrams                                             |
| Learning        | `use-learning-evolution` | `/api/muninn/engrams` (limit=500)                                                         | Yes                    | No, but needs history   | NONE -- timeline and category charts empty                                      |
| Vault           | `use-vault-health`       | `/api/muninn/stats`, `/api/muninn/engrams` (limit=500)                                    | Yes                    | No                      | NONE -- overview zeros, no type breakdown                                       |
| Knowledge Graph | `use-knowledge-graph`    | `/api/muninn/graph-data`                                                                  | Yes                    | No, but needs entities  | NONE -- empty graph                                                             |
| Workflow Editor | `use-workflow-graph`     | `/api/workflow/topology`                                                                  | No (filesystem)        | No                      | HIGH -- reads compiled workflow from disk                                       |
| Semantic Search | `use-semantic-search`    | `/api/muninn/activate` (on-demand)                                                        | Yes                    | No                      | NONE -- no results without engrams                                              |
| Decisions       | `use-decision-trail`     | `/api/muninn/engrams?type=decision`                                                       | Yes                    | Needs past decisions    | NONE -- empty list                                                              |
| Contradictions  | `use-contradictions`     | `/api/muninn/contradictions`                                                              | Yes                    | Needs engram pairs      | NONE -- always empty (product vision confirms "never populated with real data") |
| Entities        | `use-entities`           | `/api/muninn/graph-data`                                                                  | Yes                    | Needs entities          | NONE -- empty list                                                              |

Additional hooks not directly mapped to pages but used for shared data:

- `use-checkpoint` / `use-context-metrics`: Reads from `/api/muninn/checkpoint`, `/api/muninn/zone-history`, `/api/context-metrics`. Context metrics reads from filesystem (`.planning/.context-metrics.json`), so it works without MuninnDB but requires an active Claude Code session.
- `use-observations`: Reads from `/api/muninn/observations` and `/api/muninn/metrics`. Requires MuninnDB.
- `use-todos`: Reads from `/api/todos` which scans `.planning/todos/` on the filesystem. Works without MuninnDB.
- `use-mobile`: Utility hook (media query), no data dependency.
- `use-entity-clusters` / `use-entity-deep-dive`: MuninnDB entity/cluster data.

**Active development vs post-hoc analysis:**

- **Active development**: Context Metrics (live context window tracking), Checkpoint (zone transitions), Workflow Editor (pipeline visualization), Dashboard/Todos (task tracking)
- **Post-hoc analysis**: Sessions, Memory, Learning, Vault, Knowledge Graph, Decisions, Entities, Semantic Search, Observations

The overwhelming majority of pages are post-hoc analysis views into MuninnDB. The active-development pages are limited to context monitoring and the workflow visualizer.

**Recommendation**: The fresh-install experience is currently empty for 9 of 11 pages. The Studio rework should prioritize BUILD pages (Pipeline, Agents, Skills, Rules) that read from the filesystem, giving immediate value without MuninnDB. OBSERVE pages should be treated as "grows with usage" with informative empty states that explain what data will appear after running workflows. Consider a "Getting Started" card on Home that detects whether MuninnDB is configured and guides the user through setup.

**Confidence**: High -- based on direct source code analysis of all 19 hook files.

### R6: Competitive Analysis

**Finding**: The five analyzed tools each use a distinct editing pattern. The most relevant models for Luca Studio are Stately's split canvas+panel and n8n's draft/publish workflow. All tools favor split-view or panel-based editing over modals.

**Evidence**:

#### Stately Studio (stately.ai) -- State Machine Visual Editor

- **Editing pattern**: Canvas + side panel. Two modes: Design mode (create machines with drag-and-drop) and Simulate mode (run the machine). States and transitions are placed on an infinite canvas, with property editing in a right-side panel.
- **Key UX decisions**: Bidirectional sync between visual editor and XState code. VS Code extension provides the same editor inline. AI-assisted generation from natural language descriptions.
- **Relevance to Luca**: Closest conceptual match -- Luca's Pipeline editor is essentially a state/workflow DAG editor. Stately proves that drag-and-drop canvas + side detail panel works for state machines. The bidirectional code sync pattern is exactly what Luca needs for agent editing (source TS <-> compiled markdown).

#### n8n (n8n.io) -- Workflow Automation

- **Editing pattern**: Canvas + modal/panel. Nodes are placed on a drag-and-drop canvas. Clicking a node opens a configuration panel (slides over the right side of the canvas). Data mapping uses drag-and-drop from previous nodes into fields.
- **Key UX decisions**: Autosave every 2 seconds. Explicit "Publish" step separate from save -- changes stay in draft until published. Version history with named versions and descriptions. Webhooks only activate after publish.
- **Relevance to Luca**: The n8n 2.0 draft/publish model is directly applicable to Luca's two-stage editing (save to disk vs compile). The autosave-to-draft pattern would work for config.json edits, while the explicit publish maps to `bun run build:all`.

#### Retool (retool.com) -- Internal Tool Builder

- **Editing pattern**: Full-page split view. Left panel shows component tree, center is the visual canvas, right panel is the Inspector (property configuration). Bulk editing supported via multi-select + shared Inspector.
- **Key UX decisions**: 100+ components with dozens of settings per component -- addressed through presets (preconfigured component variants). AI can generate entire UIs from schema descriptions. The Inspector panel can feel overwhelming but velocity is high once the mental model clicks.
- **Relevance to Luca**: The three-panel layout (tree | canvas | inspector) maps directly to the proposed agent editing experience (metadata | prompt editor | compiled preview). The preset concept could apply to agent templates (security auditor preset, code reviewer preset).

#### Vercel Dashboard -- Deployment Observability

- **Editing pattern**: List + drill-down. Project dashboard shows deployment list with status badges. Clicking a deployment shows build logs with streaming output. Function logs are separate. Observability is streaming/polling-based.
- **Key UX decisions**: Minimal configuration surface -- mostly read-only observability. Drains system for streaming data to external tools. Basic request stats on dashboard, detailed debugging requires log drill-down.
- **Relevance to Luca**: Vercel's approach to deployment status (list with badges, drill-down to logs) maps to the Sessions page design. The streaming log viewer with expandable sections is a good model for the Eval page's harness result display.

#### Linear (linear.app) -- Project Management

- **Editing pattern**: List + inline editing + command palette. Super predictable structure: sidebar (fixed) | list (middle) | detail (right). Keyboard-first navigation. Cmd+K command palette for everything. Minimal visual noise.
- **Key UX decisions**: Speed above all -- fast transitions, immediate state changes, no loading spinners for cached data. Familiar layout patterns (no novel UX). Bottom-up information hierarchy: list items are scannable, detail opens on click without page navigation.
- **Relevance to Luca**: Linear's navigation pattern (fixed sidebar with grouped sections, 3-column layout) is the exact model proposed for Luca Studio. Their keyboard-first approach and Cmd+K palette should inform the "Send Event" and quick-navigation features. Linear's ~8-10 top-level nav items across 3 groups validates the proposed 11-item structure.

**Summary of editing patterns:**

| Tool    | Pattern                   | Config Surface              | Draft Model             |
| ------- | ------------------------- | --------------------------- | ----------------------- |
| Stately | Canvas + side panel       | Medium (state properties)   | Save = live             |
| n8n     | Canvas + slide-over panel | High (node config)          | Draft -> Publish        |
| Retool  | Three-panel split         | Very high (100+ components) | Save = live (with undo) |
| Vercel  | List + drill-down         | Minimal (read-only)         | N/A (CI/CD)             |
| Linear  | List + inline + Cmd+K     | Low (issue fields)          | Save = live             |

**Recommendation**: Adopt n8n's draft/publish model for entity changes that require compilation. Use Stately's canvas+panel pattern for the Pipeline editor. Follow Linear's navigation principles (predictable, keyboard-first, grouped sidebar). Use Retool's three-panel layout for the agent editor.

**Confidence**: Medium -- based on web search results, official documentation, and blog posts. I did not have hands-on access to these tools, so some nuances may be missed. The n8n 2.0 draft/publish model is well-documented and HIGH confidence.

### R8: Navigation Validation

**Finding**: The proposed 3-group/11-item navigation is well-structured but could be tightened to 3-group/10-item by merging Complexity + Gates into a single "Config" page, since they share the same underlying concern (complexity-gated behavior configuration).

**Evidence**:

**Current proposal evaluation:**

```
OBSERVE (3 items + Home)
  Home              -- Status + quick actions
  Sessions          -- Session explorer
  State             -- Live state inspector
  Eval              -- Harness results

BUILD (4 items)
  Pipeline          -- Visual workflow editor
  Agents            -- Agent browser + editor
  Skills            -- Skill browser + editor
  Rules             -- Rule browser + editor

CONFIGURE (3 items)
  Complexity        -- Model routing matrix + loop budgets
  Gates             -- Gate toggle grid
  Settings          -- Raw config editor
```

**Analysis by question:**

1. **Is 3-group/11-item optimal?** Competitive analysis shows: Linear uses ~8-10 top-level items across 3-4 groups. n8n uses ~6-8 items across 2 groups. Stately uses ~4-5 items. Retool uses ~8-10 items. The proposed 11 items is on the high end but defensible because Luca has genuinely distinct concerns. The 3-group structure (Observe/Build/Configure) provides clear mental model separation.

2. **Should Memory be standalone or within Home?** The proposal already removed Memory as a standalone page and consolidated it into Sessions (for session memory) and a future Memory page under OBSERVE. The product vision document says to absorb 5 pages into a unified Memory page. Given that Memory is the richest data source in the app, it deserves its own nav item -- but the vision doc omits it from the proposed nav. This is a gap: Memory/Learning/Vault/Knowledge Graph/Semantic Search are consolidated but not visible in the nav. Recommendation: add a "Memory" item under OBSERVE that opens the consolidated tabbed view, making it Home | Sessions | State | Eval | Memory (5 OBSERVE items, 12 total). Alternatively, embed memory access within Home's quick actions.

3. **Is Decisions distinct enough from Sessions?** No. The UX design doc already proposes "Decisions" as a tab within Sessions, not a standalone page. This is correct -- decision engrams are workflow-scoped and contextually belong with session data. The current hook (`use-decision-trail`) fetches `decision:*` engrams, which are a subset of the same MuninnDB data that Sessions displays. Keep Decisions as a Sessions tab.

4. **Should Complexity and Gates merge into a unified Config page?** Yes, with reservations. Both pages configure complexity-gated behavior:
   - Complexity: model routing matrix (agents x complexity levels) + loop budgets
   - Gates: gate toggle grid (gates x complexity levels)

   Both are small configuration surfaces (a matrix/grid each). A single "Config" page with tabs (Routing | Gates | Advanced) would reduce nav count by 1 and group related concerns. However, if the Complexity page grows to include preset management and visual indicators, it may justify separation. Recommendation: start merged as "Config" with tabs, split later if needed.

5. **Competitive nav counts:**
   - Linear: ~8 top-level items (Inbox, My Issues, Views, Teams, Projects, Initiatives, Roadmaps, Settings)
   - n8n: ~6 items (Workflows, Credentials, Templates, Variables, Executions, Settings)
   - Stately: ~4 items (Machines, Projects, Teams, Settings)
   - Vercel: ~7 items (Overview, Deployments, Analytics, Speed Insights, Logs, Storage, Settings)

   Average: ~6-8 items. Luca's 11 is high. Merging Complexity+Gates reduces to 10. Adding Memory back adds to 11. Consider whether State (advanced, rarely used) should be folded into Settings or a debug section to reduce to 10.

**Recommendation**: Merge Complexity + Gates into "Config" (tabs: Routing | Gates). Consider adding "Memory" back under OBSERVE as a consolidated tabbed page. This yields 3 groups / 11 items:

- OBSERVE: Home, Sessions, Memory, State, Eval (5)
- BUILD: Pipeline, Agents, Skills, Rules (4)
- CONFIGURE: Config, Settings (2)

Or 10 items if Memory stays embedded in Home's quick actions.

**Confidence**: Medium -- navigation structure is subjective and depends on user testing. Competitive analysis provides directional guidance but Luca's domain is unique (agentic workflow framework), so direct comparisons have limits.

### R9: Monaco Editor Trade-offs

**Finding**: Monaco Editor is overkill for editing agent prompts. CodeMirror 6 provides the right balance of capability and bundle size. For read-only preview, Shiki is the lightest option. A plain textarea with Shiki highlighting overlay is a viable minimal approach for V1.

**Evidence**:

**Bundle size comparison:**

| Editor         | Min Gzipped Size                    | Full Feature Size                | Notes                                                               |
| -------------- | ----------------------------------- | -------------------------------- | ------------------------------------------------------------------- |
| Monaco Editor  | ~2+ MB gzipped                      | 5-10 MB uncompressed             | Sourcegraph measured 2.4 MB optimized bundle = 40% of their page JS |
| CodeMirror 6   | ~124 KB core gzipped                | ~300 KB with typical extensions  | Modular architecture, excellent tree-shaking                        |
| Shiki          | ~200 KB with a few languages/themes | ~695 KB web bundle, ~1.2 MB full | Read-only highlighting only, no editing                             |
| Plain textarea | 0 KB                                | 0 KB                             | No highlighting, but instant load                                   |

**Monaco: custom markdown + template variable highlighting.**
Monaco supports custom language definitions via Monarch (its declarative syntax highlighting engine). You can extend the built-in markdown language to add template variable highlighting (e.g., `{{ name }}` syntax). Monaco also integrates with Shiki for TextMate grammar support. However, this capability comes at the cost of 2+ MB of JavaScript that users must download.

**Is Monaco overkill for agent prompts?**
Agent prompts are essentially markdown documents with occasional template variables. The editing needs are:

- Markdown syntax highlighting
- Line numbers
- Word wrap
- Find/replace
- Possibly bracket matching for template variables

These are all features CodeMirror 6 handles well at 1/10th the bundle size. Monaco's IDE-level features (IntelliSense, multi-cursor refactoring, TypeScript language service, minimap) are unnecessary for prompt editing.

**For the TypeScript source preview (read-only):**
Shiki is the clear winner. It uses VS Code's TextMate grammars for accurate highlighting, weighs ~200 KB, and is read-only by design. The compiled markdown preview and TypeScript source view should use Shiki, not an editable code editor.

**Progressive approach:**

| Surface                                 | V1 (Ship Fast)                  | V2 (If Needed)                            |
| --------------------------------------- | ------------------------------- | ----------------------------------------- |
| Prompt editor (center panel)            | CodeMirror 6 with markdown mode | Add custom template variable highlighting |
| TypeScript source preview (right panel) | Shiki (read-only)               | Keep Shiki                                |
| Config JSON editor (Settings)           | CodeMirror 6 with JSON mode     | Keep CodeMirror                           |
| Raw state viewer                        | Shiki or `<pre>`                | Keep as-is                                |

**Recommendation**: Use CodeMirror 6 for all editable code surfaces. Use Shiki for all read-only code display. Do not use Monaco -- the 2+ MB bundle is unjustifiable for markdown editing. CodeMirror 6's markdown mode with a custom template variable extension provides the needed functionality at ~300 KB total.

**Confidence**: High -- bundle size data is well-documented across multiple sources including Sourcegraph's migration blog post. CodeMirror 6 and Shiki capabilities are verified through official documentation.

### R10: Draft/Publish vs Direct Save

**Finding**: A two-tier model is the right approach: config.json edits take effect immediately on save, while entity edits (agents, skills, rules) require an explicit compile step. This maps naturally to the technical reality of the system.

**Evidence**:

**How competitors handle this:**

| Tool    | Save Model                                    | Compile/Build Step                          | Visual Indicator                          |
| ------- | --------------------------------------------- | ------------------------------------------- | ----------------------------------------- |
| n8n 2.0 | Autosave every 2s to draft                    | Explicit "Publish" button with version name | Draft badge, "Unpublished changes" banner |
| Stately | Save = live (code export updates immediately) | Export to code is instant                   | No compile step                           |
| Retool  | Save = live (preview updates in real-time)    | Deployment is separate                      | "Deploy" button, version history          |
| VS Code | Save = live (file on disk)                    | External build process                      | Extension indicators                      |

**n8n 2.0's model is the closest match to Luca's needs.** Key parallels:

- n8n: Save to draft (edit safely) -> Publish (go live). Luca: Save to `.agent.ts` (edit safely) -> Compile (go live in `.claude/agents/`).
- n8n: Webhooks only activate after publish. Luca: Agent changes only take effect after compilation.
- n8n: Autosave prevents data loss. Luca: Should autosave drafts to browser state (Jotai atoms).

**Proposed two-tier model for Luca Studio:**

| Change Type                                           | Save Behavior             | Effect                                   | Visual Indicator                  |
| ----------------------------------------------------- | ------------------------- | ---------------------------------------- | --------------------------------- |
| config.json fields (toggles, routing, gates, budgets) | Save = live               | Immediate effect on next workflow run    | Green "Saved" flash, timestamp    |
| Entity source files (agents, skills, rules)           | Save to source `.ts` file | Source updated but compiled output stale | Yellow "Saved (uncompiled)" badge |
| Entity compilation                                    | Explicit "Compile" button | Updates compiled output in `.claude/`    | Green "Compiled" badge, timestamp |

**Visual indicators for "saved but not compiled yet":**

- **Badge on entity card**: Yellow dot or "Uncompiled" tag next to entity name in list view
- **Editor header bar**: "Source saved. Compiled output is stale." with "Compile" action button
- **Sidebar nav**: Small yellow dot on Agents/Skills/Rules nav items when uncompiled entities exist
- **Diff indicator**: Show what changed since last compile (like git status)

**Is the two-stage model worth the complexity?**
Yes, because:

1. It matches the actual technical workflow (TypeScript source -> compiled markdown). Hiding this would create confusion when compiled output doesn't match what users see in the editor.
2. It prevents accidental production changes -- users can edit and preview without affecting running workflows.
3. n8n 2.0 proves this model is understood by developers. Their community actively requested the draft/publish separation.
4. The incremental compile approach (compile individual entities rather than `bun run build:all`) further reduces friction.

**Key UX guardrails from competitive research:**

- **Auto-save drafts** (n8n pattern): Save editor state to Jotai atoms on every change, persist to source file on explicit "Save" or after debounced interval
- **Protect against data loss** (GitLab pattern): Warn on navigation away from unsaved changes
- **Clear button labeling** (CraftCMS finding): Use "Save" for disk writes, "Compile" for build step -- never ambiguous "Publish"
- **Impact preview** (proposed in UX design doc): Before compile, show what the compiled output will change

**Recommendation**: Implement the two-tier model. Config changes save immediately. Entity changes require save + compile. Use yellow "uncompiled" badges as visual indicators. Autosave editor state to browser storage. Show "Compile" button prominently in the editor header when source is stale. Consider batch compile ("Compile All Stale") in addition to per-entity compile.

**Confidence**: High -- n8n 2.0's well-documented draft/publish model validates this pattern. The technical reality of Luca's build pipeline (TypeScript source -> compiled output) makes this a natural fit rather than added complexity.
