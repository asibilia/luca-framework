Research findings for R11, R12, and R13 — frontend implementation patterns for Luca Studio.

### R11: React Flow v12 Interactive Editing

**Finding**: The current workflow editor is already well-structured for the transition from read-only to interactive. The key props are already partially configured (`nodesDraggable: true`, `nodeDragThreshold: 5`, `elementsSelectable: true`), but `nodesConnectable` is explicitly `false`. Evolving to interactive editing requires controlled state management, event handlers for drag persistence, and custom edge interactions — all supported by React Flow v12's API.

**Evidence**:

#### Current Codebase State

The existing `workflow-canvas.tsx` (line 150-168) configures the ReactFlow component:

```tsx
<ReactFlow
  nodes={layoutNodes}
  edges={styledEdges}
  nodeTypes={nodeTypes}
  onNodeClick={onNodeClick}
  onPaneClick={closeSidebar}
  colorMode="dark"
  fitView
  nodesDraggable // Already enabled
  nodeDragThreshold={5} // 5px threshold to prevent accidental drags
  nodesConnectable={false} // Explicitly disabled — needs to change for editing
  elementsSelectable // Already enabled
  defaultEdgeOptions={{ type: "smoothstep" }}
/>
```

The current architecture uses **computed layout** (`applyGroupedColumnLayout` in `auto-layout.ts`) that positions stage-group nodes vertically and lets children use relative positions via `parentId`. This means drag-to-reorder will need to either (a) persist new positions and bypass auto-layout, or (b) recompute layout after reorder.

The custom node types (AgentNode, SkillNode, GateNode, StageGroupNode) all use Zod schema-first parsing (`WorkflowNodeDataSchema.safeParse(data)`) and the shared `NodeCard` component with `Handle` elements at `Position.Top` (target) and `Position.Bottom` (source). This handle configuration supports vertical flow reconnection.

#### React Flow v12 API for Interactive Editing

**1. Drag-to-reorder with `onNodeDragStop`:**

```tsx
const onNodeDragStop: OnNodeDrag = useCallback((event, node) => {
  // Persist the new position to server
  // node.position contains the updated { x, y }
  saveDraftPosition(node.id, node.position);
}, []);
```

Known issues in v12:

- Using `setNodes` inside `onNodeDragStop` can break the default `dragging: false` state (xyflow/xyflow#4839)
- `onNodeDragStop` fires even when node hasn't moved (xyflow/xyflow#3223) — use the existing `nodeDragThreshold={5}` to mitigate
- In v12, `onNodeDragStart/onNodeDrag/onNodeDragStop` also fire for selection drags

**Recommended pattern**: Use `onNodeDragStop` to persist position to draft state (Jotai atom), but avoid calling `setNodes` directly inside it. Instead, let the draft state update propagate through the normal React render cycle.

**2. Drop indicators (visual feedback during drag):**

React Flow v12 does NOT have built-in drop indicators. Two approaches:

- **Proximity Connect example** (reactflow.dev/examples/nodes/proximity-connect): Shows a dotted connection line when a node is near another node's handle during drag. Uses `onNodeDrag` with `getClosestEdge` to render temporary edges.
- **Custom CSS approach**: Add a `dragging` class to nodes during drag and use `onNodeDrag` to detect proximity to drop targets, then apply visual styles (glowing line, highlighted gap).

```tsx
const onNodeDrag: OnNodeDrag = useCallback(
  (event, node) => {
    // Calculate proximity to gap between existing nodes
    const nearestGap = findNearestGap(node.position, existingNodes);
    setDropIndicator(nearestGap); // Render a visual indicator
  },
  [existingNodes],
);
```

**3. Edge reconnection when nodes are reordered:**

React Flow v12 renamed `onEdgeUpdate` to `onReconnect` and provides a `reconnectEdge()` utility:

```tsx
import { reconnectEdge } from "@xyflow/react";

const onReconnect = useCallback(
  (oldEdge: Edge, newConnection: Connection) =>
    setEdges((edges) => reconnectEdge(oldEdge, newConnection, edges)),
  [],
);

// On ReactFlow component:
// <ReactFlow onReconnect={onReconnect} ... />
```

For edges to be draggable/reconnectable, you MUST define the `onReconnect` handler. Edges need `reconnectable` set on either the Edge type or individual edge data.

**4. Insert node between existing nodes:**

React Flow's **Dynamic Layouting Pro example** demonstrates this with a "+" button on edges. The pattern:

1. Create a custom edge component with an "add" button rendered at the edge midpoint
2. On click, split the edge: remove original edge (A->B), create new node C, add edges A->C and C->B
3. Use an auto-layout hook (e.g., d3-hierarchy or ELKjs) to recalculate positions

The **Add Node On Edge Drop** example (reactflow.dev/examples/nodes/add-node-on-edge-drop) shows a simpler variant where dropping a connection on empty canvas creates a new node. Both patterns are well-documented.

**5. Performance with 15-20 nodes and complex edges:**

15-20 nodes is trivially small for React Flow. The stress test example renders hundreds of nodes. At this scale, the main performance concern is unnecessary re-renders from custom nodes.

Key optimizations (already partially followed in the codebase):

- Node type registry defined at module level (already done: `const nodeTypes: NodeTypes = {...}` outside component)
- Memoize callback functions (already done: `useCallback` for handlers)
- Avoid storing flow state in Context API — use Jotai or Zustand for external state
- Keep CSS simple on nodes (the existing `shadow-md` and `backdrop-blur-sm` are fine at this scale)

**Recommendation**:

The evolution path from read-only to interactive should be phased:

1. **Phase A — Controlled state**: Replace computed `layoutNodes` with controlled state via `useNodesState` + `onNodesChange`. The current `applyGroupedColumnLayout` becomes an initialization function rather than a per-render computation. Persist positions in Jotai draft atoms.

2. **Phase B — Drag persistence**: Add `onNodeDragStop` handler to save positions to draft state. Add `onReconnect` for edge reconnection.

3. **Phase C — Insert/delete**: Add custom edge component with "+" button for insertion. Add context menu for node deletion. Use ELKjs or d3-hierarchy for re-layout after structural changes.

4. **Phase D — Connection drawing**: Set `nodesConnectable={true}`, add `onConnect` handler for new edges with DAG cycle validation.

**Confidence**: High — The existing codebase is well-architected for this transition. React Flow v12 APIs are stable and well-documented. The 15-20 node scale presents zero performance risk.

### R12: Jotai Patterns for Editing State

**Finding**: Jotai has mature primitives for all three layers of the proposed state model. The existing codebase already uses `atom`, `atomWithStorage`, and basic derived atoms — extending to `atomFamily` for per-entity drafts with dirty tracking and undo/redo is well-supported by the ecosystem.

**Evidence**:

#### Current Jotai Usage in the Codebase

The existing stores use simple patterns:

```typescript
// stores/filters.ts — Basic atoms
export const eventTypeFilterAtom = atom<string[]>([]);
export const searchQueryAtom = atom("");

// stores/session.ts — Nullable atom
export const selectedSessionAtom = atom<string | null>(null);

// stores/theme.ts — Persisted with atomWithStorage
export const themeAtom = atomWithStorage<"dark" | "light">(
  "luca-observer-theme",
  "dark",
);

// stores/vault.ts — Persisted with atomWithStorage
export const vaultAtom = atomWithStorage<string>(
  "luca-observer-vault",
  "default",
);
```

This demonstrates the team is already comfortable with `atom` and `atomWithStorage` from `jotai/utils`. The patterns below build naturally on this foundation.

#### Layer 1: Server State (Read-Only Mirror)

Use basic atoms populated by fetch + SSE invalidation:

```typescript
import { atom } from "jotai";
import type { AgentConfig } from "~/agents/__schemas/agent.schemas";

// Server state atom — populated from GET /api/entities/agents/[name]
export const agentServerAtom = atomFamily((name: string) =>
  atom<AgentConfig | null>(null),
);
```

#### Layer 2: Draft State with atomFamily

`atomFamily` creates per-entity atoms keyed by name. Each draft derives from its server state:

```typescript
import { atomFamily } from "jotai/utils";

// Draft atom per agent — initialized from server state, mutated by editor
export const agentDraftAtom = atomFamily((name: string) =>
  atom(
    (get) => {
      // Read: return draft if exists, otherwise server state
      const draft = get(agentDraftStoreAtom).get(name);
      return draft ?? get(agentServerAtom(name));
    },
    (get, set, update: AgentConfig) => {
      // Write: store in draft map
      const drafts = new Map(get(agentDraftStoreAtom));
      drafts.set(name, update);
      set(agentDraftStoreAtom, drafts);
    },
  ),
);

// Internal store backing the drafts
const agentDraftStoreAtom = atom(new Map<string, AgentConfig>());
```

**Memory management note**: `atomFamily` is internally a Map. For Studio's use case (user edits maybe 5-10 entities per session), memory is not a concern. But `myFamily.remove(param)` should be called when closing an editor tab to clean up. The `jotai-family` package (recommended for new projects) provides the same API with better TypeScript ergonomics.

#### Layer 3: Dirty Tracking

Derived atoms compare draft vs server state:

```typescript
import isEqual from "lodash/isEqual";

// Per-entity dirty flag
export const agentIsDirtyAtom = atomFamily((name: string) =>
  atom((get) => {
    const server = get(agentServerAtom(name));
    const draft = get(agentDraftAtom(name));
    return !isEqual(server, draft);
  }),
);

// Global dirty set — derived from all open drafts
export const dirtySetAtom = atom((get) => {
  const drafts = get(agentDraftStoreAtom);
  const dirty = new Set<string>();
  for (const [name] of drafts) {
    if (get(agentIsDirtyAtom(name))) dirty.add(name);
  }
  return dirty;
});

// Can save — dirty + no validation errors
export const canSaveAtom = atom((get) => {
  const dirty = get(dirtySetAtom);
  const errors = get(validationErrorsAtom);
  return dirty.size > 0 && errors.size === 0;
});
```

#### Persisting Draft State Across Navigation

Use `atomWithStorage` for draft persistence so unsaved edits survive page navigation:

```typescript
import { atomWithStorage } from "jotai/utils";

// Draft store persisted in sessionStorage (cleared on tab close, survives navigation)
const agentDraftStoreAtom = atomWithStorage<Record<string, AgentConfig>>(
  "luca-studio-agent-drafts",
  {},
  // Use sessionStorage — drafts are session-scoped, not permanent
  {
    getItem: (key, initial) => {
      const stored = sessionStorage.getItem(key);
      return stored ? JSON.parse(stored) : initial;
    },
    setItem: (key, value) => sessionStorage.setItem(key, JSON.stringify(value)),
    removeItem: (key) => sessionStorage.removeItem(key),
  },
  { getOnInit: true }, // Return stored value immediately, no flash
);
```

The `getOnInit: true` option is critical — it ensures the persisted draft appears immediately on navigation rather than causing a flash of the default value.

#### Undo/Redo with jotai-history

The `jotai-history` package provides a `withHistory` utility that wraps any atom with undo/redo:

```typescript
import { withHistory, UNDO, REDO } from "jotai-history";

// Create history-tracked version of draft atom (per entity)
export const agentDraftHistoryAtom = atomFamily(
  (name: string) => withHistory(agentDraftAtom(name), 50), // Keep 50 states max
);

// In component:
function AgentEditor({ name }: { name: string }) {
  const [history] = useAtom(agentDraftHistoryAtom(name));
  const setHistory = useSetAtom(agentDraftHistoryAtom(name));

  const handleUndo = () => setHistory(UNDO);
  const handleRedo = () => setHistory(REDO);

  const canUndo = history.canUndo;
  const canRedo = history.canRedo;
  // ...
}
```

`jotai-history` provides:

- `UNDO` / `REDO` — move target atom backward/forward in history
- `canUndo` / `canRedo` — boolean indicators
- `RESET` — clears entire history stack
- Configurable `limit` for max history entries

#### Concurrent Multi-Entity Editing

Jotai's `atomFamily` naturally supports concurrent editing because each entity gets its own atom tree:

```
Agent A open in tab 1:
  agentDraftAtom("lu-router")      → draft state
  agentDraftHistoryAtom("lu-router") → undo/redo history
  agentIsDirtyAtom("lu-router")    → dirty flag

Agent B open in tab 2:
  agentDraftAtom("lu-executor")      → separate draft state
  agentDraftHistoryAtom("lu-executor") → separate undo/redo history
  agentIsDirtyAtom("lu-executor")    → separate dirty flag
```

Changes to agent A do not trigger re-renders in agent B's editor, because Jotai's dependency tracking ensures each atom is independently subscribed. This is a core strength of Jotai over Context-based solutions — components only re-render when their specific atom dependencies change.

Batching: Multiple synchronous updates to different atoms are batched as a single atomic transaction by Jotai, so updating both agents in a bulk save won't cause intermediate re-renders.

**Recommendation**:

Implement the three-layer model exactly as proposed in `4.technical-architecture.md`:

1. **Server atoms** (`atomFamily` keyed by entity name) — populated from GET endpoints, invalidated by SSE `file:changed` events
2. **Draft atoms** (`atomFamily` with `atomWithStorage` backing via sessionStorage) — writeable clones created when editor opens
3. **Dirty tracking** (derived atoms comparing server vs draft with `lodash/isEqual`) — drives `DirtyIndicator`, `SaveBar`, and navigation guards

Add `jotai-history` for per-entity undo/redo. The `withHistory(targetAtom, 50)` pattern directly matches the brainstorm's "Max 50 entries" specification.

**Standard Stack for Jotai Layer:**

| Library          | Version   | Purpose                          | Why Standard                                               |
| ---------------- | --------- | -------------------------------- | ---------------------------------------------------------- |
| `jotai`          | 2.x       | Core state management            | Already in project                                         |
| `jotai/utils`    | (bundled) | `atomWithStorage`, `atomFamily`  | First-party utilities                                      |
| `jotai-history`  | 0.x       | Undo/redo history tracking       | Official jotai ecosystem package                           |
| `lodash/isEqual` | 4.x       | Deep equality for dirty tracking | Already in project, consistent with lodash preference rule |

**Confidence**: High — All proposed patterns use first-party Jotai utilities or well-maintained ecosystem packages. The existing codebase already uses the foundational patterns. The only risk is `jotai-history` being a 0.x package, but it's maintained by the official jotaijs organization and has a simple API surface.

### R13: Git Auto-Commit for Rollback

**Finding**: Batch-commit-on-publish using the system `git` CLI (via `Bun.$` or `simple-git`) is the recommended approach. Every "Publish" action creates a tagged git commit with a `[studio-edit]` prefix. This aligns with the brainstorm's proposal in `4.technical-architecture.md` and avoids polluting commit history with per-keystroke noise.

**Evidence**:

#### How Other Tools Handle Config Versioning

**GitOps tools (Terraform, Pulumi, ArgoCD):**

- Terraform state is versioned via backends (S3 with versioning, Terraform Cloud). Config changes go through PRs — never auto-committed silently.
- Pulumi uses git as the config source and triggers deploys from commits. Changes flow PR -> merge -> deploy.
- ArgoCD/FluxCD watch git repos and auto-deploy on commit. Northflank provides bidirectional sync — UI changes commit back to git.
- **Pattern**: Professional tools commit config changes to git but always through explicit actions (PR, deploy button, publish), never silently per-keystroke.

**etcd/Consul:**

- etcd maintains internal revision history per key with compare-and-set semantics. Every write increments a global revision counter.
- Consul requires writes to pass through Raft consensus. Both provide "version history" natively but are key-value stores, not file-based.
- **Pattern**: Built-in versioning at the storage layer, not git-based.

**VS Code Settings Sync:**

- Uses a hidden git-like mechanism (Microsoft's proprietary sync). Settings are versioned but not through user-visible git commits.
- **Pattern**: Shadow versioning invisible to the user.

#### Evaluation of Approaches

| Approach                             | Granularity               | Git noise                             | Rollback UX                                   | Complexity | Verdict                                  |
| ------------------------------------ | ------------------------- | ------------------------------------- | --------------------------------------------- | ---------- | ---------------------------------------- |
| Every edit = one commit              | Per-keystroke             | Extreme (100s of commits per session) | Fine-grained but overwhelming                 | Low        | **Reject** — Pollutes user's git history |
| Batch on publish                     | Per-publish               | Low (1-3 commits per editing session) | Good — each commit is a meaningful save point | Low        | **Recommended**                          |
| Separate branch (`studio/edits`)     | Per-edit on shadow branch | None on main, but branch diverges     | Good but complex merge UX                     | Medium     | **Acceptable fallback**                  |
| Shadow copy dir (`.studio/history/`) | Timestamped snapshots     | None                                  | File-based restore but no git integration     | Medium     | **Reject** — Reinvents version control   |
| Git stash                            | Per-stash                 | None                                  | Poor — stashes are LIFO, unnamed, local-only  | Low        | **Reject** — Not designed for history    |
| Git reflog                           | Automatic                 | None                                  | Expert-only UX, ephemeral                     | None       | **Reject** — Not user-facing             |

#### Recommended: Batch Commit on Publish

When the user clicks "Publish" (or "Save" triggers compilation):

```typescript
// In Next.js API route: POST /api/publish
import { $ } from "bun";

async function commitStudioEdit(
  files: string[],
  message: string,
): Promise<{ sha: string }> {
  // Stage only the specific files that were edited
  for (const file of files) {
    await $`git add ${file}`;
  }

  // Commit with studio prefix for easy filtering
  const commitMessage = `[studio-edit] ${message}`;
  await $`git commit -m ${commitMessage}`;

  // Get the commit SHA for the response
  const sha = (await $`git rev-parse HEAD`.text()).trim();
  return { sha };
}
```

For the "Config History" view, filter commits by prefix:

```typescript
// List studio edit commits
async function getStudioHistory(limit = 50): Promise<StudioCommit[]> {
  const log =
    await $`git log --oneline --grep="\\[studio-edit\\]" -n ${limit} --format="%H|%s|%ai"`.text();
  return log
    .trim()
    .split("\n")
    .map((line) => {
      const [sha, message, date] = line.split("|");
      return { sha, message: message.replace("[studio-edit] ", ""), date };
    });
}

// Revert a specific file to a specific version
async function revertFile(sha: string, filePath: string): Promise<void> {
  await $`git checkout ${sha} -- ${filePath}`;
}
```

#### Interaction with Normal Git Workflow

The user is actively committing code alongside Studio edits. Key considerations:

1. **Same branch, same history**: Studio commits interleave with manual commits. This is actually fine — `[studio-edit]` prefix makes them filterable via `git log --grep`.

2. **No branch pollution**: Staying on the current branch means no merge conflicts from shadow branches. The user's `git log` shows a clean history.

3. **Interactive rebase friendly**: If the user wants to squash studio edits before pushing, they can `git rebase -i` and squash all `[studio-edit]` commits. This is a standard git workflow.

4. **Conflict handling**: If the user makes a manual edit to the same file Studio is about to commit, the `git add` + `git commit` will simply include both changes. If there's a working tree conflict, Studio's ETag-based optimistic locking catches it first (409 Conflict response before git is involved).

#### Why NOT Git Stash or Reflog

- **Git stash**: Designed for temporarily shelving work-in-progress, not for persistent history. Stashes are unnamed, local-only, LIFO, and easily lost. No UI-friendly way to browse or restore specific stashes.
- **Git reflog**: Records HEAD movements but is ephemeral (garbage collected), local-only, and requires expert knowledge to navigate. Not suitable for a user-facing "Config History" feature.

#### Alternative: simple-git or isomorphic-git

If `Bun.$` shell invocation proves problematic (e.g., git not available in some environments):

- **`simple-git`** (npm: 16M weekly downloads): Lightweight wrapper around system git. Async/await API. Works in any Node.js/Bun environment. No git reimplementation — just wraps the CLI.
- **`isomorphic-git`**: Pure JavaScript git implementation. Works in browser and Node. Heavier (reimplements git internals) but doesn't require system git. Overkill for a server-side Next.js API route.

**Recommendation**: Use `Bun.$` for git operations (consistent with project conventions). Fall back to `simple-git` only if Bun shell proves unreliable for git commands.

**Recommendation**:

1. **Commit strategy**: Batch commits on "Publish" with `[studio-edit]` prefix
2. **Implementation**: `Bun.$` shell commands in Next.js API route (`POST /api/publish`)
3. **History view**: `git log --grep="[studio-edit]"` to list, `git checkout <sha> -- <file>` to revert
4. **No shadow branch**: Stay on current branch — simpler, no merge conflicts, filterable by prefix
5. **No additional dependencies**: System git via Bun shell is sufficient

**Confidence**: High — This approach directly matches what `4.technical-architecture.md` already proposes ("Every Console write creates a git commit tagged `[studio-edit]`"). The implementation is straightforward, uses no new dependencies, and is consistent with how GitOps tools handle config versioning. The only low-confidence area is whether `Bun.$` handles git edge cases (uncommitted changes, detached HEAD, merge conflicts) gracefully — this needs integration testing.
