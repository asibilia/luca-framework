# Product Vision: Luca Studio

## Tagline

_A glass control plane for your agentic workflow — see exactly what Luca does, understand why, and change how it works._

## Three Modes of Interaction

### Observe

Watch what Luca is doing. Read-only dashboards for workflow status, session history, memory health, eval results, and state machine inspection.

### Browse

Inspect what Luca is built from. Navigable registries for agents, skills, rules, and the workflow pipeline. View source code, compiled output, model routing, and configuration.

### Configure / Edit

Customize how Luca behaves. Three tiers of editing depth:

**Tier 1 — Configuration (Consumer-facing)**

- Toggle workflow steps on/off per complexity level
- Swap agent model routing (which tier at which complexity)
- Enable/disable agents, rules, gates
- Adjust loop budgets and iteration limits
- Configure verification harness (which checks run)
- Export/import workflow configs as shareable JSON

**Tier 2 — Authoring (Power user)**

- Create new agents from templates or by forking existing ones
- Edit agent prompts with live compiled preview
- Create custom rules with structured form + markdown body
- Define custom workflow steps with input/output contracts

**Tier 3 — Memory System Configuration (Specialized)**

- Edit vault routing table
- Manage brain tree entries
- Configure recall merge strategy and score thresholds

## Feature Inventory

### Workflow Pipeline Editor

- Visual drag-and-drop reordering of pipeline steps
- Per-complexity-level step configuration ("skip Discuss for TRIVIAL, add extra gates for CRITICAL")
- Step parameter editing: iteration budgets, timeout thresholds, verification depth
- Preview mode: show what the pipeline looks like at each complexity level before saving
- Step detail panel: which agents participate, model routing, input/output contracts

### Agent Management

- Card grid browsable by category (general, luca, custom)
- Agent detail view with source/compiled side-by-side
- Model routing table per agent (5 complexity levels x 3 model tiers)
- Fork existing agents to create custom variants
- Full prompt editor with live compiled preview
- Agent enable/disable toggles

### Rule Management

- Browse all rules with descriptions and glob patterns
- Toggle rules on/off
- Create custom rules with structured form
- Rule profiles: named collections of enabled/disabled rules for different project types

### Complexity Routing

- Editable model routing matrix (agents x complexity levels)
- Editable loop budget table
- Named routing presets (ALWAYS_FAST, ORCHESTRATOR, DEEP_ANALYSIS, etc.)
- Visual indicator of which agents use which preset

### Gate Management

- Toggle grid: gates x complexity levels
- Fail-closed semantics indicator
- Per-complexity gate matrix

### Verification Configuration

- Check type toggles (test, typecheck, lint, build)
- Command overrides per check
- Iteration limit configuration
- Failure threshold settings

## Page Consolidation

### Current 11 Pages → Recommended Final State

| Current Page    | Verdict                                  | Rationale                                                 |
| --------------- | ---------------------------------------- | --------------------------------------------------------- |
| Dashboard       | **Replaced** by Home                     | Home shows status + quick actions, not vanity metrics     |
| Sessions        | **Kept**                                 | Core observability — "what happened?"                     |
| Memory          | **Consolidated** — absorbs 5 other pages | All MuninnDB views become tabs on one page                |
| Learning        | **Tab within Memory**                    | Learnings are memories with specific concept prefixes     |
| Vault           | **Tab within Memory**                    | Vault health is a filtered MuninnDB view                  |
| Knowledge Graph | **Tab within Memory**                    | Graph visualization becomes a sub-view                    |
| Workflow Editor | **Replaced** by Pipeline                 | Evolves from read-only to interactive                     |
| Semantic Search | **Feature within Memory**                | Search bar + search tab, not a standalone page            |
| Decisions       | **Kept** under Sessions                  | Workflow-scoped decision log                              |
| Contradictions  | **Removed**                              | Never populated with real data                            |
| Entities        | **Removed**                              | Replaced by specific entity pages (Agents, Skills, Rules) |

### Why Memory Pages Must Merge

Memory, Learning, Vault, Knowledge Graph, Semantic Search, Decisions, Contradictions, and Entities are all different views of the same underlying data store (MuninnDB). Having 8 entry points for one data source is a navigation tax. Users should land on one Memory page and switch views (list, graph, search, health) via tabs.

## Proposed Navigation Structure

> **Updated after research (R8):** Merged Complexity + Gates into Config (as tabs). Added Memory back (was accidentally omitted despite consolidating 5 pages into it). Reduced from 11 to 9 items — competitors average 6-8 top-level items.

```
OBSERVE
  Home              — Status + quick actions (not a metrics dashboard)
  Sessions          — Session explorer with timeline, phase drill-down
  Memory            — Consolidated MuninnDB explorer (browse | graph | search | health tabs)

BUILD  (prioritized for v1 — these work without MuninnDB)
  Pipeline          — Visual workflow editor (React Flow, interactive)
  Agents            — Browse + configure agents (read-only prompts in v1)
  Skills            — Browse + configure skills
  Rules             — Browse + configure rules

CONFIGURE
  Config            — Complexity routing, gates, harness settings (as tabs)
  Settings          — Raw config editor, project identity, vault config
```

9 items in 3 groups. BUILD pages prioritized for v1 because they read from the filesystem and work on a fresh install without MuninnDB (R5).

## Consumer vs Editor Experience

### Progressive Disclosure Strategy

**Level 1 — Observe (default)**: Everything in the OBSERVE group is immediately visible and functional. This is what you see first.

**Level 2 — Configure**: BUILD and CONFIGURE groups show controls. Advanced options are collapsed by default behind "Advanced" sections.

**Level 3 — Author**: Agent/skill/rule authoring is available but visually secondary (outline buttons, not primary). Source editors show a banner about rebuild requirements.

The consumer never needs to be told they're a consumer. They stop at the depth they need. The editor never unlocks anything. They just keep clicking deeper.

**One UI. One navigation. Progressive depth.**

## The Wow Moment

Opening the **Pipeline page** and seeing YOUR workflow. Not a generic diagram — YOUR pipeline with YOUR agents, YOUR complexity levels, YOUR overrides.

1. A beautiful DAG visualization of the active workflow
2. Click a step (e.g., "Verify")
3. Panel slides out: which agents run, model tier at current complexity, iterations budgeted, last 3 session results
4. Toggle a slider: "Skip this step for TRIVIAL tasks"
5. DAG animates to show the step grayed out at TRIVIAL, active at MODERATE+
6. Click "Save" — `.planning/config.json` is updated

The moment: they realize they're not configuring a tool — they're designing their own development process, visually.

### Secondary Wow Moments

**Agent Discovery**: "I didn't know Luca had a security auditor. Let me enable it." The Agent browser shows all available agents, even disabled ones, with descriptions.

**Session Replay**: "Show me exactly what happened in last night's COMPLEX task." Phase-by-phase timeline with agent outputs, engrams captured, verification results.

**Complexity Preview**: "What does Luca actually DO differently for CRITICAL vs TRIVIAL?" Side-by-side comparison of the full pipeline at each complexity level.

## Risks and Anti-Patterns

### 1. Building an IDE

**Trap**: Adding a code editor, file tree, terminal, git integration — turning Studio into VS Code.

**Guardrail**: Luca Studio is a control plane, not a code editor. It configures the agentic workflow. The source editor for agents is a specialized, narrow editor for those TypeScript files, not a general-purpose editor.

**Litmus test**: If a feature would make sense in VS Code, it doesn't belong in Studio.

### 2. Configuration Sprawl

**Trap**: Exposing every configuration option, turning pages into walls of toggles.

**Guardrail**: Every configuration surface must answer "what decision is the user making?" Prefer smart defaults with override capability over exhaustive option lists.

### 3. Stale Preview Problem

**Trap**: Source/compiled preview gets out of sync with what `bun run build:all` actually produces.

**Guardrail**: Preview must use actual compiler code (imported from `src/compilers/`). If it can't, label it "approximate preview" with a "Build & Verify" button.

### 4. Memory Page Becomes a Database Admin Tool

**Trap**: Unified Memory page grows every MuninnDB query capability until it's a generic database admin UI.

**Guardrail**: Memory shows engrams meaningful to the workflow. Filter options map to workflow concepts (sessions, patterns, pitfalls), not database concepts.

### 5. Over-investing in Edit Before Observe is Solid

**Trap**: Building full authoring before observation is battle-tested.

**Guardrail**: Ship in order — BUILD (filesystem-based, works immediately) → Configure → Observe (needs MuninnDB) → Author (Tier 2+).

> **Research update (R5, R7):** BUILD pages should ship first — they read from the filesystem and work on fresh installs. OBSERVE pages (Sessions, Memory) need MuninnDB running with data. Launch with **Tier 1 only** (config editing + read-only prompt viewing). Defer prompt editing (Tier 2) and agent creation (Tier 3). The 47 existing agents, 58 skills, and 24 rules cover most consumer needs — configuring them is higher value than creating new ones.

### 6. Two-App Merge Creates Frankenstein

**Trap**: Stitching pages together without coherent information architecture.

**Guardrail**: Neither app's page structure survives intact. Both are dissolved and reconstituted into the three-mode structure.

### 7. Real-Time Streaming Before Architecture Supports It

**Trap**: Building live session streaming before a reliable event bus exists.

**Guardrail**: V1 is entirely post-hoc observation. Real-time streaming is V2.
