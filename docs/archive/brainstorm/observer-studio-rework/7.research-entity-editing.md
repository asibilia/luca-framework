# Research: Entity Editing

Research into TypeScript round-trip fidelity, agent editing complexity, and package rename for the Luca Studio rework.

---

### R3: TypeScript Round-Trip Fidelity

**Finding**: ALL entity files (agents, skills, rules) follow a strict canonical template with zero deviations. The pattern is highly regular, making round-trip editing feasible -- but template literal edge cases in section content require careful handling.

**Evidence**:

**Canonical Agent Template** (47 agents, 100% adherence):

```
JSDoc comment
import { createAgent } from "~/agents/__helpers/create-agent";
[optional shared imports: COLD_ISOLATION_BLOCK, RESEARCH_REVIEWER_* constants]
import type { AgentConfig } from "~/agents/__schemas/agent.schemas";

const {camelCaseName}Config: AgentConfig = {
  frontmatter: { name, description, tools?, color?, cognition?, context?, ... },
  sections: [ { title, content, order? }, ... ]
};

export const {camelCaseName}Agent = createAgent({camelCaseName}Config);
```

**Canonical Skill Template** (58 skills, 100% adherence):

```
JSDoc comment
import { createSkill } from "~/skills/__helpers/create-skill";
import type { SkillConfig } from "~/skills/__schemas/skill.schemas";

const {camelCaseName}Config: SkillConfig = {
  frontmatter: { name, description, "disable-model-invocation"? },
  sections: [ { title, content, order? }, ... ],
  evals?: [ { prompt, expected, criteria } ]
};

export const {camelCaseName}Skill = createSkill({camelCaseName}Config);
```

**Canonical Rule Template** (24 rules, 100% adherence):

```
JSDoc comment
import { createRule } from "~/rules/__helpers/create-rule";
import type { RuleConfig } from "~/rules/__schemas/rule.schemas";

const {camelCaseName}Config: RuleConfig = {
  frontmatter: { description, globs?, alwaysApply? },
  sections: [ { title, content, order? } ]
};

export const {camelCaseName}Rule = createRule({camelCaseName}Config);
```

**Structural Variations Found** (minor, all within the template):

1. **Shared constant imports** -- 5 agents import `COLD_ISOLATION_BLOCK` from `~/agents/__helpers/cold-isolation-block`; 3 agents import `RESEARCH_REVIEWER_*` constants from `~/agents/__helpers/research-reviewer-shared-sections`. These are string constants interpolated into section `content` via `${CONSTANT_NAME}`.

2. **No other import variations** -- all other imports are strictly the factory function + type. No agent, skill, or rule imports external libraries, utility functions, or computes anything dynamically.

**Template Literal Edge Cases in Section Content**:

| Edge Case                                     | Prevalence                    | Example                                                              |
| --------------------------------------------- | ----------------------------- | -------------------------------------------------------------------- |
| Escaped backticks `\`\`\`` for code blocks    | Extremely common (40+ agents) | lu-debugger has 60 occurrences                                       |
| Escaped `\${VAR}` for shell variable examples | 15+ agents                    | `\${COMMIT_HASH}`, `\${FIX_DESCRIPTION}` in lu-pr-reviewer           |
| Real `${CONSTANT}` interpolation              | 8 agents                      | `${COLD_ISOLATION_BLOCK}`, `${RESEARCH_REVIEWER_*}`                  |
| Regex patterns in content                     | Rare (2-3 files)              | `line.match(/\\*\\*Research refs:\\*\\*/)?.[1]` in lu-executor       |
| XML-like tags in content                      | Common                        | `<role>`, `<step>`, `<cognition_integration>`, `<context_isolation>` |
| Nested markdown (headings inside content)     | Universal                     | `## Sub-heading` within section content strings                      |

**The Core Schema** (`src/shared/__helpers/format.ts`):

```typescript
export const SectionSchema = z.object({
  title: z.string(),
  content: z.string(),
  order: z.number().optional(),
});
```

All three entity types (agent, skill, rule) share this same `SectionSchema`. The entire "prompt" of an entity is just an array of `{ title: string, content: string, order?: number }` objects.

**Could we migrate to YAML frontmatter + markdown body?**

Technically yes, but with significant caveats:

- **Pro**: The `frontmatter` object maps cleanly to YAML. The `sections` array could become markdown H2 sections.
- **Pro**: Would eliminate the template literal escaping nightmare (no more `\\\`\\\`\\\``or`\${}`).
- **Con**: 8 agents use `${CONSTANT}` interpolation for shared blocks. This would need a different mechanism (includes, partials, or pre-processing).
- **Con**: The current system validates via Zod schemas at parse time -- a YAML+markdown format would need equivalent validation.
- **Con**: Migration effort for 129 files is non-trivial.
- **Better alternative for Studio**: Don't change the on-disk format. Instead, extract the JSON-serializable `AgentConfig`/`SkillConfig`/`RuleConfig` objects from TypeScript at read time, edit them in the UI, and regenerate the TypeScript file from the config. The template is so regular that code generation is trivial.

**Recommendation**: Do NOT change the on-disk format. Instead, build a TypeScript round-trip layer:

1. **Read path**: Import the module -> extract `.config` from the `BaseAgent`/`BaseSkill`/`BaseRule` object -> serialize to JSON for the UI. The `config` getter already returns the validated, frozen config object.
2. **Write path**: Accept edited JSON config from UI -> generate TypeScript source using a simple template (the template is 100% regular, no variations) -> write to disk.
3. **Shared constant handling**: For the 8 agents using `${CONSTANT}` interpolation, the round-trip layer needs to know these constants and either inline them (lossy) or preserve the `${CONSTANT}` reference (requires tracking which parts of content came from constants).

The read path is nearly free -- `agentRegistry["lu-executor"]().config` already gives you the validated config as a plain object. The write path is a simple string template.

**Confidence**: High -- read every agent, skill, and rule file, plus all factory functions and schemas. Zero structural deviations found.

### R7: Agent Editing Complexity

**Finding**: The codebase contains 129 entities (47 agents, 58 skills, 24 rules). Agent prompt sizes vary enormously -- from 2.2KB config-only agents to 40KB instruction manuals. A tiered editing approach is strongly recommended: start with config-only editing (Tier 1), defer prompt authoring to Tier 2.

**Evidence**:

**Entity Counts:**

- Agents: 47 (43 general + 4 luca-specific)
- Skills: 58 (57 general + 1 luca-specific)
- Rules: 24 (17 general + 7 profile-specific)
- **Total: 129 entity files**

**Agent Prompt Size Distribution** (by file size, which includes boilerplate ~300 bytes):

| Category                   | Size Range | Count | Examples                                                                                |
| -------------------------- | ---------- | ----- | --------------------------------------------------------------------------------------- |
| Short config-like          | <3KB       | 7     | lu-verifier-fast (2.2KB), lu-router-fast (2.4KB), lu-completeness-reviewer (2.5KB)      |
| Medium                     | 3KB-8KB    | 19    | ui (2.7KB), product (3.1KB), code-architect (3.5KB), code-simplifier (3.9KB)            |
| Long detailed              | 8KB-20KB   | 14    | lu-roadmapper (16.8KB), lu-codebase-mapper (17.7KB), lu-router (14.1KB)                 |
| Very long instruction sets | >20KB      | 7     | lu-executor (24.7KB), lu-cognition (35.2KB), lu-debugger (38.2KB), lu-verifier (39.7KB) |

**Section Count Distribution:**

| Sections     | Count     | Notes                                                                   |
| ------------ | --------- | ----------------------------------------------------------------------- |
| 1 section    | 35 agents | Most common -- single "role" section with all instructions              |
| 4-6 sections | 6 agents  | lu-discuss-researcher, lu-premortem, lu-shadow-scanner, lu-process-data |
| 8-9 sections | 3 agents  | lu-executor (8), lu-planner (9)                                         |

**Frontmatter Complexity:**

Most agents have the full frontmatter complement:

- `name`, `description`: required for all
- `tools`: array of 3-6 tool names (e.g., `["Read", "Write", "Edit", "Bash", "Grep", "Glob"]`)
- `cognition`: tier config (`default_tier`, `promotable_to`, `memory_tags`, optional `eager_recall`)
- `context`: tier config (`default_tier`, `promotable_to`, `isolation`)
- `background_spawnable`: boolean
- `purpose`: enum (researcher, planner, executor, verifier, reviewer, synthesizer, auditor, general)
- `allowed_contexts`: string array

**Do consumers need to CREATE new agents?**

Analysis suggests NO for most use cases:

1. The 47 agents cover a comprehensive set of roles (routing, planning, execution, verification, review, debugging, learning, research, etc.)
2. The agent system is deeply integrated -- agents reference each other by name in prompts, the registry in `build-agent-registry.ts` manually imports each agent, and the `MODEL_ROUTING_TABLE` maps specific agent names to model tiers.
3. Adding a new agent requires: creating the `.agent.ts` file, importing it in the registry, adding it to the `MODEL_ROUTING_TABLE`, and running `bun run build:all`.
4. **More useful for consumers**: tuning existing agent behavior (adjusting prompts, changing tools, toggling cognition tiers) rather than creating entirely new agents.

**Could we start with config-only editing (Tier 1)?**

Yes, and this is the recommended approach:

**Tier 1 -- Config Editing** (high value, low risk):

- Toggle `background_spawnable`
- Change `purpose` category
- Adjust `cognition` tiers (T0-T3)
- Modify `tools` array
- Update `allowed_contexts`
- Enable/disable agents (via registry toggle, not deletion)

**Tier 2 -- Prompt Editing** (high value, higher complexity):

- Edit section `content` strings
- Add/remove sections
- Reorder sections (via `order` field)
- For the 7 agents with shared constants (`COLD_ISOLATION_BLOCK`, `RESEARCH_REVIEWER_*`), show the resolved content but warn that edits won't propagate to the constant.

**Tier 3 -- Full Authoring** (low priority, highest complexity):

- Create new agents from scratch
- This requires registry integration, model routing, and `build:all` -- better handled by the CLI/developer workflow.

**Recommendation**: Launch with Tier 1 (config editing) + read-only prompt viewing. Tier 2 (prompt editing) in a fast-follow. Tier 3 (creation) is not needed for the foreseeable future.

**Confidence**: High -- read all 47 agent files, all factory functions, the registry, and the schema definitions. The size distribution and structural analysis are based on direct file measurement.

### R14: Package Rename

**Finding**: Renaming `packages/luca-observer` to `packages/luca-studio` is straightforward but touches many files. The npm package name is `@alecsibilia/luca-observer`. The rename should happen all-at-once in a single commit to avoid broken references. `@alecsibilia/luca-studio` is the recommended new name.

**Evidence**:

**Current naming:**

- Directory: `packages/luca-observer/`
- npm package name: `@alecsibilia/luca-observer` (in `packages/luca-observer/package.json`)
- Binary: `luca-observer` (in package.json `bin` field)

**Files requiring changes (by category):**

**1. Root config files (3 files, 4 references):**

- `package.json`: 2 script references (`css:observer`, `dev:observer`) using `--filter @alecsibilia/luca-observer`
- `tsconfig.json`: 1 exclude entry `"packages/luca-observer"`
- `bunfig.toml` or similar: none found

**2. Source code references (3 files, ~15 references):**

- `packages/luca-framework/src/emitter/__helpers/emit-functions.ts`: 1 comment reference
- `packages/luca-framework/src/emitter/__helpers/muninn-http.ts`: 2 comment references
- `src/workflow/__helpers/dag-visualizer.ts`: 10+ comment/type references (mirrors observer types)

**3. Scripts (1 file):**

- `scripts/check-observer-schema-drift.ts`: file name itself + 3 internal references to `packages/luca-observer/lib/types`

**4. Documentation (14 files):**

- `docs/memory-system/` -- 3 files with references
- `docs/brainstorm/observer-studio-rework/` -- 2 files
- `docs/workflow-system/` -- 4 files
- `docs/architecture-overview.md`, `docs/observer-architecture.md`, `docs/observer-deployment.md` -- 3 files

**5. Planning artifacts (5 files):**

- `.planning/milestones/*.json` -- 4 snapshot files
- `.planning/migration/*.json` -- 1 file

**6. Internal to the package itself:**

- `packages/luca-observer/package.json`: `name` field, `bin` field
- `packages/luca-observer/stores/vault.ts`, `stores/theme.ts`: possibly internal references
- `packages/luca-observer/lib/types.ts`: type definitions
- `packages/luca-observer/.next/` -- generated, will rebuild automatically

**7. CI/CD:**

- `.github/workflows/publish.yml`: NO references to luca-observer (only publishes luca-framework)

**Rename Impact Assessment:**

| Category                    | File Count | Risk     | Notes                                               |
| --------------------------- | ---------- | -------- | --------------------------------------------------- |
| Root configs                | 3          | Low      | Simple find-replace                                 |
| Source code (comments only) | 3          | Very Low | All references are JSDoc comments, not import paths |
| Scripts                     | 1          | Low      | Rename file + update imports                        |
| Documentation               | 14         | Very Low | Find-replace in .md files                           |
| Planning artifacts          | 5          | Very Low | Historical snapshots, optional update               |
| Package internals           | 3-5        | Low      | package.json, stores, lib                           |
| Generated artifacts         | Many       | None     | .next/ and node_modules rebuild automatically       |

**Key observations:**

1. `luca-observer` is **excluded** from the root `tsconfig.json` -- it has its own `tsconfig.json`. This means NO import path aliases point to it from `src/`.
2. The `luca-framework` package references observer only in **comments** (JSDoc `@see` tags), not in actual import statements.
3. The `dag-visualizer.ts` defines its own types that "mirror" observer types but does NOT import them. The `check-observer-schema-drift.ts` script validates they stay in sync.
4. The observer package is a **standalone Next.js app** with its own dependencies. The rename is mostly a directory rename + package.json update.

**Should rename happen incrementally or all at once?**

**All at once.** Reasons:

1. No runtime imports exist between the monorepo's `src/` and `packages/luca-observer/` -- only comments and config references.
2. Bun workspace resolution uses the directory name. A partial rename would break workspace resolution.
3. The git history is preserved with `git mv packages/luca-observer packages/luca-studio`.
4. Total file changes: ~25 files for find-replace, 1 directory rename. Small enough for a single commit.

**Recommended new name:** `@alecsibilia/luca-studio` for the npm package, `packages/luca-studio` for the directory.

**Rename checklist:**

1. `git mv packages/luca-observer packages/luca-studio`
2. Update `packages/luca-studio/package.json`: name -> `@alecsibilia/luca-studio`, bin -> `luca-studio`
3. Update root `package.json` scripts: `css:observer` -> `css:studio`, `dev:observer` -> `dev:studio`, filter names
4. Update root `tsconfig.json` exclude
5. Rename `scripts/check-observer-schema-drift.ts` -> `scripts/check-studio-schema-drift.ts`, update internal paths
6. Global find-replace `luca-observer` -> `luca-studio` in all `.ts`, `.md`, `.json` files
7. `bun install` to regenerate lockfile
8. Verify: `bun run dev:studio`, `bunx --bun tsc --noEmit`

**Confidence**: High -- exhaustively searched all file types for "luca-observer" and "@alecsibilia/luca-observer" references. The observer package is well-isolated from the core `src/` tree.
