# Review: 03-muninndb-integration

## Reviewer: MuninnDB Integration Reviewer (Cold Isolation)

## Date: 2026-03-22

## Iteration: 1

## Summary Assessment

The 03-muninndb-integration section is well-structured and internally coherent within its own five documents. The three-stage memory model (files -> engrams -> targeted context) is clearly motivated and the lifecycle is comprehensive. However, there are **critical contradictions with the cross-referenced documents** (04-agent-orchestration/graduation-agent.md and 01-workflow-steps/06-graduate.md) that would make implementation impossible without resolution, and several design decisions are under-specified enough to leave implementers guessing.

## Critical Findings

- **CRIT-MN-001**: graduation-model.md vs 04-agent-orchestration/graduation-agent.md -- **Scoring formula is fundamentally different**. graduation-model.md defines a **weighted sum** (`confidence * 0.40 + actionability * 0.35 + uniqueness * 0.25`) with a threshold of **0.55**, while graduation-agent.md defines a **product** (`confidence * actionability * uniqueness`) with a threshold of **0.35**. These produce wildly different results. For example, a finding with confidence=HIGH(1.0), actionability=background(0.3), uniqueness=novel(1.0) scores **0.68** under the weighted-sum model (passes 0.55 threshold) but only **0.30** under the product model (fails 0.35 threshold). An implementer cannot know which formula to use. **Suggested resolution**: Pick one formula and one threshold, and update all documents to match. The weighted-sum model from graduation-model.md is more robust (a single zero dimension does not annihilate the entire score), so it is likely the intended design.

- **CRIT-MN-002**: graduation-model.md vs 01-workflow-steps/06-graduate.md + 04-agent-orchestration/graduation-agent.md -- **Concept prefix scheme is contradictory**. graduation-model.md and concept-prefix-extensions.md define a new `research:*` namespace (research:approach-_, research:api-_, research:pitfall-_, etc.) with REPO vault routing. But 01-workflow-steps/06-graduate.md and 04-agent-orchestration/graduation-agent.md graduate directly to the **existing** `pattern:_`, `pitfall:_`, and `decision:_`namespaces with the existing vault routing (patterns -> DEFAULT, decisions -> REPO). These are two completely incompatible designs. Under the 03-muninndb-integration model, graduation writes to`research:_`in REPO, and only lu-learner later promotes to`pattern:_`/`pitfall:_`in DEFAULT. Under the 01/04 model, graduation writes directly to`pattern:_`/`pitfall:_`in DEFAULT. **Suggested resolution**: Align 01-workflow-steps/06-graduate.md and 04-agent-orchestration/graduation-agent.md to use the`research:_` prefix scheme documented here, since the two-stage lifecycle (research:_ -> promotion -> pattern:_/pitfall:\*) is the more coherent design with clear lifecycle boundaries.

- **CRIT-MN-003**: 01-workflow-steps/06-graduate.md -- **Agent identity conflict**. Step 06 describes spawning `lu-learner` (adapted) for graduation, while graduation-model.md and 04-agent-orchestration/graduation-agent.md describe a dedicated `lu-research-graduator` agent. The `lu-learner` adaptation reuses an existing agent for a new purpose without defining how the "adaptation" changes its behavior, tools, or prompt. The `lu-research-graduator` has a full agent specification. **Suggested resolution**: Settle on one agent. The dedicated `lu-research-graduator` from graduation-model.md has a clearer contract and avoids overloading lu-learner's responsibilities.

- **CRIT-MN-004**: graduation-model.md -- **Actionability sub-scoring is ambiguous**. The actionability dimension lists four discrete levels (1.0, 0.8, 0.3, 0.1) but provides no objective criteria for distinguishing between them. "Direct implementation detail" vs. "Architecture constraint or decision" vs. "Background context" are subjective categories that an LLM will interpret inconsistently across runs. The confidence dimension is better because it ties to verifiable source categories. **Suggested resolution**: Define actionability in terms of observable signals (e.g., "contains specific function name or parameter value" = 1.0, "names a specific technology choice" = 0.8, "describes a general strategy without specifics" = 0.3, "purely informational" = 0.1).

## Important Findings

- **IMP-MN-001**: per-task-recall.md vs 01-workflow-steps/09-execute.md -- **Research ref annotation syntax differs**. per-task-recall.md uses `**Research refs:** research:approach-ws-reconnect, research:pitfall-ws-memory-leak` (a Markdown bold field with comma-separated concept prefixes). 09-execute.md uses `@research(file-path#section)` and `@engram(concept)` annotation syntax. These are different mechanisms: one is concept-prefix-based MuninnDB recall, the other is file-path-based reading plus engram recall. The executor would need to support both or one must be canonical. **Suggested resolution**: Clarify that `**Research refs:**` is the PLAN.md format for concept-based MuninnDB recall (the 03-muninndb-integration design), while `@research()` and `@engram()` are an alternative or extended annotation syntax defined in 01-workflow-steps. If both exist, document how they interact and which takes precedence.

- **IMP-MN-002**: per-task-recall.md -- **muninn_recall mode:"semantic" is not a documented MuninnDB API parameter**. The recall protocol specifies `muninn_recall(vault, context, mode: "semantic")`, but the MuninnDB MCP tools available (visible in the deferred tools list) show `muninn_recall` accepting `vault` and `context` parameters only. No `mode` parameter is documented. **Suggested resolution**: Remove `mode: "semantic"` from the recall protocol, or document what MuninnDB API version supports this parameter. If semantic recall is the default behavior of `muninn_recall`, note this explicitly and remove the parameter.

- **IMP-MN-003**: lifecycle.md -- **Cleanup implementation depends on unreliable recall**. The cleanup protocol at Stage 7 uses `muninn_recall(vault: REPO_VAULT, context: "research:*")` to find all research engrams for cleanup. Semantic recall with a wildcard pattern is not guaranteed to return all engrams -- it returns results by relevance score, and older or less-connected engrams may fall below the recall threshold. This means some `research:*` engrams could be silently orphaned and never cleaned up. **Suggested resolution**: Use `muninn_find_by_entity` or `muninn_entities` (both available in the MuninnDB MCP tools) to enumerate all engrams matching the `research:` prefix, rather than relying on semantic recall for exhaustive enumeration.

- **IMP-MN-004**: concept-prefix-extensions.md -- **`decision:*` is listed as an existing prefix in the DEFAULT vault, but 01-workflow-steps/06-graduate.md routes `decision:*` to the REPO vault**. The existing vault-routing rule (`.claude/rules/vault-routing.md`) does not list `decision:*` at all in its write routing table. concept-prefix-extensions.md shows `decision:*` in the DEFAULT vault (line 16). 06-graduate.md writes `decision:bun-ws-close-code-reconnection-map` to `luca-framework` (REPO vault). This is an existing inconsistency in the codebase that this section inherits but does not resolve. **Suggested resolution**: Add `decision:*` explicitly to the vault-routing rule's write routing table with a clear routing decision (REPO for project-scoped decisions, DEFAULT for generalizable decisions, or always one vault). Then update all documents to match.

- **IMP-MN-005**: graduation-model.md -- **Deduplication uses >0.85 similarity threshold but does not specify what "similarity" means**. MuninnDB's `muninn_recall` returns relevance scores, but the document does not clarify whether this is cosine similarity, edit distance, or MuninnDB's internal scoring. The 0.85 threshold is meaningless without knowing the score range and semantics. **Suggested resolution**: Clarify that this refers to MuninnDB's recall relevance score (range 0.0-1.0), or replace with a qualitative instruction ("if the recalled engram covers substantially the same claim, treat as duplicate").

- **IMP-MN-006**: per-task-recall.md -- **`muninn_feedback` is called with `engram_id` as a string concept prefix, but MuninnDB feedback likely expects an actual engram ID** (UUID or internal identifier), not a concept prefix. The call `muninn_feedback(vault: REPO_VAULT, engram_id: "research:approach-ws-reconnect", useful: true)` conflates concept prefix with engram ID. **Suggested resolution**: After recall, capture the engram's actual ID from the recall result and use that for feedback. Document the correct field name from the muninn_feedback tool schema.

## Minor Findings

- **MIN-MN-001**: graduation-model.md -- **Config key inconsistency**. The "Graduation Confidence Threshold" section (line 338) nests config under `"workflow": { "graduation_threshold": 0.55, "graduation_confidence_minimum": "MEDIUM" }`, while the "Configuration" section (line 370) nests under `"workflow": { "graduation": { "threshold": 0.55, "confidence_minimum": "MEDIUM" } }`. These are different JSON paths. **Suggested resolution**: Use the nested `workflow.graduation.*` structure from line 370 consistently, and remove the flat variant.

- **MIN-MN-002**: README.md -- **Step numbering mismatch**. The "Position in the 10-Step Workflow" diagram shows Step 6 as GRADUATION and Step 8 as Execution. But 01-workflow-steps/09-execute.md is labeled "Step 9: Execute", not Step 8. The README's numbering scheme differs from the 01-workflow-steps numbering by at least one step. **Suggested resolution**: Verify the canonical step numbering from 01-workflow-steps/ and update the README diagram to match.

- **MIN-MN-003**: concept-prefix-extensions.md -- **The visual vault map on line 170 shows `decision:*` in the DEFAULT vault, but the promotion section on line 214 shows `research:decision-*` promoting to `decision:*` in DEFAULT vault**. If `decision:*` is supposed to be in the DEFAULT vault, this is consistent. But if project-specific decisions should stay in REPO (as 06-graduate.md suggests), the visual map is wrong. This is a consequence of IMP-MN-004 but worth noting as a second location requiring the fix.

- **MIN-MN-004**: lifecycle.md -- **`cleanup_retain_promoted` config field is confusing**. When `cleanup_retain_promoted: true`, promoted research engrams are "retained" (not cleaned up). But the lifecycle text on line 296 says "IF engram was promoted... -> SAFE TO CLEAN UP (the promoted version persists)." This contradicts the config description on line 449: "If false, even promoted research:* engrams are cleaned up." The default `true` means promoted engrams are *retained* in REPO even though their permanent version exists in DEFAULT -- this is the opposite of what line 296 recommends. **Suggested resolution**: Clarify the field semantics. If `cleanup_retain_promoted: true` means "keep the research:* copy even after promotion," rename to `retain_promoted_source` and explain that this is for audit trail purposes. If it means "only clean up promoted ones" (which is what line 296 suggests), the field semantics are inverted.

- **MIN-MN-005**: graduation-model.md -- **`max_engrams_per_phase: 20` conflicts with graduation-agent.md's `max_engrams_per_graduation: 50`**. Both are configurable caps, but the defaults differ by 2.5x and use different config key names. **Suggested resolution**: Pick one name and one default.

## Backward Compatibility Analysis

The design is **backward compatible with existing MuninnDB usage**. Key evidence:

1. **Existing prefixes unchanged**: The concept-prefix-extensions.md explicitly preserves all existing prefixes (`session:*`, `brain:project-*`, `pattern:*`, `pitfall:*`, `preference:*`, `procedure:*`, `metric:*`, `process:*`, `version:*`, `milestone:*`) with identical vault routing.

2. **New prefix namespace is additive**: `research:*` is a net-new namespace that does not collide with any existing prefix. No existing agent writes to `research:*`, so there is no risk of namespace conflict.

3. **Existing vault-routing rule needs update**: The `.claude/rules/vault-routing.md` write routing table does not include `research:*`. The concept-prefix-extensions.md correctly identifies this gap (line 237) and notes that both the vault-routing rule and the vault-guard rule need updating. This is a required migration step, not a compatibility break.

4. **The `decision:*` prefix gap is pre-existing**: The vault-routing rule does not include `decision:*`, but `decision:*` is used by lu-learner today. This section inherits the gap but does not create it.

5. **Graduation is gated by config**: `workflow.graduation.enabled: true` (default) means existing projects without this config key would get graduation by default. However, graduation only runs if research files exist (Step 4), so projects that skip research are unaffected.

**Risk**: The only backward-compatibility risk is if the vault-routing rule and vault-guard rule are not updated to include `research:*` before the v2 graduation code is deployed. In that case, the vault-guard pre-tool-use hook would flag `research:*` writes as misrouted (falling through to the ambiguity heuristic). This is a deployment sequencing issue, not a design issue.

## Edge Case Analysis

**Graduation produces 0 engrams**: Handled. graduation-model.md (line 399-408) documents the "No Research Files Found" case, where the graduator writes a minimal report and exits. However, there is a gap: what if research files exist but ALL findings score below the threshold? The "No Research Files Found" handler would not fire (files exist), but 0 engrams would be written. The graduation report would show this, but the planner in Step 7 would have no engrams to reference. per-task-recall.md does not address this case -- it assumes engrams exist. **Recommendation**: Add explicit handling for the "all findings below threshold" case: the graduation report should flag this, and the planner should proceed without research refs rather than writing refs that will produce research gaps.

**Recall returns nothing (MuninnDB empty or down)**: Handled. per-task-recall.md (lines 234-282) documents the research gap handling protocol with severity matrix and recovery options. graduation-model.md (lines 412-415) documents the MuninnDB-unavailable fallback (write `RESEARCH-CONTEXT.md` for direct reference). These are reasonable graceful degradation strategies.

**MuninnDB latency under load**: Not addressed. If a phase has 20 engrams and a wave has 5 parallel executors each recalling 3 refs, that is 15 concurrent `muninn_recall` calls. The documentation does not discuss whether MuninnDB can handle this concurrency, whether recalls are cached, or what the timeout behavior is. For local MuninnDB instances this is likely fine; for remote instances, this could be a bottleneck. **Recommendation**: Add a note about expected recall latency and whether the orchestrator should batch recalls before spawning executors (rather than each executor recalling independently).

**Orphaned engrams from interrupted sessions**: Partially addressed. lifecycle.md (line 455-463) mentions multi-session phases and partial research. But if a session crashes after graduation (Step 6) but before execution (Step 8), the research engrams exist in MuninnDB with no plan referencing them. They will sit until milestone cleanup. This is acceptable but should be documented as expected behavior.

**Engram bloat from re-research**: The deduplication mechanism (graduation-model.md Step 3) handles re-research of the same topic within a phase. But if a phase is re-planned (lifecycle.md line 458-459), the new graduation run may create new engrams while old ones from the first graduation still exist. The deduplication check should catch exact duplicates, but partial overlaps could accumulate. The `max_engrams_per_phase` cap is the safety valve here, but it is per-graduation-run, not per-phase-total. **Recommendation**: Clarify whether `max_engrams_per_phase` is cumulative across re-graduations or per-graduation-run.

**Promotion creates cross-vault links**: lifecycle.md Stage 6 (line 258-262) shows `muninn_link` with source in DEFAULT vault and target described as "related engram in DEFAULT vault" with relation "validated_from". But the source research engram is in the REPO vault. `muninn_link` typically operates within a single vault. Cross-vault linking may not be supported. **Recommendation**: Verify whether MuninnDB supports cross-vault links. If not, the link should be within DEFAULT vault only (linking the promoted engram to other DEFAULT vault engrams), and the provenance back to the research engram should be captured in the promoted engram's content text rather than as a graph link.

## Verdict: NEEDS REVISION

The section is architecturally sound and well-motivated. The three-stage memory model, the research:\* namespace separation, and the per-task recall mechanism are all good design decisions. However, the critical contradictions with 04-agent-orchestration/graduation-agent.md and 01-workflow-steps/06-graduate.md (different scoring formula, different concept prefix scheme, different agent identity) must be resolved before this section can serve as an implementation specification. The scoring formula disagreement alone (CRIT-MN-001) would produce different graduation outcomes depending on which document an implementer reads.

**Priority for next iteration**:

1. Resolve CRIT-MN-001 (scoring formula) and CRIT-MN-002 (concept prefix scheme) -- these are blocking
2. Resolve CRIT-MN-003 (agent identity) -- needed for agent registry
3. Address IMP-MN-001 (annotation syntax) and IMP-MN-003 (cleanup reliability) -- needed for implementation
4. Remaining items can be fixed in parallel
