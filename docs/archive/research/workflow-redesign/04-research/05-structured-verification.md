# Research: Learning 5 — Structured Verification Data

> **Date:** 2026-03-31
> **Status:** Research complete
> **Learning:** GSD2 Learning 5 — Structured Verification Data
> **Pipeline scope:** Steps 5i-5j (Harness + Goal-Backward Verification), Step 6 (Milestone Boundary)
> **Cross-references:** [04-stuck-detection.md](./04-stuck-detection.md), [06-deterministic-classification.md](./06-deterministic-classification.md)

## Summary

GSD2 writes `T##-VERIFY.json` files with structured evidence (command, exit code, verdict, duration, blocking status) that enable deterministic milestone validation without LLM interpretation. Luca has a split model: the harness produces structured JSON (`harness-result.json` via `HarnessResultSchema`), but goal-backward verification produces prose (`VERIFICATION.md`). The proposed pipeline should consolidate to structured-first verification throughout, and `state.json` should become the sole source of truth for workflow state, eliminating `STATE.md` as a managed artifact.

## Current State

### What Is Already Structured

The harness verification layer is fully structured:

| Artifact              | Schema                                                         | Location                                       |
| --------------------- | -------------------------------------------------------------- | ---------------------------------------------- |
| `harness-result.json` | `HarnessResultSchema`                                          | `src/harness/__schemas/harness.schemas.ts`     |
| `CheckResult`         | Per-check status, exit code, parsed errors, warnings, duration | Same file                                      |
| `ParsedError`         | File, line, column, message, code, severity                    | Same file                                      |
| `ClassifiedError`     | Fingerprint, source, classification, iterations_seen           | `src/iteration/__schemas/iteration.schemas.ts` |
| `ConvergenceResult`   | Signals, status, consecutive_stale, should_halt                | Same file                                      |

The harness pipeline is exemplary. It demonstrates that structured verification data works in Luca's architecture.

### What Is Still Prose

The goal-backward verification (`lu-verifier` agent, Step 5j/7j) produces `VERIFICATION.md`:

```
VERDICT: PASSED/ISSUES
CRITERIA_MET: N/total
VERIFICATION_PATH: {path}
```

This is pseudo-structured — the output contract in `GOAL_VERIFY_PROMPT` specifies a format, but it's text embedded in an LLM response, not a validated JSON file. The orchestrator must parse this text output to extract the verdict. Problems:

1. **Non-deterministic format.** The LLM might say "PASSED" or "PASS" or "All criteria met" or wrap the output differently.
2. **No machine aggregation.** Milestone boundary check (Step 6) requires an LLM to read all VERIFICATION.md files and synthesize a milestone-level verdict.
3. **No convergence tracking.** The outer implementation loop (5h-5k) cannot programmatically compare verification results across iterations because the data is prose.
4. **No T1/T3 conflict detection from data.** The verification tribunal (`src/agents/__helpers/verification-tribunal.ts`) already has `detectT1T3Conflict()` which takes structured T1 and T3 statuses, but the T3 status must be manually extracted from VERIFICATION.md prose.

### STATE.md vs state.json

The codebase has a dual-write system:

- `state.json` — typed state machine, written by `luca-bridge` transitions
- `STATE.md` — human-readable markdown snapshot, generated by `luca-bridge snapshot`

The `state-machine-bridge.md` rule documents a dual-write guarantee: "The bridge always writes to BOTH the typed state machine AND STATE.md." All skills are instructed to use the bridge as primary with STATE.md as fallback.

This dual-write model:

- Doubles write operations on every state transition
- Creates inconsistency risk (STATE.md may lag state.json if a write partially fails)
- Requires all skills to handle two formats
- Exists for backward compatibility during migration

## Proposed Changes

### 1. Structured Verification Output Schema

Define a new `PhaseVerificationResult` schema that the lu-verifier agent writes as JSON:

```typescript
// Proposed: src/verification/__schemas/verification.schemas.ts

const CriterionResultSchema = z.object({
  /** Criterion ID from PLAN.md (e.g., "SC-1", "SC-2") */
  criterion_id: z.string(),
  /** The criterion text from the plan */
  description: z.string(),
  /** Whether this criterion was met */
  met: z.boolean(),
  /** Evidence supporting the assessment */
  evidence: z.string(),
  /** Files that demonstrate criterion completion */
  evidence_files: z.array(z.string()).default([]),
  /** If not met: what specific gap remains */
  gap: z.string().optional(),
  /** Whether this criterion blocks phase completion */
  blocking: z.boolean().default(true),
});

const PhaseVerificationResultSchema = z.object({
  /** Phase number */
  phase: z.number().int().positive(),
  /** Overall verdict */
  verdict: z.enum(["passed", "partial", "failed"]),
  /** Number of criteria met */
  criteria_met: z.number().int().nonnegative(),
  /** Total number of criteria evaluated */
  criteria_total: z.number().int().nonnegative(),
  /** Per-criterion results */
  criteria: z.array(CriterionResultSchema),
  /** Blocking gaps (criteria not met where blocking: true) */
  blocking_gaps: z.array(z.string()).default([]),
  /** ISO 8601 timestamp */
  timestamp: z.string(),
  /** Duration of verification in milliseconds */
  duration_ms: z.number().int().nonnegative().optional(),
});
```

The verifier agent would write this to `.planning/phases/{NN}-{desc}/verification-result.json` instead of (or alongside) `VERIFICATION.md`.

### 2. Verification Agent Prompt Change

The `GOAL_VERIFY_PROMPT` in `agent-prompts.ts` currently instructs the agent to:

```
5. Write VERIFICATION.md to the phase directory with findings
6. Determine overall verdict: PASSED (all criteria met) or ISSUES (gaps found)
```

Change to:

```
5. Write verification-result.json to the phase directory using this exact schema:
   { phase, verdict, criteria_met, criteria_total, criteria: [...], blocking_gaps: [...], timestamp }
6. Each criterion from PLAN.md's success criteria gets a CriterionResult entry
7. Optionally write VERIFICATION.md as a human-readable prose summary derived from the JSON
```

The output contract changes from:

```
VERDICT: PASSED/ISSUES
CRITERIA_MET: N/total
VERIFICATION_PATH: {path}
```

To:

```
VERIFICATION_JSON: {path to verification-result.json}
VERDICT: passed/partial/failed
BLOCKING_GAPS: N
```

### 3. Deterministic Milestone Validation

With structured verification data, milestone boundary check (Step 6) becomes deterministic:

```typescript
// Deterministic milestone validation — no LLM needed
function validateMilestone(
  phaseResults: PhaseVerificationResult[],
): MilestoneValidation {
  const allPassed = phaseResults.every((r) => r.verdict === "passed");
  const totalCriteria = phaseResults.reduce(
    (sum, r) => sum + r.criteria_total,
    0,
  );
  const metCriteria = phaseResults.reduce((sum, r) => sum + r.criteria_met, 0);
  const blockingGaps = phaseResults.flatMap((r) => r.blocking_gaps);

  return {
    milestone_passed: allPassed,
    phases_passed: phaseResults.filter((r) => r.verdict === "passed").length,
    phases_total: phaseResults.length,
    criteria_met: metCriteria,
    criteria_total: totalCriteria,
    blocking_gaps: blockingGaps,
  };
}
```

This replaces the current Step 8 pattern where the orchestrator spawns milestone agents to interpret prose summaries. The orchestrator reads JSON files, aggregates mechanically, and makes the milestone decision without token cost.

### 4. Convergence Tracking for Goal Verification

With structured verification results, the outer implementation loop (5h-5k) can track verification convergence:

```typescript
// After each verification iteration:
const currentCriteria = new Set(
  currentResult.criteria.filter((c) => !c.met).map((c) => c.criterion_id),
);
const previousCriteria = new Set(
  previousResult.criteria.filter((c) => !c.met).map((c) => c.criterion_id),
);

// Jaccard overlap of failing criteria
const intersection = [...currentCriteria].filter((id) =>
  previousCriteria.has(id),
);
const union = new Set([...currentCriteria, ...previousCriteria]);
const criteriaOverlap = union.size === 0 ? 0 : intersection.length / union.size;

// If same criteria failing across iterations, verification is stalled
if (criteriaOverlap >= 0.8) {
  // Same gaps persist — stall detected at verification level
}
```

This ties directly to Learning 4 (Stuck Detection): structured verification enables convergence detection for the goal-backward loop, not just the harness loop.

### 5. T1/T3 Conflict Detection From Data

The verification tribunal (`src/agents/__helpers/verification-tribunal.ts`) already has `detectT1T3Conflict()` which takes typed T1 and T3 statuses. With structured verification:

- T1 status comes from `HarnessResult.status` (already structured)
- T3 status comes from `PhaseVerificationResult.verdict` (now structured)
- T1 evidence comes from `HarnessResult.checks` summary (already structured)
- T3 evidence comes from `PhaseVerificationResult.blocking_gaps` (now structured)

No LLM parsing needed to invoke the tribunal.

### 6. STATE.md Elimination

With all verification data in JSON and state.json as the typed state machine:

**Phase 1 (immediate):** STATE.md becomes a read-only derived view. `luca-bridge snapshot` generates it from state.json on demand. No skill reads STATE.md for decisions.

**Phase 2 (after migration):** STATE.md generation becomes optional. It exists only as a human debugging aid, not a managed artifact. The dual-write guarantee is removed. Skills that currently fall back to STATE.md are updated to use the bridge exclusively.

**Phase 3 (eventual):** STATE.md is no longer generated. `state.json` is the sole source of truth. `luca-bridge read-status` is the only way to query workflow state.

## Claude Code Constraints

### Agent Output Parsing

Claude Code agents return text output, not structured data. When the verifier agent writes `verification-result.json`, the orchestrator needs to:

1. Instruct the agent to write the JSON file to disk (via the Write tool)
2. Read the file after the agent completes (via `cat` or `bun -e "..."`)
3. Parse and validate the JSON

This is already the pattern used for `harness-result.json`. The harness runner writes structured JSON to `.planning/harness-result.json`, and the orchestrator reads it.

**Risk:** The LLM agent might write invalid JSON. Mitigation: the schema includes defaults and the orchestrator uses `safeParse` with a prose-fallback path.

### Prose as Fallback, Not Primary

Even with JSON-first verification, the verifier agent may need to produce a prose summary for human readability. The approach:

1. **Primary:** Write `verification-result.json` (machine-consumable)
2. **Secondary:** Optionally derive `VERIFICATION.md` from the JSON (human-readable)
3. **Fallback:** If JSON write fails, the orchestrator falls back to parsing the agent's text output for VERDICT/CRITERIA_MET (current behavior)

### File-Based State Transfer

Claude Code has no inter-agent communication channel. State transfer happens via files on disk. This is compatible with structured verification: each agent writes its result as a JSON file, and the next agent (or the orchestrator) reads it.

The context file (`/tmp/lu-context.json`) already serves this purpose for orchestrator state. Verification results extend this pattern to per-phase artifacts.

## Schema Design Considerations

### Criterion IDs

PLAN.md success criteria need stable identifiers so verification results can track them across iterations. The proposed `criterion_id` field (e.g., "SC-1", "SC-2") maps to success criteria in the plan.

**Impact on planner:** The `lu-planner` agent (Step 7g) should be instructed to assign IDs to success criteria in PLAN.md. This is a prompt change.

### Verdict Granularity

GSD2 uses a binary pass/fail. The proposed schema uses three levels:

- `passed`: All blocking criteria met
- `partial`: Some criteria met, some blocking gaps remain
- `failed`: No criteria met or fundamental failure

`partial` is important for convergence tracking: a phase that goes from `failed` to `partial` is making progress even if not complete.

### Evidence Files

The `evidence_files` array in `CriterionResult` lists files that demonstrate criterion completion. This serves two purposes:

1. **Auditability:** Humans can review exactly what the verifier checked
2. **Convergence input:** If the same evidence files appear across iterations but the criterion remains unmet, the gap is likely in the verification criteria, not the implementation (relates to T1/T3 conflict detection)

### Duration Tracking

The `duration_ms` field enables performance monitoring of verification. If verification consistently takes 60+ seconds per phase, it signals an optimization opportunity (scope reduction, parallel verification, etc.).

## Interaction With Other Learnings

### Learning 4 (Stuck Detection)

Structured verification is a prerequisite for verification-level stuck detection. Without structured criteria results, the outer implementation loop cannot programmatically compare verification outcomes across iterations. See the convergence tracking section above.

The stall detector's fingerprint mechanism works on error objects. With structured verification, each unmet criterion becomes an "error" for convergence purposes:

```
fingerprint = hash(criterion_id + gap_description)
```

This reuses the existing convergence infrastructure for a new signal type.

### Learning 6 (Deterministic Classification)

Structured verification results become an input signal for adaptive complexity classification. If a phase's verification shows:

- Many criteria (criteria_total > 5): suggests COMPLEX+
- Multiple blocking gaps after first execution: suggests undercomplexified
- criteria_met/criteria_total ratio: measures execution quality at current complexity

This data can feed the routing history that Learning 6 proposes, enabling the deterministic classifier to adjust future routing based on verification outcomes.

### Learning 9 (State is Data, Not Documents)

Learning 5 and Learning 9 are the same principle applied to different artifacts:

- Learning 5: Verification output should be JSON, not prose
- Learning 9: Workflow state should be JSON, not markdown

They share the same rationale (LLM interpretation costs tokens, introduces non-determinism, and blocks mechanical aggregation) and the same migration strategy (JSON as primary, prose as derived view, eventual prose elimination).

## Risks and Tradeoffs

### Adopting

| Risk                                                    | Mitigation                                                                                                                              |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Verifier agent might write invalid JSON                 | `safeParse` with fallback to prose parsing; Zod schema with defaults                                                                    |
| Loss of nuanced prose in VERIFICATION.md                | Keep prose generation as optional secondary output; structured data captures the machine-actionable parts, prose captures the reasoning |
| Planner must assign criterion IDs                       | Simple prompt change; IDs can be auto-generated (SC-1, SC-2, ...)                                                                       |
| Migration effort for existing VERIFICATION.md consumers | Verification results are per-phase, new phases use JSON, old phases retain prose                                                        |
| STATE.md elimination breaks backward compat             | Phased rollout with fallback periods; most skills already use bridge as primary                                                         |

### Not Adopting

| Risk                                             | Impact                                                                                    |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| Milestone validation requires LLM interpretation | Tokens wasted on aggregation that could be mechanical; non-deterministic verdicts         |
| No verification convergence tracking             | Outer implementation loop cannot detect goal-verification stalls (see Learning 4)         |
| T1/T3 conflict detection requires text parsing   | Tribunal activation is fragile; depends on orchestrator correctly extracting verdict text |
| STATE.md/state.json inconsistency risk persists  | Dual-write overhead continues; skills must handle two formats indefinitely                |
| Parked phase diagnostics are prose-only          | Developer cannot programmatically query "which criteria failed across all parked phases?" |

## Recommendation

**Adopt in phases.**

**Phase 1 (immediate, low effort):**

- Define `PhaseVerificationResultSchema` and `CriterionResultSchema` in a new file under `src/verification/__schemas/`
- Update `GOAL_VERIFY_PROMPT` to write `verification-result.json`
- Keep `VERIFICATION.md` generation as optional secondary output
- Orchestrator reads JSON for verdict, falls back to prose parsing

**Phase 2 (after stuck detection is wired, medium effort):**

- Wire verification-result.json into outer loop convergence tracking
- Wire T1/T3 conflict detection to read from structured data
- Deterministic milestone validation replaces LLM-based milestone agents

**Phase 3 (after all skills use bridge, lower priority):**

- STATE.md becomes read-only derived view
- Remove dual-write guarantee from bridge
- Eventual STATE.md elimination
