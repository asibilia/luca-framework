# Plan 17-04: ComplexityGate Extension & Verifier Enhancement

## Objective

Extend the existing complexity gating system with `verifyFixIterations` limits for Loop B (semantic gap iteration), add the `iteration` configuration section to `.planning/config.json`, add `source_plan` field to the verifier gap output and result envelope for per-plan gap attribution, and update the complexity-gating rule documentation. These are prerequisite modifications to existing modules that the orchestrator loop protocol (Plan 17-05) depends on.

## Context

- **Types from Plan 17-01:** `src/iteration/types.ts` (IterationConfig, IterationMode, LoopType)
- **ComplexityGate interface:** `src/complexity/types.ts` (line 66-92, has `harnessFixIterations` but no `verifyFixIterations`)
- **Complexity defaults:** `src/complexity/defaults.ts` (DEFAULT_COMPLEXITY_MATRIX with current harness values)
- **Result envelope:** `src/context/result-envelope.ts` (resultIssueSchema has `source_agent` but no `source_plan`)
- **Verifier agent:** `src/agents/general/lu-verifier.agent.ts` (gap YAML has truth/status/reason/artifacts/missing but no source_plan)
- **Config file:** `.planning/config.json` (has harness and complexity sections, no iteration section)
- **Complexity gating rule:** `.claude/rules/complexity-gating.md` (matrix table missing verifyFixIterations row)
- **Locked decisions:** 17-CONTEXT.md Decision 5 (verifyFixIterations defaults: TRIVIAL=0, SIMPLE=1, MODERATE=1, COMPLEX=2, CRITICAL=3)
- **Locked decisions:** 17-CONTEXT.md Decision 3 (default AFK mode, config.json iteration section)
- **Refinement R2:** Verifier gap-to-plan attribution via `source_plan` field

## Design Decisions Applied

1. **verifyFixIterations in ComplexityGate**: Limits stay in ComplexityGate alongside harnessFixIterations. Lower defaults because semantic gaps are harder and costlier to auto-fix.
2. **source_plan in result envelope**: Enables Loop B to identify which plans have gaps and re-execute only those. Added as optional field on resultIssueSchema.
3. **source_plan in verifier gap YAML**: Each gap includes the plan number it traces to, leveraging Specification Anchoring from Phase 14.
4. **iteration config section**: New top-level section in config.json with default_mode, soft_stop_percent, stale_threshold, promotion_threshold.
5. **Backward compatibility**: All new fields are optional or have defaults. Existing config.json files and agent outputs continue to work without modification.

### Task 4: Add iteration config section to config.json

**Goal:** Add the `iteration` configuration section to `.planning/config.json` for controlling loop behavior.

**File:** `.planning/config.json` (modify)

Add a new top-level `iteration` section after the `complexity` section:

```json
{
  "iteration": {
    "default_mode": "afk",
    "soft_stop_percent": 80,
    "stale_threshold": 2,
    "promotion_threshold": 3
  }
}
```

**Property descriptions:**

- `default_mode`: Default iteration mode ("afk" or "hitl"). AFK runs loops autonomously; HITL pauses after each iteration for human decision. Default: "afk".
- `soft_stop_percent`: Percentage of max iterations at which the soft stop triggers. Finish current iteration but don't start a new one. Default: 80.
- `stale_threshold`: Number of consecutive stale iterations (2-of-3 no-progress rule) before halting the loop. Default: 2.
- `promotion_threshold`: Number of unchanged iterations before a correctable error is promoted to permanent. Default: 3.

**Also in the same file edit**, add `verifyFixIterations` to each level in the `complexity.matrix` section to match the defaults from Task 2.
