# 43-01: Profile Directory Structure, Config Toggle, Migrate TS-Specific Rules

## Objective

Establish the tech stack guideline profile infrastructure (STACK-01), migrate all TypeScript-specific rules into a `typescript` profile (STACK-02), and add the config toggle for opinionated guidelines (STACK-03). After this plan, rules are organized under named profiles, the typescript profile contains all current TS-specific rules, and a config toggle controls whether opinionated guidelines are included.

## Context

### Current Architecture

- All 19 rules live flat in `src/rules/general/` regardless of whether they are language-specific or framework-level
- The rule registry in `src/rules/index.ts` statically imports every rule and exports a flat `ruleRegistry: Record<string, () => BaseRule>`
- The build pipeline (`scripts/build-shared.ts` > `generateRuleOutputs()`) iterates the `ruleRegistry` and compiles every rule to `.claude/rules/` and `.cursor/rules/`
- Rules extend `BaseRuleImpl` (from `src/rules/base/base-rule.ts`) which implements the `BaseRule` interface
- `RuleConfig` has `frontmatter` (description, globs, alwaysApply) and `sections` (title, content, order)
- Config lives in `.planning/config.json` with `workflow`, `harness`, `dogfood`, etc. sections
- The dogfood config specifies `source: "src/"` and `outputs: [".claude/", ".cursor/"]`

### Rule Classification

**Language-agnostic framework rules (remain in `src/rules/general/`):**

- `complexity-gating` (workflow complexity levels)
- `harness-verification` (harness/hook boundary)
- `hook-skill-boundary` (hook vs skill decision)
- `state-machine-bridge` (state machine CLI reference)
- `mandatory-documentation` (doc requirements)
- `file-naming` (kebab-case convention)
- `cursor_rules` (Cursor rule formatting)
- `self_improve` (rule improvement guidelines)
- `atlassian-mcp` (Jira integration patterns)
- `posthog-integration` (analytics patterns)

**Framework rule (lives at `src/rules/lu-workflow.rule.ts`, not in general/):**

- `lu-workflow` (Luca workflow system)

**TypeScript/JS-specific rules (migrate to `src/rules/profiles/typescript/`):**

- `import-standards` (TS/JS import organization)
- `schema-first-parsing` (Zod schema patterns)
- `no-classes` (functional patterns, TS-specific)
- `lodash-preference` (lodash over built-in JS)
- `api-snake-case` (API payload conventions with Zod/TS examples)
- `bun-preference` (Bun runtime for TS/JS)
- `use-bun-instead-of-node-vite-npm-pnpm` (Bun over Node/npm/vite)
- `functional-api-reuse` (functional architecture, TS examples)

### Design Decisions

1. **Profile = directory + registry entry**: Each profile is a subdirectory under `src/rules/profiles/` with its own `index.ts` exporting a `TechStackProfile` object. This keeps profiles self-contained and discoverable.
2. **Config toggle**: `workflow.opinionated_guidelines: true` (default) includes profile rules. When `false`, only framework rules are compiled.
3. **Profile selection**: `workflow.tech_stack_profiles: ["typescript"]` selects which profiles are active. Defaults to `["typescript"]` for backward compatibility.
4. **Backward compatibility**: With default config, the build output is identical to the current build (all rules compiled). No existing behavior changes.
5. **Flat output preserved**: Compiled rules still go to `.claude/rules/` and `.cursor/rules/` without subdirectories. Profile organization is source-only.

### T6: Update Rule Registry for Profile-Aware Loading

**Goal:** Refactor `src/rules/index.ts` to dynamically build the rule registry from general rules + active profile rules.

**Files to modify:**

- `src/rules/index.ts`

**Steps:**

1. Remove the 8 TS-specific imports from the static import block
2. Keep the 11 general/framework rule imports
3. Import `profileRegistry` from `./profiles/index`
4. Read config to determine active profiles (or use defaults)
5. Build `ruleRegistry` by:
   - Starting with general rules (always included)
   - Adding `lu-workflow` rule (always included)
   - If `opinionated_guidelines` is true (default), iterate `tech_stack_profiles` and merge each profile's rules into the registry
6. Export the same `ruleRegistry: Record<string, () => BaseRule>` interface so build-shared.ts needs no changes

**Implementation pattern:**

```typescript
import { profileRegistry } from "./profiles/index";

// General rules (always included)
const generalRules: Record<string, () => BaseRule> = {
  "atlassian-mcp": () => new AtlassianMcpRule(),
  "complexity-gating": () => new ComplexityGatingRule(),
  // ... all 11 general rules
  "lu-workflow": () => new LuWorkflowRule(),
};

// Build profile-aware registry
function buildRuleRegistry(): Record<string, () => BaseRule> {
  const registry = { ...generalRules };

  // Read config for profile settings
  // Default: opinionated_guidelines=true, tech_stack_profiles=["typescript"]
  const config = readProfileConfig();

  if (config.opinionated_guidelines) {
    for (const profileName of config.tech_stack_profiles) {
      const profile = profileRegistry[profileName];
      if (profile) {
        Object.assign(registry, profile.rules);
      }
    }
  }

  return registry;
}

export const ruleRegistry = buildRuleRegistry();
```

**Verification:**

- [ ] With default config: ruleRegistry contains all 19 rules (11 general + 8 typescript)
- [ ] With `opinionated_guidelines: false`: ruleRegistry contains only 11 general rules
- [ ] With `tech_stack_profiles: []`: ruleRegistry contains only 11 general rules
- [ ] TypeScript compilation passes
- [ ] Existing consumers of ruleRegistry (build-shared.ts, check-drift.ts) work unchanged
