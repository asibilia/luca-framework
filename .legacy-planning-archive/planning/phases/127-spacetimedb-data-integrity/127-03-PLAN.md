# Phase 127 Plan 03: Singleton Table Unique Constraints

## Task Objective

Add unique constraints to singleton SpacetimeDB tables to prevent
accidental duplicate rows that break the singleton pattern.

## Context

- Issue #48: Add unique constraints to singleton SpacetimeDB tables
- Singleton tables (e.g., `workflow_state`, `sessions`) should have exactly one row
- Without constraints, bugs can create duplicate singleton rows
- This causes application state inconsistency

## Files to Read

- `packages/luca-spacetime/spacetimedb/src/schema.ts` - All table definitions

## Files to Update

1. `packages/luca-spacetime/spacetimedb/src/schema.ts` - Add unique constraints

## Execution Steps

1. **Identify singleton tables:**
   - Tables that should have exactly one row
   - Typically identified by a fixed ID (e.g., `id=1`)
   - Examples: `workflow_state`, configuration tables

2. **Add unique constraints:**
   - Add unique index on the primary identifier column
   - For tables with `id: t.u64().primaryKey()`, ensure `const` or unique constraint
   - Document singleton pattern in table comments

3. **Update reducers:**
   - Ensure reducers use upsert pattern for singleton tables
   - Use `ctx.db.table.filter(...).update(...)` instead of insert
   - Add guards to prevent duplicate inserts

## Verification

- [ ] Singleton tables have unique constraints on ID field
- [ ] Reducers use upsert pattern (not insert) for singleton tables
- [ ] Tests verify constraint prevents duplicate singleton rows
- [ ] Application logic enforces singleton pattern (id=1)

## Success Criteria

- Singleton tables cannot have duplicate rows
- Database schema enforces singleton pattern
- Application reducers respect singleton constraints
