# Phase 140.1: Memory Effectiveness Measurement - Research

**Researched:** 2026-03-10
**Domain:** MuninnDB feedback instrumentation, memory metrics, recall effectiveness
**Confidence:** HIGH

## Summary

This research investigates how to instrument MuninnDB feedback at the verification boundary, track applied vs ignored engrams, compute recall effectiveness metrics, and surface memory health in progress reports.

The codebase already has the complete deferred recall infrastructure (`recall-cache.ts`, `memory-context-builder.ts`, `session-digest.ts`) and a process metrics pattern (`lu-process-data` agent + MuninnDB metric engrams). The MuninnDB `muninn_feedback` tool exists but is **never called anywhere in `src/`** -- confirmed via exhaustive grep. The key gap is that `RecallCacheEntry` stores recalled content as plain strings but does not preserve engram IDs, which are required for the feedback API.

**Primary recommendation:** Extend `RecallCacheEntry` to store engram IDs alongside content strings, wire `muninn_feedback` calls into phase-execute after verification (Step 7 → Step 7.1), and follow the existing `lu-process-data` pattern for memory metrics computation.

### Pattern 1: Engram ID Tracking in Recall Cache

**What:** Extend `RecallCacheEntry` to store structured objects (with IDs) instead of plain strings.
**When to use:** Any time engram IDs need to flow from recall → execution → feedback.

Current structure (recall-cache.ts line 37-50):

```typescript
// CURRENT: Plain strings, no engram IDs
export const RecallCacheEntrySchema = z.object({
  sessionId: z.string().min(1),
  patterns: z.array(z.string()).default([]),
  decisions: z.array(z.string()).default([]),
  pitfalls: z.array(z.string()).default([]),
  findings: z.array(z.string()).default([]),
  recalledAt: z.string(),
});
```

Recommended extension:

```typescript
// NEW: Structured recall item with engram ID
export const RecalledEngramSchema = z.object({
  engramId: z.string().min(1),
  content: z.string(),
  concept: z.string().optional(),
  confidence: z.enum(["low", "medium", "high"]).optional(),
});

export type RecalledEngram = z.infer<typeof RecalledEngramSchema>;

// EXTENDED: Both strings (backward compat) and structured items
export const RecallCacheEntrySchema = z.object({
  sessionId: z.string().min(1),
  patterns: z.array(z.string()).default([]),
  decisions: z.array(z.string()).default([]),
  pitfalls: z.array(z.string()).default([]),
  findings: z.array(z.string()).default([]),
  // NEW: Structured recall items with IDs for feedback
  recalledEngrams: z.array(RecalledEngramSchema).default([]),
  recalledAt: z.string(),
});
```

This preserves backward compatibility (patterns/decisions/pitfalls arrays remain for formatting) while adding the structured `recalledEngrams` array for feedback tracking.

### Pattern 4: Metrics as MuninnDB Engrams

**What:** Store memory effectiveness metrics as `metric:memory-*` engrams in MuninnDB.
**When to use:** Following the existing lu-process-data pattern for metric storage.

The milestone-complete skill already recalls `metric:appetite-accuracy`, `metric:rework-ratio`, `metric:signal-rate`, and `metric:convergent-streak` from MuninnDB. Memory metrics follow the same pattern:

```
metric:memory-recall-precision-{milestone}-phase-{phase}
metric:memory-hit-rate-{milestone}-phase-{phase}
metric:memory-roi-{milestone}-phase-{phase}
metric:memory-stale-pct-{milestone}-phase-{phase}
metric:memory-confidence-calibration-{milestone}-phase-{phase}
```

### Anti-Patterns to Avoid

- **DO NOT store memory metrics in the observability scorecard**: The scorecard tracks per-agent invocations (T1 domain). Memory metrics are cross-cutting (T0 domain) and should be MuninnDB engrams.
- **DO NOT modify the `buildMemoryContextBlock` return type**: Consumers expect a plain string. Token estimation should be a separate export, not baked into the return value.
- **DO NOT call `muninn_feedback` for session findings**: Only recalled long-term engrams (patterns, decisions, pitfalls) get feedback. Session findings are ephemeral.

## Don't Hand-Roll

| Problem                  | Don't Build                   | Use Instead                                              | Why                                                                        |
| ------------------------ | ----------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------- |
| Token estimation         | Custom tokenizer              | Existing `estimateTokens()` in memory-context-builder.ts | Already in use, ~4 chars/token is standard rough estimate                  |
| Metric storage           | Custom metric store           | MuninnDB `metric:*` engrams                              | Pattern established by lu-process-data, milestone-complete                 |
| Engram confidence lookup | Parse engram content manually | MuninnDB `muninn_read` + content parsing                 | Engram content includes "Confidence: High/Medium/Low" as text              |
| Stale memory detection   | Custom staleness logic        | MuninnDB `muninn_recall` + feedback count analysis       | Feedback history already tracked by MuninnDB after `muninn_feedback` calls |

**Key insight:** MuninnDB's `muninn_feedback` API already updates the vault's "learned scoring weights via SGD" (from the tool description). The system auto-adjusts recall ranking based on feedback. The planner should not build custom scoring adjustments -- just wire feedback calls and let MuninnDB's SGD do the heavy lifting.

## Common Pitfalls

### Pitfall 1: Engram IDs Not Available at Recall Time

**What goes wrong:** MuninnDB `muninn_recall` returns engram content but the ID extraction depends on the recall response format. If IDs aren't parsed correctly, feedback becomes impossible.
**Why it happens:** The recall response is processed by the LLM at the skill level (phase-execute), not by TypeScript code. The LLM may not extract engram IDs consistently.
**How to avoid:** Add explicit instructions in phase-execute to parse and store engram IDs from `muninn_recall` response. Use a structured extraction template.
**Warning signs:** `recalledEngrams` array is always empty despite non-empty patterns/decisions/pitfalls arrays.

### Pitfall 2: Feedback Determination Logic Too Complex

**What goes wrong:** Trying to precisely determine which engrams were "applied" vs "ignored" requires deep semantic analysis of executor output, which is unreliable.
**Why it happens:** An LLM can reference a pattern implicitly without naming it, or follow a pitfall avoidance strategy without acknowledging it.
**How to avoid:** Use a simpler heuristic: if verification passed AND engram was recalled, mark as `useful: true`. If verification failed OR engram was recalled but the executor explicitly contradicted it, mark as `useful: false`. Start simple, refine later.
**Warning signs:** All feedback is `useful: true` (no signal) or all `useful: false` (too strict).

### Pitfall 3: Token Cost Tracking Adds Overhead

**What goes wrong:** Detailed per-agent token cost tracking bloats session findings and adds context pressure.
**Why it happens:** Memory context blocks are generated for every sub-agent spawn. Logging each one individually is noisy.
**How to avoid:** Track ONE aggregate `memory_tokens_injected` number per phase, not per sub-agent. Compute it once after all waves complete, before feedback.
**Warning signs:** Session findings dominated by token tracking entries.

### Pitfall 4: Backward Compatibility Breaking

**What goes wrong:** Changing `RecallCacheEntry` schema breaks existing code that expects plain string arrays.
**Why it happens:** `setCachedRecall` is called by skills at the LLM level (not compiled TypeScript), so schema changes affect prompt instructions.
**How to avoid:** The new `recalledEngrams` field has `.default([])`, making it optional. Existing callers that don't populate it continue to work. Memory-context-builder.ts still reads from patterns/decisions/pitfalls arrays.
**Warning signs:** `requestMemoryContext()` returns empty string despite populated cache.

### Pitfall 5: Circular Dependency Between Feedback and Scoring

**What goes wrong:** lu-cognition uses feedback data to adjust scoring, but feedback data comes from engrams scored by lu-cognition. This creates a feedback loop that could amplify biases.
**Why it happens:** High-scoring engrams get recalled more → get more feedback → score even higher (or lower).
**How to avoid:** MuninnDB's SGD-based scoring already handles this (gradient descent naturally dampens). For lu-cognition's composite scoring, add the feedback bonus/penalty as a SMALL weight (0.05-0.10), not a dominant signal.
**Warning signs:** Same 3-5 engrams recalled for every phase; new engrams never surface.

## Open Questions

1. **MuninnDB recall response format:**
   - What we know: The LLM processes recall results and populates the cache. Engram IDs are in the response.
   - What's unclear: Exactly how engram IDs appear in the recall response (MuninnDB returns them, but the LLM parsing step may lose them).
   - Recommendation: Add explicit extraction instructions in phase-execute Step 4 recall processing. Parse `id` field from each recall result entry.

2. **Feedback granularity -- per-engram vs per-category:**
   - What we know: `muninn_feedback` operates on individual engram IDs.
   - What's unclear: Whether to call feedback for EVERY recalled engram (could be 5-10 calls) or batch by category (patterns applied → all pattern engrams useful).
   - Recommendation: Call feedback for every recalled engram. The overhead is minimal (simple API calls), and per-engram granularity is more valuable for SGD scoring updates.

3. **Memory ROI denominator:**
   - What we know: `memory_token_ratio = memory_tokens / total_phase_tokens`. Total phase tokens are not currently tracked.
   - What's unclear: Whether to estimate total phase tokens or just use memory tokens as absolute cost.
   - Recommendation: Start with absolute memory token cost per phase. ROI can be computed later when total phase cost tracking exists (potentially via appetite budget data).
