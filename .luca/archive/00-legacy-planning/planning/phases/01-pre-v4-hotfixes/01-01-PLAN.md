# Phase 01 Plan 01: Fix MuninnDB Orphan Ratio

## Objective

Stop MuninnDB engrams from being created as orphans (no links). Lu-learner writes memories but never calls `muninn_link`, so every engram sits disconnected in the graph. Workflow-save has Step 5 linking documentation but the LLM skips it because it reads as optional. This plan inserts a `link_memories` step into lu-learner and a blocking hard gate into workflow-save to enforce linking at both call sites.

## Tasks

### 1. Insert `link_memories` step into lu-learner

**Type:** auto
**TDD:** false
**Depends on:** none

In `src/agents/general/lu-learner.agent.ts`, insert a new `<step name="link_memories">` block between the closing `</step>` of `write_memory` (line 445) and the opening `<step name="clear_working">` (line 447).

The step must instruct the LLM to:

1. Capture the ID returned by each `muninn_remember` call in `write_memory`. Include a self-healing fallback: if the ID was not captured, use `muninn_recall` on the concept name to retrieve it.
2. For each new engram, recall the top 2-3 semantically related existing memories via `muninn_recall` using the concept domain as context.
3. Call `muninn_link` to connect the new memory to each related result using `relates_to`.
4. If the producing phase or session memory ID is known, call `muninn_link` with `learned_from`.
5. Assert a minimum: at least 1 link per new memory. Zero links is an explicit failure condition.
6. Log: "Linked N new memories, M total links created."

The step content must use the relation types already established in workflow-save Step 5: `learned_from`, `relates_to`, `is_part_of`.

**Files to edit:**

- `src/agents/general/lu-learner.agent.ts`

**Verification:**

- The new `<step name="link_memories">` block appears between `</step>` (write_memory) and `<step name="clear_working">` in the file
- The step references both `muninn_recall` (for ID recovery fallback) and `muninn_link` (for linking)
- The step includes the minimum-link assertion ("Zero links is a failure condition")
- The step includes the `learned_from` relation for phase/session linking
- No other steps are modified or removed

### 2. Insert hard gate into workflow-save Step 5

**Type:** auto
**TDD:** false
**Depends on:** none

In `src/skills/general/workflow-save.skill.ts`, insert a hard gate paragraph inside `### Step 5: Link related memories`, after the linking priorities list (line ~219) and before the `### Step 6: Confirm` heading (line ~221).

The gate must:

1. Use imperative blocking language — "Do NOT proceed to Step 6 until..."
2. Specify a concrete, verifiable threshold: N links where N equals the number of memories stored in Step 4
3. Include a minimum-viable fallback for time-constrained situations: link each memory to the session memory via `is_part_of`
4. Be bold/prominent so it is not skipped (`**HARD GATE**` prefix)

The gate must not alter the existing Step 5 relation type table or linking priorities list — it appends to the section.

**Files to edit:**

- `src/skills/general/workflow-save.skill.ts`

**Verification:**

- The `**HARD GATE**` paragraph appears inside Step 5, between the linking priorities list and the `### Step 6:` heading
- The gate specifies N as "equal to the number of memories stored in Step 4" (not a hardcoded number)
- The fallback `is_part_of` path is included
- Step 6 heading and content are unchanged
- No other steps are modified
