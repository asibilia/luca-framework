# Phase 198: Research — Hook Pipeline Trace

## Key Finding: Two Separate Hook Deployment Paths

### Path 1: Dogfood (this repo) — Canonical Registry

```
src/hooks/__helpers/hook-registry.ts (canonical registry)
  → src/hooks/__helpers/config-generators.ts (generateClaudeHooksConfigFromCanonical)
    → scripts/build-shared.ts (generates ".claude/settings.json__hooks" fragment)
      → scripts/build-compile.ts (merges fragment into settings.json template)
        → scripts/build-deploy.ts (resolves EJS → .claude/settings.json)
```

**The canonical registry is the source of truth for `.claude/settings.json`.**

The generator (`config-generators.ts:64-65`) hardcodes `type: "command"` for ALL hook entries. There is NO support for `type: "prompt"` hooks.

### Path 2: User Projects — settings-hooks.json Template

```
packages/luca-framework/templates/hooks/settings-hooks.json
  → luca init (init.ts buildProposedHooksFromDeployed)
    → user's .claude/settings.json
```

The `settings-hooks.json` template is a SEPARATE, smaller set of hooks used by `luca init` for user project deployment. It contains fewer hooks than the canonical registry.

## CanonicalHookSchema Analysis

```typescript
// src/hooks/__schemas/hook.schemas.ts
export const CanonicalHookSchema = z.object({
  event: canonicalEventSchema,
  tool_filter: z.string().optional(),
  command_filter: z.string().optional(),
  script: z.string(), // ← Shell script filename (command hooks only)
  timeout: z.number().positive(),
  async: z.boolean(),
  status_message: z.string().optional(),
});
```

**Problem:** Schema has no `type` discriminator. The `script` field is required, meaning prompt hooks (which have no script, only a prompt string) cannot be represented.

## Options for Adding Prompt Hook

### Option A: Extend Canonical Schema (Over-engineering for SIMPLE phase)

Add a discriminated union:

```typescript
const CommandHookSchema = z.object({ hook_type: z.literal("command"), script: z.string(), ... });
const PromptHookSchema = z.object({ hook_type: z.literal("prompt"), prompt: z.string(), ... });
const CanonicalHookSchema = z.discriminatedUnion("hook_type", [CommandHookSchema, PromptHookSchema]);
```

Then update `config-generators.ts` to emit `type: "prompt"` entries. This is the "right" approach but adds significant scope.

### Option B: Bypass Canonical Registry (Recommended for SIMPLE phase)

Add the prompt hook directly to:

1. `settings-hooks.json` template (for luca init path)
2. `build-compile.ts` as a post-canonical-merge step (for dogfood path)

The prompt hook entry is a single JSON object — not a shell script. It can be added as a hardcoded JSON merge after the canonical registry hooks are generated.

### Option C: Add to settings-hooks.json Only + File a Follow-Up

Add to `settings-hooks.json` for user projects. For dogfood, the prompt hook can be added manually to `.claude/settings.json` during this phase's execution, with a follow-up todo to properly integrate it into the canonical registry.

**Problem:** The dogfood `.claude/settings.json` is regenerated by `build:all`, so any manual addition would be overwritten.

## Recommendation

**Option B** — Bypass the canonical registry for this single prompt hook:

1. Add prompt hook JSON to `settings-hooks.json` template
2. In `build-compile.ts`, after merging the canonical hooks fragment into settings.json, append the prompt hook entry to the `PreToolUse` array
3. This keeps the change minimal while ensuring both paths work

## Claude Code Prompt Hook Format

Based on Claude Code documentation pattern:

```json
{
  "type": "prompt",
  "prompt": "Check if this MuninnDB memory write is targeting the correct vault...",
  "matcher": "mcp__muninn__muninn_remember|mcp__muninn__muninn_remember_batch"
}
```

A prompt hook on PreToolUse with a matcher will fire only when the matched tool is about to be called. The LLM evaluates the prompt and can block the call by returning an error message.

## Global Rule Location

User-global rules live at `~/.claude/rules/`. The user already has 11 global rules there. The new `vault-guard.md` fits this pattern and will be loaded for all projects.

## init.ts Hook Wiring

`buildProposedHooksFromDeployed()` in `init.ts` (line 393) reads deployed hook files from the global hooks directory and builds a settings.json hooks structure. It only handles command hooks (builds `{ type: "command", command: "..." }` entries).

For prompt hooks deployed via `luca init`, the hook entry needs to be added to `settings-hooks.json` directly since `buildProposedHooksFromDeployed` only handles script-file-based hooks.
