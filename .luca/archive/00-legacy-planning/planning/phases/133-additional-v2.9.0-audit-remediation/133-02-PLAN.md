# Plan 133-02: Evaluate normalizing JSON blob fields in SpacetimeDB schema

## Objective

Evaluate whether the JSON blob fields in SpacetimeDB tables should be normalized into separate tables or kept as-is. This is issue #56 — a research/evaluation task, not an implementation task.

## Context

Several SpacetimeDB tables store JSON-serialized data in string fields (e.g., `contextJson`, `detailsJson`, `checksJson`, `metricsJson`, `configJson`). The question is whether normalizing these into proper relational tables would improve query performance, data integrity, or developer experience.

## Tasks

### Task 1: Catalog all JSON blob fields

Survey all `*Json` fields in `packages/luca-spacetime/spacetimedb/src/schema.ts` and categorize:

- Field name, parent table, approximate payload size
- Read/write frequency (hot path vs cold storage)
- Whether the JSON is ever queried/filtered on sub-fields

### Task 2: Assess normalization trade-offs

For each JSON blob field, evaluate:

- **Normalize if:** Sub-fields are queried, data has referential integrity needs, payload is large
- **Keep as blob if:** Write-once read-rarely, schema is dynamic/variable, SpacetimeDB limitations apply
- Consider SpacetimeDB's current capabilities (no JOIN support, limited query operators)

### Task 3: Write evaluation summary

Create `133-02-SUMMARY.md` with:

- Recommendation per field (normalize / keep as-is / defer)
- Rationale for each recommendation
- Overall assessment: "normalize now", "defer to future", or "keep as-is"

## Verification Criteria

- [ ] All JSON blob fields cataloged
- [ ] Trade-off analysis completed for each field
- [ ] Summary with clear recommendation written
- [ ] No code changes required (research only)
