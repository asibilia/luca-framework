# Phase 145 Plan 3: Revise Stale Engram Pruning in milestone-complete Skill

## Objective

Revise the existing Step 0.5 in milestone-complete to implement the conservative stale engram threshold from CONTEXT.md, add a human review checkpoint before deletion, integrate `muninn_consolidate()` for near-duplicate merging, and document that `muninn_forget` is soft-delete (7-day recovery).

The current Step 0.5 has a DIFFERENT stale definition (3+ recalls with low usefulness OR never recalled) that must be replaced with the CONTEXT.md definition (5+ recalls with 0 positive AND 3+ milestones no positive, BOTH required).

### 1. Revise stale detection threshold in Step 0.5

**Type:** auto
**TDD:** false
**Depends on:** none

In `src/skills/general/milestone-complete.skill.ts`, replace the ENTIRE stale detection logic in Step 0.5 section "2. Identify stale engrams".

**Current (REPLACE):**

```
An engram is "stale" if:
- It was recalled 3+ times across the milestone but received feedback with useful=false more than useful=true
- OR it was never recalled at all during the entire milestone
```

**New (BOTH conditions required):**

```
An engram is "stale" when BOTH conditions are met:

1. 5+ recalls with 0 positive feedback (useful=true) across the rolling window
2. 3+ milestones with no positive feedback

Steps to compute:
a. Recall last 10 phase metric engrams from MuninnDB
b. For each pattern/decision/pitfall engram that appeared in recalls:
   - Count total recalls across phases
   - Count positive feedback instances (useful=true)
   - Group by milestone, count milestones with 0 positive feedback
c. Flag engrams meeting BOTH thresholds
```

Update the MuninnDB recall query to fetch enough data for the rolling window:

```
mcp__muninn__muninn_recall(
  vault: "default",
  context: "pattern: decision: pitfall: metric:memory- feedback",
  mode: "deep",
  limit: 100
)
```

### 3. Replace automatic prune with forget-after-approval

**Type:** auto
**TDD:** false
**Depends on:** 2

Replace the current 3-way decision logic (forget/evolve/consolidate per engram) in Step 0.5 section "3. Prune stale engrams" with a simpler post-approval deletion pattern.

**New section "4. Prune after approval":**

For each approved engram:

```
mcp__muninn__muninn_forget(vault: "default", id: "{engram_id}")
```

Note in the skill content that `muninn_forget` performs a soft-delete with a 7-day recovery window. This is the strongest delete available in MuninnDB. If a mistake is made, the developer can use `muninn_restore` within 7 days.

Remove the old "evolve" path for stale engrams -- the CONTEXT.md decision is that stale engrams are deleted (after human approval), not evolved. Evolution is for engrams that are still useful but need content updates.

### 4. Add muninn_consolidate call

**Type:** auto
**TDD:** false
**Depends on:** 3

Add a new section "5. Consolidate near-duplicates" to Step 0.5, after the pruning step.

This runs at every milestone boundary regardless of whether stale engrams were found or pruned:

```
mcp__muninn__muninn_consolidate(vault: "default")
```

The consolidation step:

- Merges near-duplicate engrams using MuninnDB's built-in semantic similarity
- Reduces recall noise by collapsing redundant entries
- Runs AFTER pruning to avoid consolidating engrams that were just deleted
- Runs even if no stale engrams were found (deduplication is always valuable)

Log the consolidation result in the pruning report.
