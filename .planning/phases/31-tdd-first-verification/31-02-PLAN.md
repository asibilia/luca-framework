# Plan 31-02: Red-Green Verification Loop in lu-executor

## Objective

Replace the existing TDD stub in `lu-executor.agent.ts` with a complete Red-Green-Refactor cycle. When a plan or task has `tdd="true"`, the executor must: (1) spawn `lu-test-writer` to generate tests from verification criteria, (2) run those tests and confirm they FAIL (Red phase), (3) implement the task, (4) run the tests again and confirm they PASS (Green phase), (5) retry implementation if tests still fail (up to the harness fix iteration limit). Additionally, update `phase-execute.skill.ts` to propagate TDD context through to executor sub-agents so the orchestrator is aware of TDD phases.

## Context

@src/agents/luca/lu-executor.agent.ts -- The executor agent. Currently has a TDD stub at `execute_tasks` step: checks `task.tdd="true"` attribute but has no implementation beyond the mention. The full TDD cycle must replace this stub with concrete instructions for spawning lu-test-writer, running tests, confirming red/green, and retrying.
@src/agents/general/lu-test-writer.agent.ts -- The lu-test-writer agent created in Plan 31-01. The executor will spawn this agent via Task() to generate test files from plan verification criteria. Its output includes the test file path and test count.
@src/skills/general/phase-execute.skill.ts -- The phase-execute orchestrator skill. Step 4 spawns lu-executor for each plan in a wave. The execution_rules block must be updated to include TDD context (whether the plan has tdd=true, instructions for red/green phases).
@src/harness/runner.ts -- The harness runner that executes bun test, tsc, eslint checks. The executor uses `bun test {file}` directly for targeted TDD test runs, but the harness provides the broader verification after all tasks complete.
@.planning/phases/31-tdd-first-verification/RESEARCH.md -- Research findings including TDD cycle design, integration points, and the existing stub location.
@CLAUDE.md -- Project conventions (Bun-first, bun:test for testing).

## Tasks

### Task 1: Add TDD execution flow sections to lu-executor agent

**Goal:** Modify `src/agents/luca/lu-executor.agent.ts` to replace the TDD stub with a complete TDD execution flow. Add two new sections to the agent config: `tdd_execution_flow` and `tdd_retry_loop`. These sections contain the natural language instructions that tell the executor LLM how to handle TDD-flagged tasks.

**Files:** `src/agents/luca/lu-executor.agent.ts` (modify)

**Steps:**

1. Locate the `execute_tasks` section (order: 3) where the current TDD stub exists. The stub is the line:

   ```
   - Check if task has `tdd="true"` attribute -> follow TDD execution flow
   ```

   Replace it with a reference to the new TDD section:

   ```
   - Check if task has `tdd="true"` attribute -> follow TDD execution flow (see tdd_execution_flow section)
   - Check if plan frontmatter has `tdd: true` -> apply TDD to ALL tasks in this plan (see tdd_execution_flow section)
   ```

2. Add a new section `tdd_execution_flow` (order: 5) with this content:

   **TDD Execution Flow Instructions:**

   When a task or plan has `tdd="true"`, execute the following cycle BEFORE normal task implementation:

   **Step TDD-1: Spawn lu-test-writer**

   Spawn the `lu-test-writer` agent via Task() with the plan content, verification criteria, and success criteria as context:

   ```python
   Task(
     prompt="""
   <tdd_context>
   **Plan Content:**
   {plan_content}

   **Current Task:**
   {task_description}

   **Verification Criteria:**
   {verification_checklist}

   **Success Criteria:**
   {success_criteria}

   **Files to be created/modified:**
   {task_files_list}
   </tdd_context>

   Generate test files for this plan's verification criteria. Write tests that will FAIL before implementation (Red phase). Return the test file path and test count.
   """,
     subagent_type="lu-test-writer",
     description="Generate TDD tests for {task_name}"
   )
   ```

   Wait for the Task to return. Parse the output for:
   - `Test file:` path
   - `Tests generated:` count
   - `Testable tasks:` count
   - Any `testable: false` entries (skip TDD for those tasks)

   **Step TDD-2: Confirm RED Phase**

   Run the generated tests to confirm they fail:

   ```bash
   bun test {test_file_path} 2>&1
   TDD_RED_EXIT=$?
   ```

   **If tests FAIL (exit code != 0):** RED phase confirmed. Log to WORKING.md:

   ```bash
   echo "- $(date -u +%H:%M) [TDD-RED] Tests fail as expected ({test_count} tests, {failure_count} failures)" >> .planning/WORKING.md
   ```

   Proceed to implementation.

   **If tests PASS (exit code == 0):** RED phase VIOLATION. Tests should not pass before implementation. This indicates:
   - Tests are testing existing functionality (not new work)
   - Tests are trivial and don't actually verify the task
   - The code already exists (task may be unnecessary)

   Log the violation and proceed with caution:

   ```bash
   echo "- $(date -u +%H:%M) [TDD-RED-VIOLATION] Tests passed before implementation - investigating" >> .planning/WORKING.md
   ```

   Continue to implementation but flag this in the SUMMARY.

   **Step TDD-3: Implement the Task**

   Implement the task normally following all existing execution rules (deviation rules, commit protocol, etc.). The implementation should make the failing tests pass.

   **Step TDD-4: Confirm GREEN Phase**

   After implementation, run the tests again:

   ```bash
   bun test {test_file_path} 2>&1
   TDD_GREEN_EXIT=$?
   ```

   **If tests PASS (exit code == 0):** GREEN phase confirmed. Log:

   ```bash
   echo "- $(date -u +%H:%M) [TDD-GREEN] All {test_count} tests pass after implementation" >> .planning/WORKING.md
   ```

   Proceed to commit the task (implementation + test file together).

   **If tests FAIL (exit code != 0):** GREEN phase not achieved. Enter retry loop (see `tdd_retry_loop` section).

3. Add a new section `tdd_retry_loop` (order: 6) with this content:

   **TDD Retry Loop:**

   When tests fail after implementation (GREEN phase not achieved), retry the implementation:

   **Retry budget:** Use the same `harnessFixIterations` from the complexity matrix (read from `.planning/config.json`). Default: 3 iterations for MODERATE complexity.

   **For each retry iteration:**
   1. Analyze the test failures:

      ```bash
      bun test {test_file_path} 2>&1 | tail -50
      ```

   2. Identify what the tests expect vs what the implementation provides.

   3. Fix the implementation to make tests pass. Do NOT modify the tests -- the tests represent the specification.

   4. Re-run tests:

      ```bash
      bun test {test_file_path} 2>&1
      TDD_RETRY_EXIT=$?
      ```

   5. If tests pass: Exit retry loop, log GREEN, proceed to commit.

   6. If tests still fail and retries remaining: Continue to next iteration.

   7. If retries exhausted and tests still fail: Log failure and proceed with a warning:

      ```bash
      echo "- $(date -u +%H:%M) [TDD-FAIL] Tests still failing after {max_retries} retries. Proceeding with partial implementation." >> .planning/WORKING.md
      ```

      Commit the implementation as-is. The failing tests will be caught by the verification harness (Step 6.5) and the verifier (Step 7).

   **Critical rule:** NEVER modify test expectations to make tests pass. The tests are the specification. If tests are genuinely wrong (testing impossible behavior), document the issue and flag it for review, but do not silently change test assertions.

**Verification:**

- [ ] `src/agents/luca/lu-executor.agent.ts` has `tdd_execution_flow` section with TDD-1 through TDD-4 steps
- [ ] `src/agents/luca/lu-executor.agent.ts` has `tdd_retry_loop` section with retry budget and iteration cycle
- [ ] The `execute_tasks` section references the TDD flow for `tdd="true"` tasks
- [ ] Plan-level `tdd: true` frontmatter triggers TDD for ALL tasks in the plan
- [ ] `bunx --bun tsc --noEmit` passes

### Task 2: Update phase-execute skill with TDD context propagation

**Goal:** Modify `src/skills/general/phase-execute.skill.ts` to pass TDD context through to executor sub-agents. The orchestrator needs to detect `tdd: true` in plan frontmatter and include TDD-specific instructions in the executor spawn prompt.

**Files:** `src/skills/general/phase-execute.skill.ts` (modify)

**Steps:**

1. In Step 4 ("Execute Waves"), update the executor spawn prompt template. Before the `<execution_rules>` block, add TDD detection:

   ```
   **TDD Mode:** {tdd_enabled_or_disabled}
   ```

   Where `tdd_enabled_or_disabled` is determined by reading the plan's YAML frontmatter for a `tdd: true` field. If the plan has `tdd: true`, include:

   ```
   **TDD Mode:** ENABLED
   - Before implementing each task, spawn lu-test-writer to generate tests
   - Confirm RED phase (tests fail) before implementation
   - Confirm GREEN phase (tests pass) after implementation
   - Follow tdd_execution_flow section for detailed steps
   ```

   If the plan does NOT have `tdd: true`, include:

   ```
   **TDD Mode:** DISABLED (standard execution)
   ```

2. In the `<execution_rules>` block, add a TDD rule:

   ```
   - If TDD Mode is ENABLED: follow TDD execution flow (generate tests -> confirm RED -> implement -> confirm GREEN) for each task
   - If a task has `testable: false`: skip TDD for that task, execute normally
   ```

3. In the model lookup table (Step 0), add `lu-test-writer` entry:

   | Agent          | quality | balanced | budget |
   | -------------- | ------- | -------- | ------ |
   | lu-test-writer | sonnet  | sonnet   | haiku  |

4. In the sub-agent delegation list at the top, add `lu-test-writer`:

   ```
   - `lu-test-writer` - Generates test files from plan verification criteria (spawned by lu-executor during TDD cycle)
   ```
