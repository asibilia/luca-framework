    Structure as a template that enterprise teams can fill out or reference:

    1. **Introduction**: This questionnaire covers Luca's security posture for vendor assessments. Answers reference SECURITY.md.

    2. **Data Handling** section:
       - Q: What data does Luca access?
       - A: Project files, .planning/ directory, .cursor/ directory, git repository. No telemetry, no data collection.
       - Q: What data leaves the machine?
       - A: Only when using external adapters (Jira, GitHub Issues) - user explicitly configures these. No automatic data transmission.

       - A: Luca doesn't store data - uses local filesystem. External adapters use their own encryption (Jira HTTPS, GitHub HTTPS).

    3. **Access Control** section:
       - Q: How are permissions managed?
       - A: Approval gates configurable in .planning/config.json. Secure defaults: all approvals enabled. No auto-execution.
       - Q: What is the principle of least privilege?
       - A: Luca only accesses files in project directory. No system-level access. User controls all operations via approvals.

    4. **Audit Trail** section:
       - Q: How are actions logged?
       - A: Git commits track all changes. .planning/ artifacts log decisions. manifest.json tracks framework updates.
       - Q: Can actions be audited?
       - A: Yes, via git history. All planning artifacts timestamped. No separate audit log (uses git).

    5. **Supply Chain Security** section:
       - Q: How are dependencies managed?
       - A: Bun lockfile (bun.lock) pins all dependencies. Framework updates tracked via manifest.json.
       - Q: How are updates handled?
       - A: User-initiated via `npx luca update`. Conflict detection prevents overwrites. No auto-updates.

    6. **Compliance** section:
       - Q: What compliance frameworks does Luca align with?
       - A: General best practices (OWASP). No specific certifications (SOC 2, ISO) claimed.
       - Q: Can Luca be used in air-gapped environments?
       - A: Yes, core functionality works offline. External adapters require network but are optional.

  <files>
    docs/enterprise/offline-deployment.md
  </files>
  <action>
    Create `docs/enterprise/offline-deployment.md`:

    Structure:
    1. **Overview**: Luca can be deployed in air-gapped/offline environments. Core functionality requires no network.

    2. **Installation** section:
       - Download luca-framework package from npm registry (on connected machine)
       - Transfer to air-gapped machine
       - Install: `npm install -g luca-framework` or use local package
       - Initialize: `npx luca init` (works offline)
       - Note: External adapters (Jira, GitHub) require network but are optional

    3. **Updates** section:
       - Download new version on connected machine
       - Transfer to air-gapped machine
       - Run `npx luca update` (compares manifest, shows conflicts)
       - Manual update: Replace files in .cursor/luca/ if needed
       - Note: Update mechanism requires network to fetch latest, but can be done manually

    4. **MCP Configuration** section:
       - MCP servers may require network (Jira, GitHub MCP servers)
       - Core Luca functionality doesn't require MCP
       - MCP servers are optional enhancements
       - For fully offline: Don't configure external MCP servers

    5. **Limitations** section:
       - External work trackers (Jira, GitHub Issues) won't work offline
       - Update notifications won't work (no network to check)
       - All core planning, execution, verification works offline
       - Git-based workflow fully functional offline

    6. **Best Practices** section:
       - Test installation on connected machine first
       - Document version pinned in manifest.json
       - Use git for all changes (audit trail)
       - Configure approvals for production

    Reference SECURITY.md offline section. Be practical and specific.
  </action>
