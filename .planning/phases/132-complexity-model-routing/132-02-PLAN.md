# Plan 132-02: Wire model routing table and create sub-agent variants

## Objective

Wire `resolveModelForAgent()` into the existing `resolveModel()` priority chain so the centralized routing table participates in model selection. Create granular sub-agent variant definitions for key agents that benefit from complexity-aware model splitting. Mark deprecated step activation fields in `ComplexityGateSchema` with migration guidance.

## Context

Phase 132-01 created the model routing table (`src/complexity/__helpers/model-routing.ts`) with `resolveModelForAgent()` and the `MODEL_ROUTING_TABLE`, but it is not yet wired into the live `resolveModel()` priority chain in `src/agents/__helpers/resolve-model.ts`. The current 6-step chain is:

1. Agent's `complexity_overrides[level]`
2. Agent's `model_routing.default_model`
3. Agent's `model_tier` mapped via `MODEL_TIER_TO_MODEL`
4. Agent's `purpose` mapped via `ROLE_MODEL_DEFAULTS`
5. Complexity gate's `default_model`
6. `"sonnet"` universal fallback

The routing table should slot in between steps 3 and 4 — after per-agent frontmatter overrides but before generic role defaults. This gives the centralized table authority when an agent has no explicit `model_tier` or `complexity_overrides`, while preserving per-agent frontmatter as the highest priority.

Additionally, `ComplexityGateSchema` has 5 deprecated step activation fields (`research`, `discussion`, `codeReviewAgents`, `uat`, `learningCapture`) that are still populated in `DEFAULT_COMPLEXITY_MATRIX` and `session-init.ts`. These need clear migration notes but must NOT be removed yet — consumers in skills (`phase-plan.skill.ts`, `phase-execute.skill.ts`), rules (`complexity-gating.rule.ts`), and Pi extensions still reference them.

## Tasks

### Task 1: Wire `resolveModelForAgent()` into `resolveModel()` priority chain

**File:** `src/agents/__helpers/resolve-model.ts`

- Import `resolveModelForAgent` from `~/complexity`
- Add a new step 3.5 in `resolveModel()`: after checking `model_tier` (step 3) and before checking `purpose` (step 4), call `resolveModelForAgent(agentName, complexityLevel)` using the routing table
- This requires adding `agentName` as a parameter to `resolveModel()` — extract it from `agentFrontmatter.name` or accept as explicit param
- Update `resolveModelWithDecision()` to include `"routing_table"` as a new `source` variant
- Update the `ModelRoutingDecision.source` type to include `"routing_table"`
- Update all three resolve functions (`resolveModel`, `resolveModelWithZone`, `resolveModelWithDecision`) to thread the agent name through

**Verification:**

- [ ] `resolveModel()` for an agent in `MODEL_ROUTING_TABLE` at CRITICAL returns the table's tier (not the role default)
- [ ] `resolveModel()` for an agent NOT in `MODEL_ROUTING_TABLE` falls through to role default / gate default
- [ ] Per-agent `complexity_overrides` still take highest priority (step 1 unchanged)
- [ ] `bunx --bun tsc --noEmit` passes

### Task 2: Create sub-agent variant definitions

**Directory:** `src/agents/general/`

Create lightweight sub-agent variants for key agents that benefit from complexity-aware model splitting. These are full agent definitions (using `createAgent()`) that reference the same sections as the base agent but override `model_tier` and `model_routing`:

- `lu-router-fast.agent.ts` — A fast-tier variant of lu-router for TRIVIAL/SIMPLE tasks. Sets `model_tier: "fast"`, `model_routing.default_model: "haiku"`. Uses the same sections as lu-router but with a shorter system prompt focused on quick classification only.
- `lu-verifier-fast.agent.ts` — A fast-tier variant of lu-verifier for TRIVIAL/SIMPLE verification (quick mode). Sets `model_tier: "fast"`, `model_routing.default_model: "haiku"`. Uses simplified verification sections (existence + basic functionality only, no goal-backward analysis).
- `lu-executor-capable.agent.ts` — A capable-tier variant of lu-executor for COMPLEX/CRITICAL execution. Sets `model_tier: "capable"`, `model_routing.default_model: "opus"`. Uses the same sections as lu-executor.

Each sub-agent variant:

- Has its own `.agent.ts` file (kebab-case)
- Uses `createAgent()` from `~/agents/__helpers/create-agent`
- Has a distinct `name` (e.g., `"lu-router-fast"`)
- Has `purpose` matching the base agent
- Includes `allowed_contexts` matching the base agent
- Is exported from `src/agents/index.ts` barrel

**Verification:**

- [ ] Each sub-agent file creates a valid agent via `createAgent()`
- [ ] Sub-agents are exported from the agents barrel
- [ ] `bunx --bun tsc --noEmit` passes

### Task 3: Mark deprecated fields with migration guidance in schemas and defaults

**Files:**

- `src/complexity/__schemas/complexity.schemas.ts`
- `src/complexity/__helpers/defaults.ts`

Enhance the existing `@deprecated` JSDoc on the 5 step activation fields (`research`, `discussion`, `codeReviewAgents`, `uat`, `learningCapture`) with specific migration guidance:

For each field, add a `@migration` JSDoc tag explaining:

- What replaces it (model routing table + per-agent `model_tier`)
- How consumers should transition (e.g., "Instead of checking `gate.research === 'skip'`, use `resolveModelForAgent('lu-phase-researcher', complexity)` to determine if the researcher runs at a lightweight tier")
- When removal is planned (after all skill/rule consumers are migrated)

Add a block comment in `defaults.ts` above `DEFAULT_COMPLEXITY_MATRIX` documenting:

- Which fields are deprecated and their replacements
- That the matrix values are retained for backward compatibility with skill/rule consumers
- A reference to `MODEL_ROUTING_TABLE` as the forward-looking replacement

Do NOT remove any fields or change any runtime values. This is documentation-only.

**Verification:**
