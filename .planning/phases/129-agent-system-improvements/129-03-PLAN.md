# Plan 129-03: Skill dependency graph and tribunal consensus model

## Objective

Complete Phase 129's remaining two items: implement a skill dependency graph with topological ordering (#54) and enhance the tribunal debate system with a configurable consensus model supporting multiple resolution strategies (#55).

## Context

- **Skill system**: `src/skills/` (T2 Entity domain). Registry in `__helpers/build-skill-registry.ts` maps 47 skill names to factory functions. `SkillConfigSchema` defines frontmatter + sections. No dependency metadata exists between skills.
- **Tribunal system**: `src/shared/` (T0 Foundation). Already has `tribunal-detector.ts` (normalize findings, detect disagreements, gate check), `tribunal-rebuttals.ts` (build prompts, resolve rebuttals, build result), `tribunal-consensus.ts` (majority-vote resolution for exactly 3 perspectives). The consensus model is hardcoded to 3-perspective majority vote with no configurable thresholds, no expert weighting, and no fallback resolver.
- **Tier compliance**: Skill dependency schema goes in `src/skills/__schemas/` (T2). Consensus model enhancement goes in `src/shared/__schemas/` and `src/shared/__helpers/` (T0) since it's consumed by both agents and skills tribunal patterns.

## Tasks

### Wave 1: Schemas (both features, no cross-dependency)

#### Task 1: Add skill dependency schema

- Create `src/skills/__schemas/skill-dependencies.ts`
- Define `SkillDependencySchema` with Zod:
  - `skill_name`: z.string() — the skill this entry describes
  - `required_before`: z.array(z.string()).default([]) — skills that must run before this one
  - `blocked_by`: z.array(z.string()).default([]) — skills that block this one from running
  - `mutually_exclusive`: z.array(z.string()).default([]) — skills that cannot run concurrently
  - `parallel_safe`: z.boolean().default(true) — whether this skill can run in parallel with others
- Define `SkillDependencyMapSchema` as z.record(z.string(), SkillDependencySchema)
- Export types via z.infer
- Use snake_case per API schema convention

#### Task 2: Add consensus model schema

- Create `src/shared/__schemas/consensus.schemas.ts`
- Define `ConsensusMode` enum: `"unanimous"`, `"majority"`, `"supermajority"`, `"expert_weighted"`
- Define `ConsensusConfigSchema` with Zod:
  - `mode`: consensusModeSchema.default("majority")
  - `required_agreement`: z.number().min(0).max(1).default(0.5) — threshold (e.g., 0.67 = 2/3)
  - `expert_agents`: z.array(z.string()).default([]) — agents whose votes count double
  - `fallback_strategy`: z.enum(["highest_confidence", "halt", "escalate"]).default("highest_confidence")
  - `min_perspectives`: z.number().int().positive().default(2) — minimum voters required
- Export types via z.infer

### Wave 2: Helpers (depend on Wave 1 schemas)

#### Task 3: Implement topological sort and conflict detection for skill dependencies

- Create `src/skills/__helpers/dependency-graph.ts`
- Implement `buildDependencyOrder(deps: SkillDependencyMap, requested: string[]): string[]`
  - Topological sort of requested skills based on `required_before` edges
  - Detect circular dependencies and throw descriptive error
- Implement `detectConflicts(deps: SkillDependencyMap, requested: string[]): string[]`
  - Check `mutually_exclusive` constraints among requested skills
  - Return array of conflict descriptions (empty = no conflicts)
- Implement `groupParallelBatches(deps: SkillDependencyMap, ordered: string[]): string[][]`
  - Group skills into parallel-safe batches based on `parallel_safe` flag and `blocked_by` constraints
  - Skills in the same batch can execute concurrently
- All functions are pure (no side effects, no imports above T0)

#### Task 4: Implement configurable consensus resolver

- Create `src/shared/__helpers/consensus-resolver.ts`
- Implement `resolveConsensus<T>(perspectives: VotablePerspective<T>[], config: ConsensusConfig): ConsensusResult<T>`
  - Generalizes `resolveMajorityVote` to support N perspectives (not just 3)
  - Mode "unanimous": all must agree
  - Mode "majority": >50% (or `required_agreement` threshold)
  - Mode "supermajority": uses `required_agreement` as threshold (e.g., 0.67)
  - Mode "expert_weighted": expert agents' votes count double, then apply majority
  - Fallback: when no mode produces consensus, apply `fallback_strategy`
- Return `ConsensusResult<T>` with: `consensus_category`, `consensus_voters`, `dissenters[]`, `consensus_confidence`, `mode_used`, `fallback_applied`
- Keep `resolveMajorityVote` in `tribunal-consensus.ts` unchanged (backward compat); the new resolver is an additive alternative

### Wave 4: Tests

#### Task 7: Test skill dependency graph

- Create `__tests__/src/skills/dependency-graph.test.ts`
- Test cases:

  - Circular dependency throws error
  - Mutually exclusive skill conflict detection
  - Parallel batching groups independent skills together

#### Task 8: Test consensus resolver

- Create `__tests__/src/shared/consensus-resolver.test.ts`
- Test cases:

  - Majority mode: 3/5 agree -> consensus; 2/5 -> no consensus
  - Supermajority mode with 0.67 threshold: 2/3 passes, 1/3 fails
  - Expert-weighted mode: expert vote counts double
  - Fallback strategies: highest_confidence, halt, escalate
  - Edge case: single perspective with min_perspectives=2 -> fallback
  - Backward compat: existing `resolveMajorityVote` still works unchanged
