# 43-02: Build System Conditional Includes, Codebase-Mapper Integration, Placeholder Profiles, Tests

## Objective

Complete the tech stack guideline profile system by wiring conditional build output (STACK-05), integrating with lu-codebase-mapper for auto-detection (STACK-04), creating placeholder profiles for python/go/rust (STACK-01 completion), and adding comprehensive tests. After this plan, the build system conditionally includes/excludes guidelines per profile, the codebase mapper detects and suggests profiles, and placeholder profiles are ready for future stack rule development.

## Context

### Prerequisites (from 43-01)

- Profile directory structure exists: `src/rules/profiles/{typescript,python,go,rust}/`
- TypeScript profile contains 8 migrated rules with working registry
- Config fields added: `workflow.opinionated_guidelines` and `workflow.tech_stack_profiles`
- `src/rules/index.ts` builds a profile-aware `ruleRegistry` from general + active profile rules
- Build output with default config is identical to pre-migration (backward compatible)

### Current Build Pipeline

- `scripts/build-shared.ts` has `generateRuleOutputs()` which iterates `ruleRegistry` from `src/rules/index.ts`
- `scripts/build-all.ts` calls `generateAllOutputs()` and writes to `.claude/`, `.cursor/`, `dist/plugin/`
- `scripts/check-drift.ts` regenerates outputs in memory and compares against committed files
- The `ruleRegistry` is consumed as `Record<string, () => BaseRule>` -- the build system is registry-driven

### Codebase Mapper

- `lu-codebase-mapper` agent has a "tech focus" that writes `STACK.md` and `INTEGRATIONS.md`
- The tech mapper already looks at `package.json`, `requirements.txt`, `Cargo.toml`, `go.mod`
- The `codebase-map` skill orchestrates 4 parallel mapper agents and collects confirmations
- Stack detection currently produces descriptive text but no structured profile suggestions

### Design Decisions

1. **Build system is already registry-driven**: Since `generateRuleOutputs()` iterates `ruleRegistry` and `ruleRegistry` is already profile-aware (from 43-01), the build system mostly "just works." This plan adds logging, drift detection updates, and verification.
2. **Mapper integration via structured STACK.md section**: Rather than creating a separate detection module, we extend the mapper's STACK.md template with a `## Detected Profiles` section containing machine-readable profile suggestions.
3. **Skill reads STACK.md post-mapping**: The codebase-map skill reads the generated STACK.md after all agents complete to extract profile suggestions. This keeps the flow simple and avoids agent-to-agent data passing.
4. **Placeholder profiles with empty rules**: Python, go, and rust profiles start with zero rules. They validate the registry and serve as documented extension points. Future phases can add stack-specific rules.
