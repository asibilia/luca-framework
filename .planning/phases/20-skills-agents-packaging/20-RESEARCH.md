### 1.2 Skill Format (Current)

Compiled SKILL.md files follow this format (from `git-commit/SKILL.md`):

```markdown
# git-commit

Create a commit using the interactive commit tool. Use when the user wants to commit changes, make a commit, save changes to git, or stage and commit code.

## main

<main>
# Git Commit
...full skill content...
</main>
```

The H1 line is the skill name, followed by the description, then H2 sections with content. Generated by `BaseSkillImpl.toClaudeFormat()`:

```typescript
toClaudeFormat(): string {
    return toClaudeFormat(`# ${this.name}\n\n${this.description}`, this._config.sections);
}
```

And `shared/format.ts`:

```typescript
export function toClaudeFormat(heading: string, sections: Section[]): string {
  const body = sections
    .sort((a, b) => (a.order || 0) - (b.order || 0))
    .map((section) => `## ${section.title}\n\n${section.content}\n\n`)
    .join("")
    .trim();
  return `${heading}\n\n${body}`;
}
```

### 1.5 Rule Format (Current)

There are **two** `lu.skill.ts` files:

## 4. /lu Skill Chaining Investigation

### 4.1 Root Cause

The `/lu` skill (`src/skills/luca/lu.skill.ts` and `src/skills/general/lu.skill.ts`) is an **orchestrator** that describes a workflow diagram:

```
User Request → Git Context → Cognitive Pre-Flight → Complexity Classification
    → TRIVIAL/SIMPLE: Direct Execute
    → MODERATE: Quick Plan
    → COMPLEX/CRITICAL: Full Pipeline
→ Verify → Learn → Commit
```

The problem: **The /lu skill instructs Claude to perform all these steps inline** — it describes the workflow as a series of steps Claude should execute directly. It does NOT instruct Claude to invoke other skills (like `/lu-discuss-phase`, `/lu-plan-phase`, `/lu-execute-phase`) as separate skill calls.

Specifically, the `/lu` skill's workflow section says:

- For COMPLEX/CRITICAL → "Full Pipeline" — but it never says "invoke /lu-plan-phase" or "invoke /lu-execute-phase"
- The sub-agent delegation section mentions spawning agents (lu-verifier, lu-learner) via the Task tool, but does NOT mention invoking other **skills** as skill calls.

### 4.2 Why It Doesn't Chain

1. **Skill invocation mechanism**: In Claude Code, a skill is invoked via the Skill tool (`Skill(skill: "name", args: "...")`). The `/lu` skill's content never instructs Claude to call the Skill tool for sub-skills.

2. **The skill was designed as a monolithic orchestrator**: It contains the complete workflow inline — git context setup, cognitive pre-flight, complexity routing — all as instructions within the skill body, not as references to other skills.

3. **Agent vs Skill distinction**: The skill correctly delegates to **agents** (lu-verifier, lu-learner) via the Task tool but conflates agent delegation with skill invocation. Skills and agents are different primitives in the plugin system.

### 4.3 Fix Approach

The `/lu` skill needs to be rewritten to act as a **routing skill** that invokes sub-skills instead of inlining their behavior. The rewrite should:

1. **Keep lightweight routing logic** in `/lu`:
   - Parse arguments (task description, Jira URL, ticket ID)
   - Determine if this is a new project, existing phase work, PR work, debug, etc.
   - Classify complexity (or invoke lu-router agent)

2. **Invoke sub-skills via the Skill tool** for each workflow branch:

   ```
   For COMPLEX/CRITICAL new work:
     1. Invoke Skill("lu-discuss-phase", args: "{phase}")
     2. Invoke Skill("lu-plan-phase", args: "{phase}")
     3. Invoke Skill("lu-execute-phase", args: "{phase}")

   For TRIVIAL/SIMPLE:
     1. Invoke Skill("lu-quick", args: "{task}")

   For PR work:
     1. Invoke Skill("lu-address-pr", args: "{pr-url}")

   For debug:
     1. Invoke Skill("lu-debug", args: "{description}")
   ```

3. **Update the skill content** to instruct Claude to use the Skill tool:

   ```markdown
   ### Routing

   Based on complexity classification:

   **TRIVIAL/SIMPLE**: Invoke the lu-quick skill:
   ```

   Skill(skill: "lu-quick", args: "{task description}")

   ```

   **MODERATE+**: Follow the full phase pipeline:
   1. Invoke Skill(skill: "lu-discuss-phase", args: "{phase}")
   2. Invoke Skill(skill: "lu-plan-phase", args: "{phase}")
   3. Invoke Skill(skill: "lu-execute-phase", args: "{phase}")
   ```

4. **Considerations:**
   - Claude Code's Skill tool invocation is sequential (one skill at a time).
   - Each skill invocation starts a new skill context — the user sees the skill header, gets the full skill instructions loaded.
   - The `/lu` skill should return control to the user between major steps (or chain them if Claude's skill execution supports it).
   - Need to verify if Claude Code supports skill-to-skill invocation within a skill's execution context.

### 4.4 Plugin Skill-to-Skill Invocation

In Claude Code's plugin system, when a skill is loaded, Claude receives the SKILL.md content as instructions. Claude can then:

- Use the Skill tool to invoke another skill (if available)
- Use the Task tool to spawn sub-agents

The question is whether invoking a Skill from within a Skill is supported. Based on the Claude Code architecture (skills are loaded into the context window, and Claude has access to the Skill tool), this should work. The skill content would instruct Claude: "Now invoke the Skill tool with skill='lu-plan-phase'."

**Risk**: If the Skill tool is not available within a skill execution context, the chaining won't work. In that case, the fallback is to have `/lu` output a message telling the user which skill to invoke next (manual chaining).
